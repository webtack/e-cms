# Design

## Context

Поле — модель `ContentField` (`content_fields`, `is_multiple`, `settings` json, що для нефайлових типів заборонений правилом `settings => prohibited`). Правила форм поля — `StoreContentFieldRequest::sharedRules()` (їх успадковує `UpdateContentFieldRequest`). Значення пише й перевіряє `ContentValueWriter::validate()`: для множинного поля правила `[$presence, 'array']` + `{key}.*`. Форма запису — `ContentNodeForm.tsx` → `NodeFieldList` (множинні) / `NodeFieldInput` (одиночні); блок «Назва»/«Опис» файлу — `FileMetaFields` у `NodeFieldInput`, що передається у `details` віджета `FileUpload`. Метадані файлів їдуть ключем `file_meta` (див. архівну зміну `edit-file-metadata-in-node-form`); цей контракт не змінюється. Опис компонентів: [`docs/admin-content-fields.md`](../../../docs/admin-content-fields.md), [`docs/admin-content-nodes.md`](../../../docs/admin-content-nodes.md), [`docs/file-storage.md`](../../../docs/file-storage.md), [`docs/e2e-testing.md`](../../../docs/e2e-testing.md).

## Goals / Non-Goals

**Goals:**
- Ліміт елементів для будь-якого множинного поля, що дотримується і формою, і сервером.
- Компактний блок файлу: метадані редагуються в модальному вікні.

**Non-Goals:**
- Мінімальна кількість елементів; ліміт для немножинних полів; зміна контракту `file_meta`; автоматичне обрізання вже збережених списків при зменшенні ліміту.

## Decisions

1. **Окремий стовпець `content_fields.max_items`** — `unsignedSmallInteger`, `default 0`, міграція `add_max_items_to_content_fields_table`. *Альтернатива:* `settings.max_items` — відкинуто не через те, що `settings` «для файлових типів» (він задуманий як специфічні налаштування будь-якого поля, і правило `prohibited` для решти типів — лише поточний стан, якого ця зміна не чіпає й не закріплює), а тому, що ліміт — загальна властивість множинності поряд з `is_multiple`, а не налаштування конкретного типу значення; окремий стовпець також не потребує розширювати валідацію й форму `settings` на всі типи. Не входить у `SYSTEM_LOCKED` (системні поля не множинні).
2. **Правила:** `max_items` — `nullable|integer|between:0,65535` у `sharedRules()`; `null`/відсутнє → `0`. Для `is_multiple = false` значення примусово скидається в `0` перед збереженням (у контролері, як і решта нормалізації; модель лишається останнім бар'єром). `ContentFieldController` додає `max_items` у `only([...])` форми й відповіді; `formFields()` віддає `max_items` у `NodeField`.
3. **Сервер:** у `ContentValueWriter::validate()` для множинного поля з `max_items > 0` до `[$presence, 'array']` додається `max:{max_items}`. `normalize()` уже відкидає порожні елементи, тож рахуються лише непорожні. Повідомлення — стандартне `max.array`, ключ помилки — `values.{key}` (форма показує біля поля).
4. **Форма поля (`ContentFieldForm.tsx`):** `Input type=number` (`min=0`, `max=65535`) «Максимальна кількість елементів» з підказкою «0 — без обмеження» показується під прапорцями, лише коли `is_multiple` увімкнено; при вимкненні значення скидається в `0`.
5. **Форма запису:** `NodeFieldList` отримує `max = field.max_items` і рахує `full = max > 0 && value.length >= max`. «Додати елемент» — `disabled={full}`. Для файлових полів `FileUpload` (multiple) отримує `disabled` за `full` і підказку; у `addFiles`-шляху пакет обрізається до `max - value.length` **до** завантаження (нова опція віджета/обгортки — перелік дозволених файлів: ті, що не вміщуються, не завантажуються, а їхні імена йдуть у повідомлення «Ліміт: :max»). Лічильник «n / max» — поруч із підписом поля в `ContentNodeForm` (лише для `max > 0`). *Альтернатива:* завантажувати все й обрізати — відкинуто: зайві файли лишилися б у сховищі без використання.
6. **Модальне вікно:** новий `Components/ui/dialog.tsx` (оболонка над `radix-ui` `Dialog`, у стилі наявного `alert-dialog.tsx`). `FileMetaFields` замінюється на `FileMetaDialog`: кнопка (іконка олівця, `aria-label` «Редагувати дані файлу») відкриває вікно з чернеткою (`name`, `description`), «Готово» викликає `editor.onChange(uuid, draft)` й закриває, «Скасувати»/Escape/зовнішній клік закривають без змін. Чернетка ініціалізується при відкритті зі стану форми. *Альтернатива:* редагувати стан форми напряму у вікні — відкинуто: «Скасувати» тоді вимагало б окремого відкату.
7. **Розміщення кнопки:** кнопка належить блоку файлу. `FileUpload` отримує необов'язковий слот `actions` (ReactNode) у рядку кнопок блоку, поруч із «Видалити файл» (`removable`). У рядку множинного поля `removable={false}`, тож `actions` займає місце колишнього хрестика; в одиночному — стоїть поруч із «Видалити файл». `details` лишається (для сумісності/інших споживачів), але форма запису ним більше не користується. Демо-сторінка не змінюється.
8. **Помилки метаданих:** оскільки поля сховано у вікні, `NodeFieldInput` показує помилки `file_meta.{uuid}.*` під блоком файлу текстом (`role="alert"`), а у вікні вони теж показуються біля відповідних полів; кнопка отримує `aria-invalid`.

## Risks / Trade-offs

- [Ліміт зменшили нижче наявної кількості елементів → запис не зберегти, доки не прибрати зайве] → прийнято свідомо, форма показує лічильник вище за ліміт і помилку сервера; дані не обрізаються мовчки.
- [Прихований стан у модальному вікні: користувач натиснув «Готово», але не «Зберегти»] → зміни живуть лише у формі, як і решта полів; цей же стан зберігає поточну поведінку guard-а незбережених змін, якщо він є.
- [Обрізання пакета до вільних місць: частина вибраних файлів не завантажується] → повідомлення називає пропущені файли й ліміт.
- [Два місця правди про ліміт (форма і сервер)] → сервер — остаточний бар'єр; форма лише зручність.

## Migration Plan

`docker compose exec app php artisan migrate` додає стовпець з `0` для наявних полів (поведінка не змінюється). Відкат — `migrate:rollback` (ліміти зникають).
