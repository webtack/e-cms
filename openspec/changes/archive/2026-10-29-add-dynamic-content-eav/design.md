# Design

## Context

Laravel 13 / PHP 8.3, MySQL у Docker (`ecms_db`); тести працюють на SQLite `:memory:` (див. `phpunit.xml`). У `app/Models` зараз лише `User`. Мотивацію й обсяг див. у `proposal.md`. Код пишеться англійською з докблоками, документація в `docs/` — українською.

## Goals / Non-Goals

**Goals:**
- Структура контенту — це дані; нові типи контенту/полів не потребують міграцій.
- Новий тип значення = один клас + одна міграція таблиці + рядок у конфігурації реєстру; ядро не змінюється.
- Переклади — звичайні рядки значень з іншим `lang`, придатні для фільтрації й сортування в БД.
- Вибірка за динамічними полями виконується в БД (фільтр, пошук, сортування, пагінація), а не в PHP.

**Non-Goals:**
- UI адмінки, HTTP-контролери/API, конструктор блоків, міграція старої системи.
- Ієрархія вузлів (дерево сторінок), публічні шляхи з кількох сегментів, редиректи при зміні slug, зв'язки між вузлами, файли/зображення, версіонування, права доступу.
- Підстановка `default` при відсутньому перекладі, переклад назв полів/типів, UI керування мовами, самі фронтенд-сторінки (надається лише PHP-доступ до налаштувань мов), зміна мови інтерфейсу адмінки (`admin-i18n` не зачіпається).
- Повнотекстовий пошук (лише `LIKE`).

## Decisions

### 1. Схема таблиць

- `content_types`: `id` (PK), `key` `VARCHAR(64)` (unique, незмінний, формат `^[a-z][a-z0-9_]*$`; на нього посилаються зв'язки з типом), `name` `VARCHAR(255)`, `description` `TEXT` null (довільний опис типу для адмінки; не впливає на поведінку), `parent_type` `VARCHAR(64)` null (FK → `content_types.key`, self-FK, `restrictOnDelete`), `kind` `VARCHAR(32)` default `'content'`, `settings` JSON null, timestamps.
- `content_fields`: `id`, `content_type` `VARCHAR(64)` (FK → `content_types.key`, cascade), `key` `VARCHAR(64)` (незмінний, формат `^[a-z][a-z0-9_]*$`, як у ключа типу), `name` `VARCHAR(255)`, `type` `VARCHAR(32)` (ключ із реєстру), `is_multiple`, `is_required`, `is_translatable`, `is_system` (усі boolean, default `false`), `weight` unsigned small int default 0, `settings` JSON null, timestamps; unique (`content_type`, `key`).
- `content_nodes`: `id`, `uuid` `CHAR(36)` (unique), `content_type` `VARCHAR(64)` (FK → `content_types.key`, cascade), `slug` `VARCHAR(190)` NOT NULL (unique, зі збіркою без урахування регістру), timestamps; index (`content_type`, `id`); unique (`id`, `content_type`) — ціль складеного FK таблиць значень (див. нижче).
- Зв'язки з типом (`parent_type`, `content_fields.content_type`, `content_nodes.content_type`) посилаються на `content_types.key`, а не на `id`: `key` унікальний і незмінний, тож FK стабільний між середовищами й не потребує мапи `id` при імпорті; `ON UPDATE` не потрібен. Колонки FK мають ту саму колацію й довжину, що й `content_types.key`. Таблиці значень посилаються на поле парою (`content_type`, `field_key`) → `content_fields(content_type, key)` і на вузол через `id` та тип (див. нижче).
- Усі три таблиці та `app_languages` створюються однією міграцією на таблицю одразу з усіма колонками (`kind`, `parent_type`, `slug` тощо): таблиці нові, окремі «додавальні» міграції не потрібні. «Node» не означає дерево вузлів: ієрархія є лише в типах (`content_types.parent_type`), а parent-зв'язку вузлів немає (див. Non-Goals).
- `app_languages` (загальна системна таблиця мов; до контенту їх застосовує сервіс `ContentLanguages`): `id`, `code` `VARCHAR(16)` (unique, бінарна колація `utf8mb4_bin`; лише нормалізований вигляд, див. §3), `name` `VARCHAR(255)`, `is_active` default `false`, `weight` unsigned small int default 0, timestamps.
- `app_settings`: `key` `VARCHAR(191)` (PK), `value` JSON NOT NULL (JSON `null` — валідне значення), timestamps. Загальне сховище для ядра й будь-яких модулів; ключі `модуль.назва`. Вмикач багатомовності — `content.multilingual` (відсутній = `false`).
- Таблиці значень `content_values_{string,text,integer,decimal,boolean,date,datetime}`: `id`, `content_node_id` (→ `content_nodes.id`), `content_node_uuid` `CHAR(36)` (`uuid` вузла, для імпорту/експорту; заповнює й не змінює модель), `content_type` `VARCHAR(64)` (окремого FK немає: існування типу гарантує складений FK на поле), `field_key` `VARCHAR(64)`, `lang` `VARCHAR(16)` NOT NULL default `'default'` (бінарна колація `utf8mb4_bin`, нормалізований код), `weight` unsigned small int default 0, `value` (відповідний тип), `options` JSON null. Колонки `field_id` немає: поле визначається парою (`content_type`, `field_key`). Зовнішні ключі: складений (`content_type`, `field_key`) → `content_fields(content_type, key)` (cascade: видалення поля видаляє його значення); складений (`content_node_id`, `content_type`) → `content_nodes(id, content_type)` (cascade) — він гарантує на рівні БД, що тип у значенні збігається з типом вузла, а отже поле належить типові вузла. Унікальний індекс (`content_node_id`, `content_type`, `field_key`, `lang`, `weight`).

Типи колонок `value`: string — `VARCHAR(512)`, text — `LONGTEXT`, integer — `BIGINT`, decimal — `DECIMAL(20,6)`, boolean — `TINYINT(1)` (0/1), date — `DATE`, datetime — `DATETIME`; усі NOT NULL (відсутність значення = відсутність рядка).

**Чому окремі таблиці, а не одна з `value_*` колонками чи JSON:** кожен тип має власний індекс і правильне порівняння/сортування на рівні БД; JSON-колонка не дає типізованих індексів. Альтернатива «одна таблиця зі строковим value» відкинута через некоректне числове/датове сортування.

**Переклади через `lang` у рядку значення, не в JSON і не окремими таблицями.** Альтернатива «JSON `{lang: value}`» відкинута: ламає типізований індекс, фільтрацію й сортування за мовою. Альтернатива «окрема таблиця перекладів» — зайва, бо значення вже EAV. `lang = 'default'` — значення без мови/базова мова; інші коди — перекладені. `options` залишається для додаткових налаштувань значення, а не для перекладів.

**Ключ значення — пара (`content_type`, `field_key`), а не числовий `field_id`:** `key` поля й тип незмінні, тож зв'язок однаковий у всіх середовищах і не потребує мапи `id` при імпорті, а вибірка не шукає `field_id` окремим запитом. Ціна: до 128 байтів і ширші індекси на рядок значення (замість одного числа), плюс `content_node_uuid` (36 байтів) на рядок. Тип у значенні дублює `content_nodes.content_type`, тому узгодженість забезпечує складений FK на `content_nodes(id, content_type)`.

### 2. Системне поле `title`

`ContentType::created` (в тій самій транзакції, що й створення типу) вставляє поле `title`: type `string`, `is_required = true`, `is_multiple = false`, `is_translatable = true`, `is_system = true`, `weight = 0`. Модель `ContentField` відхиляє `deleting` для `is_system` (окрім каскаду від видалення типу, який виконується на рівні БД FK і не викликає подій моделі) і відхиляє `updating` зміни `key`, `type`, `is_multiple`, `is_required`, `is_system` для системних полів. Метод `ContentType::create` через Eloquent — єдиний шлях створення, тож `title` гарантовано з'являється; тест перевіряє це і через фабрику.

**Альтернатива:** вимагати створювати `title` вручну — відкинута за вимогою продукту. **Альтернатива:** колонка `title` у `content_nodes` — відкинута: `title` має бути перекладним і однаково фільтруватися/сортуватися, як решта полів.

### 2a. Вид типу контенту (`kind`)

Сторінки й блоки — це типи контенту з іншим `kind`, а не окремі таблиці: вони ділять поля, значення, переклади й вибірку. Допустимі значення беруться з `config/content.php` (`'kinds' => ['content', 'page', 'block']`), тож додати вид пізніше = рядок у конфігурації. `ContentType` валідує `kind` проти конфігурації та забороняє його зміну після створення (`updating`), незалежно від наявності вузлів. Scope `ContentType::ofKind($kind)` для переліку типів; `ContentNodeQuery` лишається прив'язаним до одного типу і виду не знає; пошук вузла за slug — окремий метод `ContentNode::findBySlug`. Поведінка, специфічна для видів (дерево сторінок, `slug`, розміщення блоків, вкладення блоків, поле-посилання на вузол, публікація), свідомо винесена в майбутні зміни: вони мають розширювати модель допоміжними таблицями 1:1 до `content_nodes` або новими типами полів, не змінюючи ядро.

**Альтернативи:** окремі таблиці `pages`/`blocks` — відкинуті (дублювання EAV); без дискримінатора — відкинуто (різні інваріанти й окремі списки в адмінці); вид `section` — відкинуто (розділ — це сторінка з дочірніми сторінками, вирішується деревом пізніше).

### 2b. Ієрархія типів

`parent_type` (`key` батьківського типу) — організаційне дерево типів (групи типів у навігації адмінки тощо); поля й налаштування не успадковуються (простіше й без неочікуваних наслідків при зміні батька; успадкування — окрема зміна за потреби). `ContentType` при збереженні перевіряє: батько існує, `kind` збігається, нема циклів (підйом по ланцюгу `parent_type`); FK `restrictOnDelete` не дає видалити тип із дочірніми. Видалення типу без дочірніх каскадує як раніше. Scope `ContentType::childrenOf`/`roots`.

### 2c. Slug вузла

Slug — колонка `content_nodes.slug`, а не EAV-поле: він потрібен для унікальності на рівні БД, пошуку за O(1) та не перекладається. Унікальність — спільна для всіх видів одним індексом (колація `utf8mb4_0900_ai_ci`/`NOCASE` у SQLite, значення й так зберігаються малими літерами).

Створення вузла йде через `ContentNodeCreator::create(ContentType, array $values, ?string $slug = null, string $lang = 'default')` — єдиний шлях, бо `slug` NOT NULL, а `title` лежить у значеннях: у транзакції валідуються значення (`ContentValueWriter` у режимі `$creating`), визначається slug, вставляється вузол, записуються значення. Модель `ContentNode` додатково на `saving` перевіряє формат (`^[a-z0-9]+(-[a-z0-9]+)*$`, ≤190), префікс `block-` (обов'язковий для `block`; для інших видів не обмежується) і не дає змінити slug неявно (зміна лише через присвоєння).

`SlugGenerator`: для `content`/`page` — `Str::slug($title, '-', 'uk')` (транслітерація), порожній результат → `node`; префікс не додається, slug із початковим `block-` допустимий; для збігу — шукає вільний суфікс `-2`, `-3`, … (один запит `LIKE base%`, не цикл запитів). Для `block` — `block-` + 8 символів `a–z` (`Str::random` з обмеженим алфавітом), повтор при збігу (кілька спроб, далі помилка). Явний slug ніколи не змінюється генератором.

**Рішення (підтверджено власником) про `block-[8 [a-z-]]`:** автоматична частина — 8 малих латинських літер без дефісів (дефіс у випадковій частині давав би початкові/кінцеві/подвійні дефіси, що суперечить формату slug); дефіси допустимі у ручних slug. **Гонки:** унікальний індекс — остаточний арбітр; при порушенні генератор повторює спробу один раз, явний slug повертає помилку валідації. Публічний шлях як ієрархія (`parent/child`) і маршрутизація — майбутні зміни; поки slug — один сегмент.

**Альтернативи:** slug як EAV-поле — відкинуто (немає глобальної унікальності й дешевого пошуку); окремі простори унікальності за видом — відкинуто за вимогою продукту (один ідентифікатор для всіх трьох видів).

### 2d. Стабільний `uuid` вузлів та ідентичність типів і полів

`content_nodes` має колонку `uuid` (`CHAR(36)`, NOT NULL, unique). Це зовнішній стабільний ідентифікатор: `id` відрізняється між середовищами, `slug` вузла може змінюватися, а `uuid` — ні. Тип і поле `uuid` не мають. `key` типу унікальний у всій таблиці, незмінний (`updating` відхиляє зміну) і відповідає формату `^[a-z][a-z0-9_]*$`, тож сам є стабільним ідентифікатором, а зв'язки з типом посилаються саме на нього (див. §1). `key` поля теж незмінний, а унікальний у межах типу, тож ідентичністю поля між середовищами є пара (`content_type`, `key`) — та сама, якою на поле посилаються значення. `uuid` призначений для зіставлення вузлів при імпорті/експорті (повторний імпорт оновлює вузол із тим самим `uuid`, а не дублює його).

Генерується автоматично при створенні (UUID v7 через `HasUuids`/`Str::uuid7`; впорядкований формат менше фрагментує індекс). Явно заданий `uuid` (імпорт) зберігається як є, якщо він валідний і вільний. Після створення `uuid` не змінюється (`updating` відхиляє зміну). `ContentNode::findByUuid` повертає вузол або `null`; `ContentType::findByKey` — тип за ключем або `null`. Первинні ключі й зв'язки значень лишаються на `id` (запити, JOIN, індекси), бо 36-символьний ключ роздув би індекси великих таблиць значень.

**Зв'язки конфігурації.** Зв'язок із типом (`parent_type`, `content_fields.content_type`, `content_nodes.content_type`) зберігає `key` типу як FK, тож окремих колонок `*_uuid`/`*_key` поруч не потрібно: у файлі експорту зв'язок уже виражений ключем. `content_type` поля й вузла після створення не змінюється; `parent_type` змінювати дозволено. Значення посилаються на поле парою (`content_type`, `field_key`) — теж без `id` — і на вузол через `content_node_id` разом із `content_node_uuid`: `uuid` вузла копіюється в кожен рядок значення, щоб експорт значень не потребував JOIN, і лишається незмінним (бо незмінний `uuid` вузла).

**Імпорт.** Порядок: спочатку типи (спершу батьки за `parent_type`), потім поля й вузли, потім значення. Тип шукається за `key`, поле — за парою (`content_type`, `key`), вузол — за `uuid`: знайдений оновлюється, інакше вставляється, і цільова БД присвоює йому власний `id`. Для зв'язку з типом і для поля в значенні береться `key` із файлу як є, без мапи `id`. Мапа `uuid → id` потрібна лише для вузлів: значення в файлі посилається на вузол через `content_node_uuid`, імпортер знаходить локальний `content_node_id` і записує обидва. `id` із вихідного середовища не переноситься.

**Індекс і тип колонки.** На `uuid` у `content_nodes` один унікальний індекс, складених немає. Він обслуговує `findByUuid` і зіставлення вузлів при імпорті, а також є остаточним арбітром унікальності на рівні БД (як індекс `slug`); перевірка в моделі лише дає зрозумілу помилку. Тип колонки — `CHAR(36)` (`$table->uuid()`): читабельний, однаково працює на SQLite у тестах і на MySQL. UUID v7 впорядкований за часом, тож вставки йдуть переважно в кінець індексу.

**Альтернативи:** пара (`*_id`, `*_uuid`/`*_key`) у зв'язках конфігурації — відкинуто (дублює дані); складений FK, що лише захищає пару `id`+`uuid`, — відкинуто (переносу не допомагає), але складений FK на (`content_nodes.id`, `content_type`) для значень прийнято — він захищає інший інваріант: тип значення збігається з типом вузла; `uuid` у `content_types` — відкинуто (`key` типу вже унікальний і незмінний); `uuid` як первинний ключ — відкинуто (розмір індексів таблиць значень); `BINARY(16)` — відкинуто (компактніший, але ускладнює запити, відлагодження й тести, а `uuid` не входить до таблиць значень); `uuid` у `content_fields` — відкинуто (ідентичність поля задає пара (`content_type`, `key`), `key` незмінний); експорт вузлів за `slug` — відкинуто (`slug` змінюваний). Самі імпорт/експорт і зв'язки між вузлами — окремі майбутні зміни; тут лише закладається ідентичність.

### 3. Мови контенту та вмикач багатомовності

`AppLanguage` (таблиця `app_languages`, загальна системна) — звичайні записи; нова мова неактивна (`is_active = false`) до явної активації; `lang` у таблицях значень лишається рядком без FK (бо `default` немає в `app_languages`). Сервіс `ContentLanguages` (singleton, залежить від `AppSettings`) дає `isMultilingual()`, `active()` (впорядкований перелік активних кодів, порожній при вимкненій багатомовності), `assertReadable($lang)` та `assertWritable($lang)`; значення вмикача читається з `app_settings` через `AppSettings` (ключ `content.multilingual`) із кешем у межах запиту, скидається при зміні.

Правила: `default` завжди допустима. Інша мова для запису: багатомовність увімкнена + мова існує + `is_active`. Для читання/вибірки: багатомовність увімкнена + мова існує (активна чи ні). Порушення → `ValidationException`. Перемикання вмикача і деактивація не змінюють збережені значення.

Видалення `AppLanguage` перевіряє відсутність значень цієї мови у 7 таблицях (`exists` по кожній) і відхиляє видалення, якщо вони є. Код мови при створенні нормалізується до канонічного регістру BCP-47 (перший підтег малими, 4-літерний підтег письма з великої — `Hant`, 2-літерний регіон великими — `BR`, решта малими; `PT-br` → `pt-BR`) і лише потім перевіряється: формат `^[a-z]{2,3}(-[A-Za-z0-9]{2,8})*$`, довжина ≤16 (розмір колонки), не `default`, унікальність. Тим самим методом `ContentLanguages` нормалізує кожен вхідний `lang` перед перевіркою, записом, читанням і вибіркою, тож `pt-br` і `pt-BR` — одна мова, а в БД зберігається лише нормалізований вигляд. Колонки `app_languages.code` і `lang` мають бінарну колацію (`utf8mb4_bin`), щоб порівняння в MySQL збігалося з SQLite у тестах.

**Альтернатива:** регістронезалежна колація без нормалізації — відкинута: різні записи одного коду в БД і розбіжність MySQL/SQLite.

**Чому БД, а не `config/`:** і мови, і вмикач мають змінюватись адміністратором без деплою. **Чому `app_settings`, а не `content_*` таблиця:** вмикач глобальний, а не належить типу контенту, а сховище має бути спільним для майбутніх модулів; key-value зручно розширювати. **Альтернатива** FK `lang → app_languages.code` — відкинута через `default`. **Незалежність від адмінки:** сервіс не взаємодіє з `users.locale`, middleware локалі та `lang/*` адмінки (див. `docs/admin-i18n.md`); це перевіряється тестом.

### 3a. Сховище `app_settings`

Сервіс `AppSettings` (`app/Support/AppSettings.php`, singleton): `get(string $key, mixed $default = null)`, `has($key)`, `set($key, $value)` (upsert), `forget($key)`, `prefix(string $prefix): array`. Ключ валідується регулярним виразом `^[a-z0-9_-]+(\.[a-z0-9_-]+)+$` (≥2 сегментів) і довжиною ≤191 (розмір PK). Значення кодується через JSON, тому `null` відрізняється від відсутнього ключа (`has`). Читання кешується в пам'яті процесу/запиту; `set`/`forget` оновлюють кеш (узгодженість у межах запиту); міжпроцесний кеш (Cache store) не вводиться — рішення про нього відкладено, поки сховище не стане «гарячим». Фасад/хелпер не додається; модулі отримують сервіс через контейнер.

**Альтернатива:** пакет `spatie/laravel-settings` або таблиця на кожен модуль — відкинуті: зайва залежність і міграція на кожен модуль, тоді як вимога — одне просте спільне сховище. **Конвенція:** кожен модуль користується власним префіксом (`content.`, у майбутньому `seo.`, `mail.` тощо).

### 4. Індекси

Окрім унікального (`content_node_id`, `content_type`, `field_key`, `lang`, `weight`) — він обслуговує читання значень вузла й префікс складеного FK на вузол, — додається індекс (`content_type`, `field_key`, `lang`, `value`) (також префікс складеного FK на поле) для фільтрації/сортування за полем, мовою і значенням у таблицях string, integer, decimal, boolean, date, datetime. Для `text` індексу за `value` немає (LONGTEXT), лише (`content_type`, `field_key`, `lang`). `LIKE '%x%'` індекс не використовує — прийнятно на цьому етапі.

### 5. Реєстр типів полів

Інтерфейс `FieldType` (у `app/Content/FieldTypes/`): `key()`, `table()`, `rules(ContentField): array`, `cast(mixed): mixed` (з БД у PHP-тип), `prepare(mixed): mixed` (у значення для БД), `operators(): array`, `searchable(): bool`. Спільна база `AbstractFieldType`. `FieldTypeRegistry` (singleton) будується з `config/content.php` (`'field_types' => [key => Class]`, також `default_lang => 'default'`), відхиляє невідомі ключі. `ContentField` при збереженні перевіряє, що `type` є в реєстрі.

Таблиці значень не мають окремих Eloquent-моделей: мапінг «тип → таблиця» береться з реєстру, запити будуються через Query Builder. **Альтернатива:** модель на кожну таблицю з поліморфним зв'язком — відкинута, бо додає клас на кожен тип і ускладнює пакетні запити.

### 6. Запис, валідація, читання

`ContentValueWriter::write(ContentNode, array $values, string $lang = 'default', bool $creating = false)`: перевіряє `lang` через `ContentLanguages::assertWritable`, завантажує поля типу контенту за ключем, відхиляє невідомі ключі та `lang != default` для неперекладних полів, будує правила через реєстр (`field.key` для немножинного, `field.key.*` + `array` для множинного), валідує, при помилці кидає `ValidationException` за ключами полів. Далі в одній транзакції для кожного вказаного поля: delete рядків (`content_node_id`, `field_key`, `lang`; `content_type` береться з вузла й ззовні не приймається) і insert нового набору з `weight` = індекс; `null`/`[]` лише видаляє. При `$creating = true` і `lang = default` перевіряються всі обов'язкові поля (зокрема `title`); для інших мов обов'язковість не перевіряється.

`ContentValueReader::load(iterable $nodes, ?array $fieldKeys, string $lang = 'default')`: групує поля за таблицею, один запит на таблицю з `whereIn(content_node_id)`, `where(content_type)`, `whereIn(field_key)`, `where(lang)`, `orderBy(weight)`, приводить значення через `cast`, повертає `[node_id => [field_key => value|list|null]]`. Підстановки `default` немає (рішення для простоти й однакової семантики з вибіркою; fallback — окрема майбутня зміна).

Правила типу `decimal` відхиляють значення з більш ніж 6 знаками після коми (колонка `DECIMAL(20,6)`), щоб не округляти мовчки. Decimal у PHP — рядок; date/datetime — `CarbonImmutable`; boolean — `bool`; integer — `int`. Зміна `type` поля при наявних значеннях відхиляється в `ContentField` (перевірка існування значень у таблиці старого типу).

### 7. Вибірка вузлів

`ContentNodeQuery` над `content_nodes`; вхід — `ContentType` та DTO: `fields`, `lang` (за замовчуванням `default`), `search` + `searchFields`, `filters[] {field, operator, value}`, `sort {field, direction}`, `page`, `perPage`. Ключі полів резолвляться в межах типу; невідомі → `ValidationException`; оператор перевіряється через `FieldType::operators()`.

- Фільтр: `whereExists` по таблиці значень із `content_type`, `field_key`, `lang` і умовою (звідси «хоча б одне значення» для множинних, AND між фільтрами, без `DISTINCT`).
- Пошук: група `OR` з `whereExists ... LIKE` по кожному текстовому полю; `%`/`_` екрануються.
- Сортування: `LEFT JOIN` таблиці значень поля з `lang` і `weight = 0` (однозначно, бо сортування за множинним заборонено), `ORDER BY (v.value IS NULL), v.value dir, content_nodes.id`.
- Пагінація `LengthAwarePaginator`; після отримання ID сторінки значення завантажуються `ContentValueReader` лише для видимих полів у вказаній мові.

`settings` типу — JSON-об'єкт; зараз використовується ключ `list`: `{ "list": { "visible": [keys], "search": [keys], "sort": {"field": key, "direction": "asc|desc"} } }` (конфігурація списку, не переклади), валідується проти полів типу при збереженні; параметри запиту перекривають її.

### 8. Структура коду й документація

`app/Models/{ContentType,ContentField,ContentNode}.php`, `app/Content/FieldTypes/*`, `app/Models/AppLanguage.php`, `app/Content/{ContentLanguages,FieldTypeRegistry,ContentValueWriter,ContentValueReader,ContentNodeQuery}.php`, `config/content.php`, міграції, фабрики. Документація: `docs/app-settings.md` (сховище, формат ключів, API для модулів), `docs/content-model.md` (сутності, схема, `title`), `docs/content-languages.md` (мови контенту, вмикач, незалежність від адмінки), `docs/content-values.md` (типи, реєстр, переклади, запис/читання, як додати тип), `docs/content-querying.md` (вибірка, оператори, сортування, `settings.list`); індекс — `docs/README.md`.

## Risks / Trade-offs

- [Багато JOIN/EXISTS при великій кількості фільтрів] → індекс (`content_type`, `field_key`, `lang`, `value`) + пагінація; ліміт кількості фільтрів у запиті (конфіг, за замовчуванням 10).
- [`LIKE '%x%'` не використовує індекс] → прийнятно для початку; повнотекстовий пошук — окрема зміна.
- [Тести на SQLite, прод на MySQL: розбіжності в DECIMAL, порядку NULL, колації] → NULL-порядок задано явно; ключові сценарії вибірки додатково прогнати проти MySQL у Docker.
- [Зміна типу поля з даними неможлива] → свідоме обмеження.
- [Гонка при генерації slug] → унікальний індекс + повтор спроби.
- [Транслітерація `Str::slug` залежить від мови `uk`] → покрито тестом на кириличних назвах.
- [Зміна slug ламає публічні посилання] → slug не змінюється автоматично; редиректи — майбутня зміна.
- [Вид визначає лише класифікацію, а не поведінку] → логіка сторінок/блоків додається окремими змінами; до того `page`/`block` поводяться як `content`.
- [Нове поле для наявних вузлів не має значень] → вважається `null`; обов'язковість перевіряється лише при створенні вузла.
- [Рядки значень стали ширшими: `content_type`, `field_key`, `content_node_uuid` на кожен рядок, ширші індекси] → свідомий обмін на незалежність від `id` і простий експорт; `content_node_uuid` узгоджується з вузлом на рівні моделі (`uuid` вузла незмінний), типи й поле — складеними FK.
- [Каскадне видалення знищує значення] → за специфікацією; захист — на рівні UI в наступних змінах.
- [Немає fallback на `default` для відсутнього перекладу] → клієнт може запитати обидві мови; fallback додається окремою зміною.
- [`lang` у значеннях без FK на `app_languages`] → цілісність забезпечує сервіс і заборона видалення мови зі значеннями; пряме втручання в БД поза обсягом.
- [Кеш `AppSettings` лише в межах запиту, без міжпроцесного] → читання з БД при кожному запиті; прийнятно для малої кількості ключів.
- [Вимкнення багатомовності робить переклади недоступними, але не видаляє їх] → навмисно; повторне вмикання відновлює доступ.
- [`VARCHAR(512)` для короткого тексту] → валідація `max` ≤ 512.
- [Індекс (`content_type`, `field_key`, `lang`, `value`) на `string` ≈ 2624 байти з 3072 дозволених InnoDB (utf8mb4)] → не збільшувати довжини `field_key`, `lang` і `value` без повторної перевірки ліміту.
- [Видалення типу обходить заборону видалення `title` через FK-каскад] → навмисно, покрито тестом.
