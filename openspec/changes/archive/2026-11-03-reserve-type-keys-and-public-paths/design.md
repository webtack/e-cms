# Design

## Context

Мотивація та обсяг: див. `proposal.md`. Поточний стан, від якого відштовхується підхід:

- Усі правила цілісності типів і записів живуть у моделях (`ContentType::assertValid()`, `ContentNode::assertValidSlug()`, подія `saving`), а form requests дублюють їх навмисно, щоб помилки показувались біля полів (`StoreContentTypeRequest::sharedRules()`, `StoreContentNodeRequest::slugRules()`).
- Заборона зарезервованих ключів існує лише для полів (`ContentField::RESERVED_KEYS`, `Rule::notIn` у `StoreContentFieldRequest`); переклад «This key is reserved.» уже є в `lang/*.json`.
- Slug типу унікальний серед типів, slug запису унікальний серед записів; між собою вони не перевіряються. Тип `content` має `slug` (`kind = content`), тип `page` його не має.
- `SlugGenerator::fromTitle()` перевіряє зайнятість лише в `content_nodes`; `ContentNodeCreator` ловить `UniqueConstraintViolationException` як останню межу унікальності.
- Публічної маршрутизації ще немає; перший сегмент службових маршрутів: `admin`, `login`, `logout`, `locale`, `email`, `up`; у `public/` лежать каталоги `build` і `storage`.
- Робоча БД чиста: типи `ddd`, `dsfsdf`, `news` (slug типу `news`), сторінка `rtrtyrty`.

## Goals / Non-Goals

**Goals:**
- Одне джерело правди для зарезервованих ключів типів і для зарезервованих шляхів.
- Однакова поведінка в моделі (код, імпорт) і формах (помилка біля поля `slug` чи `key`).
- Автогенерація slug сторінки не створює колізій.
- Захист від дрейфу: новий службовий маршрут чи каталог у `public/` без запису в переліку ламає тест.

**Non-Goals:**
- Мовні префікси (`/en/…`): окрема зміна; коли вона з'явиться, коди мов додадуться до зарезервованих шляхів.
- Правило пріоритету під час публічної маршрутизації (службовий шлях, тип, сторінка): вирішить зміна з публічними маршрутами. Тут лише гарантуємо, що колізій у даних не виникає.
- Виправлення наявних даних із колізіями (міграція чи команда-аудит): у робочій БД їх немає, тож лишаємо без автоматичного виправлення.
- Перевірка slug записів `content` і `block`: вони не стоять на першому сегменті.
- Обмеження на рівні БД між двома таблицями.

## Decisions

### 1. Зарезервовані ключі типів: константа в `ContentType`

`ContentType::RESERVED_KEYS = ['content', 'pages', 'blocks', 'fields', 'menus', 'errors']` поряд із `KEY_PATTERN`. Перевірка в `assertValid()` лише для нового типу (`! $this->exists`), бо `key` незмінний, тож наявні типи ні ламаються, ні перевіряються повторно. У `StoreContentTypeRequest::rules()` додається `Rule::notIn(ContentType::RESERVED_KEYS)` до ключа (для всіх трьох розділів); повідомлення «This key is reserved.» (переклад уже є).

*Чому константа, а не config:* перелік пов'язаний із назвами папок теми, тобто з кодом, а не з налаштуванням середовища; новий службовий каталог теми означає новий рядок у коді та тесті, а не зміну `.env`. Так само вирішено для `ContentField::RESERVED_KEYS`.
*Альтернатива:* підпапка `types/` для папок типів у темі. Відхилено власником: вибрано заборону ключів.

### 2. Зарезервовані шляхи: `config('content.reserved_paths')` плюс тест-страж

Перелік `['admin', 'login', 'logout', 'locale', 'email', 'up', 'storage', 'build']` у `config/content.php`. Це конфіг, бо залежить від розгортання (каталоги `public/`, окремі службові маршрути); проєкт може додати свої.

Тест-страж виводить множину «перший сегмент кожного маршруту без параметра першим сегментом (крім `/`)» плюс «каталоги в `public/`» і перевіряє, що вона міститься в конфігу. Новий маршрут або каталог без запису ламає тест.

*Альтернатива:* виводити перелік динамічно з `Route::getRoutes()`. Відхилено: валідація залежала б від порядку реєстрації маршрутів і від майбутнього публічного catch-all, а статичний перелік із тестом простіший і передбачуваний.

### 3. Сервіс `PublicPaths` у `app/Content/`

Єдина реалізація правила, яку викликають модель, form requests і генератор:

- `reserved(): array` читає конфіг у нижньому регістрі;
- `pageSlugConflict(string $slug): ?string` повертає причину (`reserved` або `type`) чи `null`: slug збігається зі зарезервованим шляхом або зі slug типу `content`;
- `typeSlugConflict(string $slug, ?int $ignoreTypeId = null): ?string`: зі зарезервованим шляхом або зі slug запису виду `page` (запит через `content_nodes` → `content_types.kind = 'page'`);
- `isTakenForPage(string $slug): bool` для генератора.

Порівняння виконується на значеннях у нижньому регістрі; формат slug (малі літери) і так перевіряється раніше, тож регістр лише додатковий запобіжник.

### 4. Рівні перевірки

- **Модель.** `ContentNode::assertValidSlug()` після перевірки формату й префікса блока: для виду `page` викликає `pageSlugConflict`. `ContentType::assertValid()`: для `kind = content` і непорожнього slug викликає `typeSlugConflict`. Обидва виклики виконуються лише коли `! $this->exists || $this->isDirty('slug')`. Для запису це вже так, для типу умову треба додати, бо зараз `assertValid()` викликається на кожному збереженні. Це забезпечує «наявний збіг не блокує інші правки». Помилка: `ValidationException` за ключем `slug`.
- **Форми.** Валідаційне правило-обгортка (`AvailablePublicPath`, `ValidationRule`) викликає сервіс. Підключається в `StoreContentNodeRequest` / `UpdateContentNodeRequest` лише для маршруту виду `page` (для update ще й лише коли slug відрізняється від збереженого) і в `StoreContentTypeRequest::sharedRules()` для виду `content` (для update лише коли slug змінено). Повідомлення: «This slug is reserved.», «This slug is already used by a content type.», «This slug is already used by a page.» (додаються до `lang/en.json` і `lang/uk.json`).

*Чому обидва рівні:* так працює решта проєкту (форма дає помилку біля поля, модель лишається останньою межею для tinker та імпорту).

### 5. Автогенерація slug сторінки

`SlugGenerator::forType()` для виду `page` передає в `fromTitle()` прапорець, і множина «зайнятих» (зараз лише slug записів із префіксом основи) доповнюється slug типів `content` і зарезервованими шляхами, що збігаються з основою чи її числовими суфіксами. Так `admin` дає `admin-2`, `news` при типі зі slug `news` дає `news-2`. Для `content` поведінка не змінюється. Явний slug ніколи не змінюється: колізія дає `ValidationException` з ключем `slug`.

`ContentNodeCreator` не змінюється: модель кидає `ValidationException` ще до INSERT, а гонка (два записи одночасно) і далі ловиться існуючою гілкою `UniqueConstraintViolationException` для унікальності між записами.

## Risks / Trade-offs

- [Гонка між таблицями: тип і сторінка зі slug `x` зберігаються одночасно] → між таблицями немає обмеження БД; запис в адмінці рідкісний, а публічна маршрутизація пізніше однаково детермінована. Приймаємо без блокувань.
- [Наявні дані зі збігом] → не виправляємо автоматично; перевірка лише при створенні й зміні slug, тож такі записи редагуються без помилки. У робочій БД збігів немає. Виявляти їх буде `theme:check` або окремий аудит у зміні про публічні маршрути.
- [Тести й фікстури, які використовують зарезервовані ключі, зокрема `pages`] → оновлюємо одним проходом на нейтральні ключі (`landing`, `static`, `articles`), без зміни суті тестів. Перелік знаходимо `grep` у `tests/` і `e2e/`, `database/`.
- [Перелік шляхів застаріє] → тест-страж (рішення 2).
- [Мовні префікси додадуть ще зарезервовані сегменти] → свідомо поза обсягом; зміна про мови додасть коди з активних мов у `reserved()`.
- [Slug сторінки, що збігається з назвою файла в `public/` без крапки] → страж перевіряє каталоги `public/`; файли з розширенням не збігаються з форматом slug.

## Migration Plan

Міграцій БД немає. Розгортання: звичайний деплой коду. Відкат: повернути код; збережені дані не змінюються. Перед деплоєм у середовищах з реальними даними перевірити вручну (запит у `tinker`) відсутність збігів slug типів і сторінок та зарезервованих ключів типів.
