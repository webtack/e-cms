# Design

## Context

Правило живе в `ContentField::assertValid` (подія `saving`): якщо `type` змінено, а в таблиці значень початкового типу є рядки цього поля (`hasStoredValues`), кидається `ValidationException` з ключем `type`. Інші незмінні атрибути (`key`, `content_type`) перевіряються в тому ж методі через `isDirty`. Форма редагування (`ContentFieldForm.tsx`) блокує селект типу через `lockType = field.is_system || field.has_values`. `UpdateContentFieldRequest` повторно використовує `StoreContentFieldRequest::sharedRules()`, тож `type` приходить у запиті завжди. Прапорець `has_values` лишається потрібним для діалогу видалення. Мотивація й межі — у `proposal.md`, вимоги — у `specs/`.

## Goals / Non-Goals

**Goals:**
- Один безумовний шар правила в моделі, що діє для будь-якого шляху запису (форма, tinker, імпорт).
- Форма не пропонує дію, яку сервер однаково відхилить.

**Non-Goals:**
- Підказка про незмінність типу у формі створення.
- Зміна діалогу видалення в адмінці та `has_values` (вони вже відповідають вимозі).
- Перенесення значень між типами (конвертація).

## Decisions

**1. Правило типу в моделі, без запиту до БД.** Умова `isDirty('type')` на наявному полі кидає `ValidationException(['type' => ...])` без звернення до таблиці значень. `hasStoredValues` для типу більше не потрібен, але лишається для перевірки видалення (див. рішення 6). Це простіше й швидше, а результат не залежить від стану даних. Альтернатива — залишити умову за наявністю значень: це поточна поведінка, від якої власник відмовився.

**2. Зміна типу відхиляється помилкою, а не ігнорується.** Для `key` і `content_type` запит не містить значень (їх немає в `validated()`), а `type` у формі є завжди, тому «ігнорувати» означало б мовчки відкидати введене. Сервер повертає помилку біля поля `type` (так само, як для поля зі значеннями зараз); форма, що надсилає поточний тип, проходить. Альтернатива — прибрати `type` із правил оновлення й ігнорувати його: менше коду, але явна зміна типу прямим запитом пройшла б непоміченою.

**3. Одне повідомлення.** Текст помилки: `The type of a field cannot be changed.` (en) / «Тип поля змінити не можна.» (uk). Це замінює два наявні рядки перекладу (`…of a field that has values…` і `…of a system field…`) одним, бо причина тепер одна. Старі ключі видаляються з `lang/*.json`.

**4. Форма: `lockType = !!field`.** У режимі `edit` селект типу завжди `disabled` з підказкою. Прапорці «множинне» й «обов'язкове» для системного поля блокуються як і раніше. `SYSTEM_LOCKED` у моделі лишається без змін (`type` у ньому стає дубльованою страховкою для системного поля, шкоди немає).

**5. Дані не мігруються.** Правила не торкаються збережених значень, тож міграція не потрібна. Поле, створене з хибним типом, потрібно видалити й створити заново, а для поля зі значеннями спершу очистити значення.

**6. Видалення поля зі значеннями забороняє модель.** У `booted()` до події `deleting` (де вже є перевірка системного поля) додається перевірка: якщо в таблиці значень типу поля є рядки з `content_type` і `field_key` цього поля, кидається `ValidationException(['key' => 'A field that has values cannot be deleted.'])`. Таблиця береться з `FieldTypeRegistry` за `type` поля. Контролер `ContentFieldController::destroy` лишає власну перевірку (`valuedKeys`, `back()->with('error', ...)`), щоб користувач отримав звичайне повідомлення, а не помилку валідації; модель — остання межа для коду, tinker та імпорту. Каскад БД при видаленні **типу** не проходить через подію моделі й не змінюється: тип разом з усім вмістом видаляється за окремою вимогою («Каскадне видалення конфігурації»). Альтернатива — лишити перевірку лише в контролері: тоді `ContentField::delete()` у коді мовчки знищує значення, що суперечить духу незмінності, яку вводить ця зміна.

**7. Тести каскадів.** `CascadeTest` тепер перевіряє: поле без значень видаляється; поле зі значеннями відхиляється, значення цілі; тип з полями, що мають значення, видаляється каскадом.

## Risks / Trade-offs

- [Помилився з типом, значення вже є] → спочатку видалити значення (поле зі значеннями не видаляється ні в адмінці, ні в моделі), потім видалити й створити поле заново; конвертація типів — окрема зміна, за потреби.
- [Код, що покладався на каскадне видалення значень при `ContentField::delete()`] → у проєкті лише `CascadeTest`; решта шляхів (адмінка) вже забороняла видалення. Масове видалення значень перед видаленням поля робить сам виклик.
- [Масове видалення `ContentField::query()->delete()` обходить події моделі] → як і для решти перевірок моделі; захищає лише видалення через екземпляр моделі (задокументовано).
- [Тести й e2e, що покладаються на зміну типу порожнього поля] → оновлюються в цій зміні: `ContentFieldTest`, `ContentFieldEditTest`, `FileFieldTypesTest` (сценарій «без значень») та e2e `admin-content-fields` (перевірка заблокованого селекта на полі без значень).
- [Спільний компонент форми] → зачіпає `ContentFieldForm`, тож за `docs/e2e-testing.md` запускаються `admin-content-fields` та залежні спеки типів і сторінок (`admin-content-types`, `admin-page-types`, `admin-block-types`, `admin-content-nodes`).
- [Тип даних, створений до зміни, у «проміжному» стані] → поведінка для існуючих полів однакова: тип змінити не можна.

## Migration Plan

Міграцій і залежностей немає. Відкат — повернення попереднього коду. Опублікованих даних, які зміна робить недійсними, немає.
