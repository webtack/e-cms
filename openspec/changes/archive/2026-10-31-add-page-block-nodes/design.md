# Design

## Context

Див. proposal.md. Нинішній стан, з якого виходить підхід:

- Розділи типів уже узагальнені за видом: `routes/web.php` реєструє набір маршрутів типів циклом по `['content-types' => 'content', 'page-types' => 'page', 'block-types' => 'block']` з `defaults('kind', …)`, `Route::bind('contentType')` відбирає тип за видом, а трейт `ResolvesTypeSection` дає `kind()`, `routeName()` і Inertia-проп `section` (`{ kind, basePath }`) ([admin-page-types.md](../../../docs/admin-page-types.md#вид-задає-маршрут)).
- Записи зареєстровано окремим циклом лише під `/content-types/{contentType}/nodes` з `defaults('kind', 'content')` (`routes/web.php`). `ContentNodeController` уже використовує `ResolvesTypeSection` (`section($request)` у пропсах, `routeName($request, 'nodes.index')` у `store`), а React-сторінки `Pages/Admin/ContentNodes/*`, `ContentNodeForm` і `ContentNodeRowActions` будують адреси від `section.basePath`. Тобто бекенд і фронтенд записів майже готові до інших видів.
- Жорстко прив'язані до `content` лише: цикл маршрутів записів; `ContentTypeNav` і `ContentTypeRowActions` (пункт «Записи» лише при `section.kind === 'content'`); `linkedNodesColumn` у `Pages/Admin/ContentTypes/Index.tsx`; шаблони крихт записів у `navigation.ts`; `ContentNodeOwner` (посилання лише при `kind === 'content'`, ім'я маршруту `admin.content-types.nodes.edit`).
- Правила slug за видом уже в моделі: `ContentNode::assertValidSlug()` вимагає префікс `block-` для блоків, `SlugGenerator::forType()` генерує `block-xxxxxxxx` для блоків і slug із заголовка для решти ([content-model.md](../../../docs/content-model.md#slug-запису)).
- Опис поведінки записів: [admin-content-nodes.md](../../../docs/admin-content-nodes.md); розділи типів: [admin-page-types.md](../../../docs/admin-page-types.md), [admin-block-types.md](../../../docs/admin-block-types.md); медіатека: [media-library.md](../../../docs/media-library.md).

## Goals / Non-Goals

**Goals:**
- Один контролер, одні сторінки й форми записів для всіх трьох видів; вид визначає лише маршрут.
- Жодного дублювання маршрутів, контролерів чи React-компонентів.
- Однакова поведінка записів у розділах (адресація за `uuid`, 404 для чужого виду, перенаправлення в розділ того самого виду).

**Non-Goals:**
- Дерево сторінок, публічні адреси й рендер, розміщення блоків на сторінці, зміна `kind`-специфічних полів форми.
- Нові поля або службові атрибути запису; будь-які міграції.
- Макетний пункт «Pages» (`/admin/pages`) у sidebar лишається макетом.

## Decisions

**1. Цикл маршрутів записів по тих самих трьох розділах.** Маршрути записів реєструються всередині циклу по розділах: `"/$section/{contentType}/nodes…"` з іменем `"$section.nodes.$name"` і `defaults('kind', $kind)`. Імена `admin.content-types.nodes.*` не змінюються, з'являються `admin.page-types.nodes.*` і `admin.block-types.nodes.*`. Правила прив'язки (`Route::bind('contentType')` за видом, `Route::bind('node')` за парою (тип, `uuid`)) уже коректно працюють для будь-якого виду, тому чужий вид дає 404 без нового коду. *Альтернатива* — окремі контролери записів для сторінок і блоків: відхилено, бо поведінка однакова, а розходження з'явиться лише коли виникнуть специфічні для виду функції (окремі зміни).

**2. Пункт «Записи» показується для всіх видів.** У `ContentTypeNav`, `ContentTypeRowActions` і `Index.tsx` умова `section.kind === 'content'` для записів прибирається; `linkedNodesColumn` застосовується для всіх видів. Лічильник `nodes_count` уже віддає `ContentTypeController` для кожного виду, тож змін на сервері не потрібно. *Альтернатива* — прапорець «підтримує записи» на розділі: відхилено як зайву абстракцію, поки всі три розділи підтримують записи.

**3. Крихти — узагальнений шаблон.** Три шаблони записів у `navigation.ts` об'єднуються в `(content|page|block)-types`, як уже зроблено для полів; пункт sidebar для проміжної крихти знаходить наявна логіка `isActive`.

**4. `ContentNodeOwner` будує URL за видом.** Ім'я маршруту складається з розділу виду (`content` → `content-types`, `page` → `page-types`, `block` → `block-types`); відповідність береться з одного місця (спільна константа/метод поруч із `ResolvesTypeSection::SEGMENTS`), щоб не дублювати мапу. Для невідомого виду посилання лишається `null`. *Альтернатива* — копія мапи у власнику: відхилено через ризик розсинхронізації з маршрутами.

**5. Префікс slug блоку — у формі, правда — на сервері.** Сервер лишається арбітром: блок без явного slug отримує `block-…` від `ContentNodeCreator`, явний slug без префікса відхиляє модель помилкою `slug`, яку `ContentNodeController::forForm()` віддає біля поля slug (перевіряється Feature-тестом; якщо помилка не потрапляє до поля — виправляється в межах цієї зміни). Поверх цього форма для виду `block` показує `block-` як незмінну частину поля (addon перед `Input`, наприклад на основі наявного `ButtonGroup`) і працює лише з рештою slug. Префікс форма не пише в жорсткий рядок: контролер передає його пропсом `slugPrefix` (`ContentNode::BLOCK_PREFIX` для виду `block`, порожній рядок для інших), тож знання про префікс живе в одному місці. Нормалізація в `ContentNodeForm`: стан `data.slug` зберігає лише решту; `onChange` обрізає на початку явно введений/вставлений префікс (щоб не подвоїти), а `transform` перед запитом додає префікс до непорожньої решти. Порожня решта надсилається порожньою. Підказка під полем у режимі створення пояснює, що порожнє поле дає згенерований slug із префіксом. Ліміт довжини (190) рахується від повного slug, тому помилку довжини віддає сервер. *Альтернативи:* (а) тримати в стані повний slug із передзаповненим `block-` — відхилено, бо порожнє поле перестає означати «згенерувати» і префікс можна стерти; (б) лише підказка під полем — відхилено, бо користувач не бачить кінцевий результат.

**6. Тестове покриття.** Поточні Feature-тести очікують 404 для `page-types`/`block-types` записів (`ContentNodeIndexTest`, `ContentNodeWriteTest`); вони переписуються на нову поведінку (200 для свого виду, 404 для чужого). E2E: нові сценарії в `admin-page-types.spec.js` і `admin-block-types.spec.js` (меню, перехід до списку, створення запису, крихти); повного прогону `admin-content-nodes` не потрібно, бо форма записів не змінюється, окрім як у тесті, що перевіряє відсутність посилань у розділі сторінок (його оновлено).

## Risks / Trade-offs

- [Тести, що закріплюють «записів немає для page/block» (Feature, e2e, docs), залишаться застарілими] → завдання явно переписують `ContentNodeIndexTest`, `ContentNodeWriteTest`, e2e `admin-content-types` і `admin-content-nodes` (перевірка відсутності посилань на записи в розділі сторінок), та `grep` по `docs/` на формулювання «записів немає».
- [Видалення типу з записами] → без змін: `nodes_count > 0` уже блокує видалення типу й для `page`/`block`; тепер користувач може дійти до записів із діалогу.
- [Робоче дерево містить незакомічену зміну `redesign-node-form`] → код форми записів у цій зміні не переписується, лише використовується; конфліктів файлів немає, окрім `ContentNodeController` (коментар класу).
- [Розбіжність між префіксом у формі та на сервері] → префікс приходить із сервера пропсом `slugPrefix`, а не дублюється в JS; Feature-тест перевіряє пропс, e2e — кінцевий slug.
- [Користувач вставляє slug з префіксом] → `onChange` обрізає його у полі, `transform` додає назад, тож результат не подвоюється; покривається e2e.
