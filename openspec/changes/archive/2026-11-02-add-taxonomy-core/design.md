# Design

## Context

Модель контенту — EAV: структура (типи, поля) є даними, значення лежать у типізованих таблицях `content_values_{тип}` зі спільним контрактом (власник `entity` = запис або тип, `lang`, `weight`, `value`, `options`). Тип поля — клас у реєстрі `config/content.php` (`field_types`); ядро запису, читання й вибірки від нових типів не змінюється. Поля-посилання на інші сутності немає. Обґрунтування — у [proposal.md](proposal.md); вимоги — у [specs/](specs/).

Узгоджене в обговоренні: таксономія — окремий домен, а не `kind` типу контенту й не нова `entity` у таблицях значень; словники глобальні й підключаються через поле; дерево з одним батьком; нащадків шукаємо обходом у PHP; видалення використовуваного терміна заборонене.

Описують компоненти: `docs/content-values.md` (реєстр типів, схема значень), `docs/content-querying.md` (оператори), `docs/content-model.md`, новий `docs/taxonomy.md`.

## Goals / Non-Goals

**Goals:**
- Мінімальний новий код у ядрі контенту: один тип поля й дві невеликі точки розширення (перевірка `settings` поля; розгортання значень фільтра).
- Усі інваріанти таксономії діють незалежно від способу запису (код, імпорт, майбутня адмінка): у моделях і на рівні БД, а не в контролерах.

**Non-Goals:**
- Адмін-інтерфейс, вибір терміна у формі запису, публічні маршрути категорій (`add-taxonomy-admin` та далі).
- Імпорт-експорт термінів між середовищами (сам механізм; `uuid` для нього закладено).
- Власні (користувацькі) поля на термінах: набір атрибутів терміна фіксований.
- Матеріалізований шлях або closure table для дерева.

## Decisions

### 1. Окремі таблиці, а не вузли контенту

```
taxonomy_vocabularies(id, key UNIQUE, name, description, settings JSON, timestamps)
taxonomy_terms(id, uuid UNIQUE,
               vocabulary_key FK → taxonomy_vocabularies.key RESTRICT,
               parent_uuid FK self → taxonomy_terms.uuid RESTRICT null,
               slug, weight, image null, timestamps;
               UNIQUE(vocabulary_key, slug), INDEX(parent_uuid, weight))
taxonomy_term_translations(id, term_uuid FK → taxonomy_terms.uuid CASCADE, lang, name, description null;
                           UNIQUE(term_uuid, lang))
```

**Ідентичність.** Термін ідентифікується `uuid` (UUID v7, `CHAR(36)`, як у `content_nodes.uuid`): він задається явно (імпорт) або генерується, і він незмінний. Словник `uuid` не має: його ідентифікатор — незмінний унікальний `key` (`VARCHAR(64)`, формат `^[a-z][a-z0-9_]*$`), як у `content_types`, де інші таблиці посилаються на `key`, а не на `id`. Зв'язки: термін → словник по `vocabulary_key`, термін → батько по `parent_uuid`, переклад → термін по `term_uuid`; поле `term` посилається на словник по `key` (`settings.vocabulary`), значення поля — на термін по `uuid`. `id` лишається первинним ключем (потрібен `media_relations.owner_id`, який `unsigned bigint`) і назовні не виходить. Прецеденти: FK по `key` — `content_types.parent_type`, FK по `uuid` — `media_relations.file_uuid`. Індекси вкладаються в ліміт InnoDB: `slug` (190 символів, ≈ 760 байтів) + `vocabulary_key` (64 символи, ≈ 256 байтів) ≪ 3072.

Термін — легка сутність без `published_at`, автора й SEO. Набір його атрибутів фіксований: `slug`, `weight`, `image`, переклади (`name`, `description`). Його `slug` має власний простір у межах словника (у вузлів `slug` глобально унікальний; URL публічних сторінок категорій міститиме словник, тож пара (словник, slug) однозначно знаходить термін), `slug` унікальний без урахування регістру (nocase на SQLite, колація MySQL за замовчуванням — як у `content_nodes.slug`) і не перекладається. `lang` має бінарну колацію, як у таблицях значень. Slug плоский у межах словника, а не батька: однойменні терміни під різними батьками отримують суфікс `-2`.
**Зображення** — одне на термін, колонка `image` (значення `{uuid}.{розширення}`, профіль `image`, правило `FileValue`), а не в перекладах. Облік використання — через `FileRelations::sync('taxonomy_term', $term->id, 'image', 'default', …)` в одній транзакції із записом терміна (`TermWriter`); власник реєструється в `config/files.php` класом `App\Files\Owners\TermOwner` (підпис — назва терміна мовою `default`, посилання з'являється в `add-taxonomy-admin`, до того — без посилання). Хук `deleting` терміна викликає `FileRelations::forgetOwner('taxonomy_term', $id)`.
**Альтернативи:** термін як `ContentNode` із новим `kind` — дає поля/переклади безкоштовно, але тягне службові атрибути, спільний (глобальний) простір slug, `parent_id`/`weight` у всіх вузлах і новий вид типу в адмінці; нове значення `entity = 'term'` у всіх таблицях значень — міграція всієї EAV-схеми. Обидві відхилено: власні поля на термінах не потрібні (рішення власника), фіксовані колонки й переклади дешевші та дають дерево одним запитом.

### 2. Інваріанти — у моделях (`saving`/`deleting`), атомарні записи — у сервісі

За прикладом `ContentType`/`ContentField`: моделі `Vocabulary`, `Term`, `TermTranslation` у `app/Models`, валідація в подіях `saving` і `deleting` з `ValidationException`. Перевіряється: формат і незмінність `key`; батько з того самого словника; відсутність циклів (підйом по предках у PHP); глибина (глибина батька + 1 + висота піддерева ≤ `max_depth`); незмінність словника терміна; `max_depth` ціле ≥ 1 і не нижче поточної висоти дерева; видалення терміна (діти, використання), видалення словника (терміни, посилання полів). Сервіс `App\Taxonomy\TermWriter` створює/оновлює термін разом з перекладами в одній транзакції (мови через `ContentLanguages::assertWritable`, назва `default` обов'язкова) і генерує `slug` з назви `default` (транслітерація як у `SlugGenerator`, суфікс `-2`, `-3` у межах словника), якщо `slug` не задано. `SlugGenerator::fromTitle` дивиться лише в `content_nodes`, тому напряму не підходить; генерацію для термінів пишемо поруч у `App\Taxonomy`, не змінюючи `SlugGenerator`.
Каскади БД не запускають події моделей, тому: FK `parent_uuid` і `vocabulary_key` — `RESTRICT` (БД не дає видалити батька чи словник з термінами), переклади каскадяться разом з терміном.

### 3. Тип поля `term`: значення в `content_values_string`

`App\Content\FieldTypes\TermType` (`AbstractFieldType`): `key() = 'term'`, `table() = 'content_values_string'` (як у `image`/`file`/`youtube`), `cast`/`prepare` → `string` (канонічний нижній регістр `uuid`), `operators() = ['eq', 'in']`. Нової таблиці значень і міграції немає: поле належить типу контенту, значення — записам (`entity = node`); значень типу в звичайних полів не буває (`SystemFields::owns`), тож спільний контракт власника тут нічого не додає. Читання повертає `string` — `uuid` терміна. Назви термінів мовою й дерево для відображення — через сервіс дерева (рішення 5), а не через `ContentValueReader`.
Правила валідації значення (`rules($field)`): рядок формату UUID + перевірка, що термін існує й належить словнику `settings.vocabulary` поля (`taxonomy_terms.uuid` з `vocabulary_key = settings.vocabulary`). Фільтри перевіряють значення порожнім `ContentField` (див. `ContentNodeQuery::filterValue`), тож для порожнього поля правило зводиться до формату UUID + `exists:taxonomy_terms,uuid` (як `AbstractFileFieldType` розрізняє поле й фільтр).
**Цілісність без FK.** У `content_values_string` немає зовнішнього ключа на `taxonomy_terms` (таблиця спільна з рядковими типами). Тому: (а) `TermUsage` рахує використання запитом до `content_values_string` з приєднанням `content_fields` (`type = 'term'`, `settings->vocabulary` словника терміна) за (`content_type`, `field_key`); (б) видалення терміна виконується в транзакції з `lockForUpdate` на рядок терміна, а `TermType` реалізує нову необов'язкову можливість `App\Content\FieldTypes\LocksReferences` (`lockReferences(array $prepared): void`), яку `ContentValueWriter::replace` викликає всередині транзакції запису (поруч із `TracksFiles`): `lockForShare` на посилані терміни. Так видалення й запис значення серіалізуються (на SQLite блокування — no-op). Прецедент — видалення файлу під блокуванням у медіатеці.
**Альтернативи:** окрема `content_values_term` з FK на `taxonomy_terms` — жорсткий бар'єр у БД, але міграція в остаточній формі контракту (CHECK, функціональний індекс, гілки MySQL/SQLite) заради одного FK; slug терміна як значення — ламається при зміні slug. Обидві відхилено.

### 4. Перевірка `settings` типу поля

Нова необов'язкова інтерфейсна можливість `App\Content\FieldTypes\ValidatesSettings` (поряд із `TracksFiles`, `ComposedValue`): `settingsErrors(array $settings, ?array $original, bool $hasValues): array<string, string>`. `ContentField::assertValid` викликає її для типу, що її реалізує, і перетворює помилки на `ValidationException` за ключем `settings.<ключ>`. `TermType` вимагає наявний `vocabulary` і забороняє його зміну, якщо в поля є значення (`ContentField::hasStoredValues`). Решта типів не змінюється.

### 5. Сервіс дерева і нащадки (BFS у PHP)

`App\Taxonomy\TermTree`: `descendantUuids(array $uuids): list<string>` — обхід у ширину, по одному запиту `WHERE parent_uuid IN (...)` на рівень, з множиною відвіданих (захист від дублів і, на випадок пошкоджених даних, від зациклення); `height(Term)` для перевірки глибини; `tree(Vocabulary, lang)` — дерево термінів для відображення (братні за `weight`, `id`; назва мовою без fallback — `null`, якщо перекладу немає). Рівнів мало (глибина обмежена `max_depth`), тож обхід дешевший за додаткову колонку `path`, яку довелося б перераховувати при перенесенні гілки. Якщо дерева виростуть до десятків тисяч термінів, перехід на матеріалізований шлях не змінить специфікації.

### 6. Фільтр за терміном охоплює нащадків

Нова необов'язкова можливість `App\Content\FieldTypes\ExpandsFilterValues`: `expandFilterValues(array $prepared): array`. У `ContentNodeQuery::applyFilters` після `filterValue` для типу з цією можливістю значення розгортається, а оператор `eq` перетворюється на `in` по розгорнутому набору — решта (`EXISTS` по таблиці значень, множинні поля, AND між фільтрами) без змін. Нащадків «за замовчуванням завжди» — окремого прапорця нема (узгоджено); запит «лише напряму» додасть окремий оператор, якщо знадобиться.

### 7. Тип `term` не з'являється в адмінці до окремої зміни

`ContentFieldController` віддає форму `typeOptions = registry->keys()`. Без інтерфейсу вибору словника й введення значень у формі запису тип у випадаючому списку створив би незавершене поле. Тому `config/content.php` отримує `admin_hidden_field_types => ['term']`, а `ContentFieldController` прибирає ці ключі з `typeOptions`. `add-taxonomy-admin` видаляє запис з конфігурації. Пряме створення поля `term` кодом/запитом лишається можливим і перевіряється моделлю.

## Risks / Trade-offs

- [`whereIn` з тисячами id при великій гілці] → дерева обмежені `max_depth`; обхід по рівнях; якщо гілка стане завеликою, перейти на матеріалізований шлях.
- [Гонка: термін використано між перевіркою в моделі й видаленням] → `lockForUpdate` терміна при видаленні проти `lockForShare` при записі значення (`LocksReferences`); жорсткого FK у БД на значення немає. Видалення рядків терміна сирим SQL залишає у значеннях «висячий» `uuid` — документується в `docs/taxonomy.md`.
- [`whereIn` по `uuid` ширший, ніж по `id`] → дерева обмежені `max_depth`; різниця неістотна для очікуваних розмірів словників.
- [Зменшення `max_depth` не перевіряє паралельні вставки] → ризик прийнятний для адміністративних операцій; перевірка при кожному збереженні терміна доповнює її.
- [Змінений `slug` терміна ламає зовнішні посилання на нього] → ідентифікатором у значеннях є `uuid`, не `slug`; публічні маршрути категорій — окрема майбутня зміна.
- [Пряме видалення рядків SQL обминає моделі] → документувати в `docs/taxonomy.md`: терміни й словники видаляти через модель; БД лишає `RESTRICT`-бар'єри.
- [Нове поле, створене кодом до адмінки, не матиме інпуту у формі запису] → поле не пропонується в адмінці (рішення 7); `add-taxonomy-admin` закриває розрив.

## Migration Plan

1. Міграція таблиць таксономії (`vocabularies` → `terms` → `translations`).
2. Реєстрація типу в `config/content.php` і власника `taxonomy_term` у `config/files.php`.
Відкат: `down()` видаляє таблиці таксономії у зворотному порядку; існуючі дані не зачіпаються (значення `term` лежать у `content_values_string`: перед відкатом міграції поля `term` слід видалити). Повний PHP-набір тестів запускається один раз для цієї зміни (міграції/схема БД, конфігурація).

## Open Questions

- Чи називати адмін-розділ «Таксономія» і чи потрібні словники з перекладеною назвою (зараз назва словника не перекладається, як назва типу) — вирішується в `add-taxonomy-admin`, схему не змінює.
