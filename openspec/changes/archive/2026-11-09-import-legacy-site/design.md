# Design

## Context

**The legacy side** (observed in the running legacy database, MariaDB at `host.docker.internal:3307`, reachable from the `app` container): `node` / `block` / `page` hold `id`, `uuid`, `type_id`, `slug`, `status`, `views`, `user_id`, `created`, `updated`; `node_type` / `block_type` / `page_type` hold the types (`type`, `parent_type`, `path`, `name`, `config` as PHP-serialized data); `node_fields` / `block_fields` / `page_fields` define fields (`name`, `label`, `field_type`, `required`, `multiple`, `weight`, `config`). Values live in `field_textarea`, `field_text`, `field_link`, `field_youtube`, `field_date`, `field_file` (images and documents together), `field_reference_node_type`, `field_reference_block`, `field_meta` and the title tables `node_title` / `block_title` / `page_title`, each keyed by `entity_type` (the type key, or a model class for metadata), `entity_id`, `entity_field`, `lang` (always `ua`), `weight`. Files are named by `uri` (`news/gallery/xxx.jpg`) under `storage/app/public`. Known data problems: orphan titles and files (an owner that does not exist, `entity_id = 0`), fields that have values but no definition (`news.preview`, the `contacts_reference` of institutions), 478 node slugs outside the strict format, and 113 images over 5 MB.

**The new side:** nodes are created by `ContentNodeCreator::create()` (explicit `uuid`, `slug`, author, dates, `isActive`, and — after `add-node-views` — `views`); values are written by `ContentValueWriter` (composed values for `youtube` and `url`, file values are `{uuid}.{ext}` of an existing media row of the field's profile); files are stored by `FileStorage::store(UploadedFile, profile, user)`, which checks the profile, downscales images, and creates the media row; types and fields are rows created by `ContentType::create()` and `ContentField::create()`; after `nested-type-slugs` a child type's slug starts with its parent's. The `legacy` source database is not part of the app schema. Roles have no migration-created non-system role; the `Manager` role in the development database is test data.

## Goals / Non-Goals

**Goals:**

- A command an operator can run, inspect with `--dry-run`, and re-run until the result is accepted, without duplicating data.
- A faithful result: the same addresses, slugs, uuids, authors, dates, counters, files and content.
- A report that makes every loss visible.

**Non-Goals:**

- Migrating menus, settings, history, comments; redirects; keeping the unreferenced files.
- Making a dry run copy or validate files by storing them.
- Keeping the importer forever: it is a one-time tool; its removal is a later cleanup.

## Decisions

1. **Connection and configuration.** `config/database.php` gets a `legacy` MySQL connection from `LEGACY_DB_HOST` (default `host.docker.internal`), `LEGACY_DB_PORT`, `LEGACY_DB_DATABASE`, `LEGACY_DB_USERNAME`, `LEGACY_DB_PASSWORD` (documented in `.env.example`, no credentials in code). A new `config/legacy.php` holds the files directory (`LEGACY_FILES_PATH`, default `storage/app/public/_old`), the report directory, the hosts whose absolute `/storage/` image addresses count as legacy paths (`site_hosts`), and the user map (legacy id → email and role). `env()` is read only in config files. On Linux, `host.docker.internal` needs `extra_hosts` in the compose file, which the doc mentions; macOS Docker Desktop resolves it today.

2. **Structure: a thin command over small classes in `App\Legacy`.** `LegacyImportCommand` parses options and prints the report; `LegacyImporter` runs the steps in order; each step is a class (`ImportUsers`, `ImportTypes`, `ImportFiles`, `ImportNodes`) with a `run(ImportContext)` method; `LegacySource` is the only class that queries the legacy connection (and unserializes `config` with `allowed_classes => false`); `ValueMapper` turns the rows of one node into the `values` array; `RichTextRewriter` rewrites image addresses; `ImportReport` collects counters and lists; `ImportMap` stores the file map. This keeps the mapping unit-testable without the command. Alternatives considered: one long command class (untestable) and a seeder (no options, no report).

3. **Reading values efficiently.** Nodes are read in chunks of 200 by `id`; for each chunk one query per value table with `entity_type = ? AND entity_id IN (...)` returns the values, grouped in memory. The title comes from the matching `*_title` table. This avoids a query per node and per field (about 4400 nodes and ten tables).

4. **Order and dependencies.** Users, then types (parents before children so the prefix rule holds; the `path` becomes the slug, the legacy `type` the key), then fields, then files, then blocks and pages, then content nodes. Blocks go before content nodes because institutions refer to blocks by slug. Each node is written in its own transaction; a failure goes to the report and the run goes on.

5. **Types and fields.** The legacy `path` becomes the slug of a `content` type (`common/institutions`), and block and page types get no slug. Field keys, names (`label`), order (`weight`), `multiple` and `required` come from the definitions; `config.help`, when present, becomes the description. The field type comes from the legacy field type: `field_textarea` → `richtext`, `field_text` → `string`, `field_link` → `url`, `field_youtube` → `youtube`, `field_date` → `datetime` (multiple, at most two values), `field_image` → `image`, `field_file` → `file`, `field_reference_node_type` → `type_ref` (kind `content`), `field_reference_block` → `node_ref` (the type of the referenced blocks, `contacts`). A field that has values but no definition is added from the value table (the file field is an `image` when every value is an image, otherwise a `file`; a reference is multiple when an existing node has more than one value) and is listed in the report. The legacy field setting `config.hidden_label` (exactly `true`, as the legacy `isHiddenLabel()` reads it; a missing key means the label is shown) becomes the field setting `hide_label` of `field-hide-label`; the other legacy key `show_label` is never read by the legacy code and is ignored. The legacy field flag `hidden` (the field is not shown on the page, but stays editable and stored) becomes the "Public display" of the type: for a type that has a hidden field the importer saves `settings.public.page_fields` with every added field except the hidden ones, in `weight` order, only when the type has no `page_fields` yet (a re-run never replaces what the editors chose); types without a hidden field get no `page_fields`, so all their fields show, and the values of a hidden field are imported like any other. The rest of the legacy `config` of types and fields (display settings) and `alt` are not migrated; the report counts the dropped `alt` texts and lists the types that received `page_fields`. A legacy key that is reserved in the new CMS is reported as an error for that field.

6. **Dates.** A legacy date is one row with `begin` and `end`. It becomes the begin value of the field with weight 0, in the base language; the end is added with weight 1 only when it is not empty and differs from the begin (compared as the stored datetime), so a one-moment event has a single value. `required` follows the legacy flag (events and greetings). `max_items = 2` is set on the field.

7. **Files.** `ImportFiles` walks `field_file` rows whose owner exists (an owner is a node/block/page of the right type), plus the metadata images and YouTube previews, and for each unique `uri`: builds an `UploadedFile` in test mode from `{files}/{uri}` with the legacy `title` as the original name, calls `FileStorage::store()` with the profile of the field type (`image` for images, `document` otherwise, chosen by the field definition or, for an undefined field, by the mime of the legacy row), sets the media description from the legacy description, and records `uri → media uuid`. The profile does the checks (mime by content, size, pixel limit) and downscaling, so no import-specific file logic is needed. A missing, unreadable or rejected file is reported and its value is left out. Because the profile limit rises to 30 MB, the biggest legacy file (25 MB) passes. The PHP limits (`docker/php/uploads.ini` is already 150M/200M) need no change; the docs, which still say 25M/30M, are corrected.

8. **The import map.** A table `legacy_import_map (id, source varchar(32), source_key varchar(191), target varchar(64), timestamps; unique (source, source_key))` stores the file map (`source = 'file'`, key = the legacy `uri`, target = the media uuid). Types, fields, users and nodes are matched by their natural keys (key, type + key, email, uuid), so they need no map. Alternatives considered: matching files by `original_name + hash` (fragile with renames and duplicates) and a cache file (lost between environments). The table is created by a migration; a later cleanup change removes it with the importer.

9. **Nodes.** `ContentNodeCreator::create()` is called with the legacy `uuid`, `slug`, `authorId`, `publishedAt`, `isActive`, `views` and the mapped values, and a new named argument `legacySlug: true`. A node that already exists (matched by `uuid`) is updated: `is_active`, `published_at` and the values are rewritten (values through `ContentValueWriter::write()` per field set, replacing), but `views` is never touched after creation, so counters collected on the new site survive a re-run. `created_at` and `updated_at` are set afterwards with a base query update (they are not mass-assignable and the creator stamps now). Unpublished dates do not exist in the legacy data, so `unpublished_at` stays empty.

10. **Legacy slugs.** The model keeps its strict pattern. `ContentNode` gets a transient flag set by the creator when `legacySlug: true`; `assertValidSlug()` then validates against `LEGACY_SLUG_PATTERN` (`^[a-z0-9_-]+$`, up to 190 characters) and keeps every other rule (uniqueness, the `block-` prefix, page restrictions, the type-list collision check from `nested-type-slugs`). The node edit form (`UpdateContentNodeRequest`) keeps `regex` for a changed slug but skips it when the submitted slug equals the stored one, so editors can save an imported node. The public route widens its segment pattern from the strict slug to `[a-z0-9_-]+` (type slugs are looked up by exact match, so a wider route pattern only lets more requests reach the controller, which answers 404 for unknown ones); the reserved-path lookahead is unchanged. This is the least invasive option: no new column, no rewriting of slugs, and the strict rule still guards everything created by people. Alternative considered: normalizing the 478 slugs and adding redirects; rejected by the owner because the addresses must not change.

11. **Rich text.** `RichTextRewriter` finds `<img src="/storage/{type}/{field}/{name}">`, maps `{type}/{field}/{name}` to a legacy `uri`, imports that file on demand (through the same file routine) and replaces the address with `/storage/{uuid}.{ext}`; a missing file keeps the old address, which the sanitizer then removes, and the report lists it. The text is written through `ContentValueWriter` (so the existing sanitizer applies); to report what it removed, the importer compares the cleaned HTML with the input by counting tags, attributes and frames before and after (`HtmlSanitizer::clean()` is a pure function). The same rewrite applies to an absolute `http(s)://{host}/storage/...` address when `{host}` is in `config/legacy.php` `site_hosts` (default: `kultura-poltava.gov.ua` only; the old site host `old.kultura-poltava.gov.ua` is deliberately not listed and stays as it is). All other absolute addresses, all link addresses and frames stay as they are. `config/content.php` gets `www.google.com/maps/embed` in `richtext.iframe_hosts`.

12. **Metadata.** A `field_meta` row is one record with the columns `title`, `description`, `keywords`, `image` (it has no `entity_field`). Rows with the model class `Modules\Node\Models\Node` (65, all pointing to content nodes) become the node's `meta_title` (from `title`), `meta_description` (from `description`), `meta_image` (from `image`); rows of `NodeType` (16, one per type) become the type values of the same keys; `field_text` rows of `NodeType` with `entity_field = title` (16, one per type) become the type value `section_title`. Every value is written in the base language `default` (the legacy `lang` is `ua` everywhere). Verified on the legacy database: the metadata `image` is empty in every node and type row (only the site configuration has one), `description` is filled in 1 of 65 node rows and 14 of 16 type rows, and `field_textarea` and `field_file` have no rows for `NodeType`, so **`section_description` and `section_cover` have no source and stay empty**. Keywords, the site configuration and the `sitemap` rows of `NodeType` are dropped. The `public` settings of a type (`list_fields`, `sort`, `per_page`, `pagination`, `meta`) are display settings of the legacy `config` and are deliberately not migrated. This reading follows the system fields table in `docs/content-model.md`.

13. **Users and rights.** Users are matched by email; the two accounts (legacy ids 2 and 5, mapped in `config/legacy.php`) are created with their `password` hash (the `hashed` cast keeps an already hashed value), `email_verified_at` from the legacy row, the role `admin` (`Role::admin()`) and `Manager`. `Manager` is found or created as an ordinary role, then receives `role_permissions` rows `node:{key}` = `any` for every imported type (content, page, block) and `media` = `any`, so the editor can keep working as before. This is a proposed default (the legacy editor changed all content); the owner can narrow it in the roles screen afterwards. An existing account keeps its password and, when it is an administrator, its role.

14. **`--fresh`.** After confirmation (`--force` required without interaction): `media_relations` and `media` rows are deleted with their files and image styles (`FileStorage::delete()` semantics, row first), `legacy_import_map` is emptied, `content_types` are deleted leaf-first (the database cascades to fields, nodes, values, favorite types and admin menu entries), `role_permissions` with `node:%` scopes are removed, and the auto-increment counters of the owned tables are reset (`ALTER TABLE ... AUTO_INCREMENT = 1` on MySQL, `sqlite_sequence` on SQLite). Users, roles, menus, settings and terms stay. Menu items that point to deleted content are left alone and mentioned in the doc. `--fresh --dry-run` only prints what would go.

15. **Dry run.** `--dry-run` runs the reading and mapping parts without writing: counts by type, orphans, slug format and collisions between legacy slugs, file existence and size/mime checks against the profile limits (by reading the file, not storing it), the sanitizer comparison on the mapped HTML, and fields found only in data. It cannot validate things that need rows to exist (node references to not-yet-created blocks are checked against the legacy data instead). Copying 6.8 GB for a trial was rejected.

16. **Report and exit code.** `ImportReport` counts per step (created, updated, unchanged, skipped, failed) and keeps the lists; the command prints a table and writes `storage/app/legacy-import/report-{Ymd-His}.json`. Exit code 1 when the run could not start or any item failed.

17. **Tests.** The `legacy` connection is pointed at a second in-memory SQLite database in tests; a test helper creates the minimal legacy tables and a few rows per scenario. Files come from a temporary directory with small generated images and PDFs. No e2e: no UI and the route change is covered by feature tests.

The components are described in the new `docs/legacy-import.md`, with updates to [docs/file-storage.md](../../../docs/file-storage.md), [docs/content-model.md](../../../docs/content-model.md), [docs/public-site.md](../../../docs/public-site.md) and [docs/content-values.md](../../../docs/content-values.md).

## Risks / Trade-offs

- [Importing 29 thousand files takes long (image decoding and resizing)] → The `files` step is separate, resumable, shows progress, and a re-run skips mapped files; `--limit` allows trials.
- [A wider public segment pattern lets more junk reach the controller] → It only answers 404 after exact lookups; reserved paths and service routes are unaffected.
- [Re-running the import after the new site started editing would overwrite editors' changes to the values] → Documented: the import is for the migration window; `views` is protected from reset, other values are rewritten on purpose; a flag to skip existing nodes can be added if needed.
- [The sanitizer may remove legacy markup (tables, inline styles)] → The report counts it, and the dry run shows it before the real run.
- [Metadata and `section_title` mapping is inferred from field names] → Marked as an assumption; cheap to adjust before the real run.
- [Manager permissions default to `any`] → Visible and editable in the roles screen.
- [`--fresh` is destructive] → Confirmation, `--force` for non-interactive runs, no effect with `--dry-run`, users and roles preserved.
- [`ALTER TABLE ... AUTO_INCREMENT` is MySQL-specific] → The branch by driver is covered by a test on SQLite and exercised on MySQL during the real run.
