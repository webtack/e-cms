# Design

## Context

Див. proposal.md (чому й що). Поточний стан, що визначає підхід:

- Кожен тип поля дає одне скалярне значення: `FieldType::prepare()` повертає те, що йде в колонку `value` таблиці `content_values_*`. `ContentValueWriter::replace()` пише лише `value`, `ContentValueReader::load()` читає лише `value` і викликає `cast()`.
- Усі таблиці значень мають JSON-колонку `options` для додаткових даних значення (`docs/content-values.md`), яку ніхто не читає й не пише. За рішенням власника всі додаткові дані складених значень лежать саме в ній (окремі таблиці й JSON у `value` відкинуто).
- Writer трактує масив як **список** значень: `normalizeAll()` фільтрує його елементи, `singleValue()` відхиляє масив для немножинного поля, `replace()` розгортає масив у рядки. Складене значення (асоціативний масив) цим правилам суперечить.
- Файлові типи реалізують `TracksFiles`: після запису Writer синхронізує `media_relations`. `fileUuids()` отримує значення в тому вигляді, в якому його передано до запису, і в тому, в якому його читають.
- Завантаження файлу поля: `FileController`, `UploadRules::forField()` і `StoreFileRequest` мають окрему гілку `instanceof RichTextType` («поле без файлових налаштувань, але з профілем зображень»).
- Файли (`FileStorage::store`) приймають `UploadedFile` і профіль; вільні файли без зв'язків прибирає `files:prune`.
- `.env` уже містить `YOUTUBE_API_KEY`; у `config/services.php` запису `youtube` немає.
- Документація: `docs/content-values.md` (реєстр типів і схема таблиць), `docs/admin-content-nodes.md` (форма запису), `docs/admin-content-fields.md` (типи), `docs/file-storage.md` (файли й зв'язки), `docs/e2e-testing.md`.

## Goals / Non-Goals

**Goals:**
- Тип `youtube` без нових таблиць і без змін для наявних типів.
- Найменше розширення ядра, потрібне для `options`: опційний контракт складеного значення.
- Збереження не залежить від мережі: ходити до YouTube може лише явний запит «Отримати дані».
- Скрін під контролем медіатеки (використання, очищення).

**Non-Goals:**
- Переклади, кеш відповідей API, фонове оновлення, відтворення відео на сайті.
- Загальний механізм «усі типи можуть мати `options`»: контракт потрібен лише типам, що його реалізують.
- Редагування імені й опису файлу скріна з віджета (це робить медіатека).

## Decisions

### D1. Опційний контракт складеного значення `ComposedValue`

Новий інтерфейс (за зразком `TracksFiles`), який реалізує `YoutubeType`:

```
split(mixed $input): array   // [$scalar, ?array $options]; вхід — рядок-посилання або масив форми
compose(mixed $scalar, ?array $options): mixed   // складене значення для читання
```

- Writer у `replace()`: для типу з `ComposedValue` бере `[$scalar, $options]` з `split()` і пише `value = $scalar`, `options = json_encode($options)` (або `NULL`); для інших типів `options` = `NULL`, `prepare()` працює як раніше.
- Reader: вибирає `options` разом зі `value`, для типу з `ComposedValue` викликає `compose($row->value, json_decode($row->options))` замість `cast()`.
- `FieldType` не змінюється, інші типи не чіпаємо.

Відкинуто: (а) додати `options` у `FieldType::prepare()` і `cast()` для всіх типів: ламає контракт і всі реалізації; (б) тип сам пише в БД: обходить транзакцію й `TracksFiles`.

### D2. Складене значення — асоціативний масив, а не список

Форма значення (PHP, JSON форми, читання): `{ url, video_id, title, description, screen }`. На вході `url` — будь-яка приймана форма посилання або 11 символів `id`; зберігається введене посилання (обрізані пробіли), крім Shorts і голого `id`, які стають `https://www.youtube.com/watch?v={id}`. На вході `video_id` ігнорується: його завжди визначає `split()` із `url`, тож не розходиться з посиланням. У `options` лежать `video_id` (завжди) та непорожні `title`, `description`, `screen`. Для читання `compose()` повертає всі п'ять ключів, відсутні як `null`. `video_id` у `options` не фільтрується ядром (фільтри працюють лише по колонці `value`), тому пошук за відео лишається `contains` по `value`; `video_id` потрібен для читання без розбору посилання (рендер, запит до API, превʼю) і як стабільний ключ.

Через це Writer повинен відрізняти «одне складене значення» від «списку»: у `normalizeAll()`, `singleValue()` і `replace()` умова «значення є списком» стає «масив і (тип не `ComposedValue` або `array_is_list`)». Для множинного поля `youtube` значення — список асоціативних масивів, як і очікується. Це єдині три місця Writer, що торкаються форми значення.

Посилання зберігається у `value` (рішення власника), а не в `options`, тож дубльованого стану немає. Параметри посилання, зокрема таймкод `t`, зберігаються (рішення власника).

### D3. Значення, фільтр і валідація

- `table()` = `content_values_string`, `value` = введене посилання (обмеження 512 символів за колонкою `string(512)`; правило `max:512`). Одне відео може лежати в різних формах, тож `value` не ідентифікує відео однозначно.
- `operators()` = `['contains']`; `searchable()` = `false`. Рівність не підтримується, бо форми посилання на одне відео різні; відео знаходиться за вхідним `id` через `LIKE` (оператор `contains` ядра, `prepare()` для нього не викликається). Це наслідок рішення зберігати введене посилання; індекс по `value` для `LIKE '%…%'` не використовується, що прийнятно для адмінського пошуку.
- `rules()` для запису: значення — рядок або масив з ключами `url`, `title`, `description`, `screen` (інші ігноруються); `url` розпізнається як посилання на відео або `id`; `title` ≤ 255 символів, `description` ≤ 10000 символів (обрані межі, не налаштовуються; `settings` поля у типу немає); `screen` — наявний файл профілю `image` (правило `FileValue` без звуження). Межі довжини піддаються зміні одним рядком коду.
- `isBlank()`: `null`, `''` або масив без непорожнього `url`.
- Розбір посилання: одна функція типу витягує 11-символьний `id` з форм `watch?v=`, `youtu.be/`, `embed/`, `shorts/`, `live/` (хости `youtube.com`, `www.`, `m.`, `music.`, `youtube-nocookie.com`, `youtu.be`) або приймає рівно 11 символів `[A-Za-z0-9_-]` і для голого `id` будує `https://www.youtube.com/watch?v={id}`. Посилання на Shorts (`/shorts/{id}`) переписується на звичайне `watch?v={id}` зі збереженням решти параметрів, тому що YouTube відтворює той самий ролик за `watch?v=`, а Data API `videos.list` ідентифікує Shorts так само, як звичайне відео, за `id`. Мережа не використовується. Посилання на канали, списки відтворення й `watch` без `v` відхиляються.

### D4. Файл скріна: `TracksFiles` без змін контракту

`YoutubeType` реалізує `TracksFiles`. `fileUuids()` приймає і вхідне, і прочитане значення: обидва мають ключ `screen`; оскільки одне складене значення — асоціативний масив, метод розрізняє його від списку через `array_is_list` (інакше стандартне `is_array ? $v : [$v]` розгорнуло б ключі). Тому розширення `TracksFiles`, яке виглядало необхідним, не потрібне. Writer і далі синхронізує зв'язки в тій самій транзакції. Скрін, завантажений і не збережений, стає вільним файлом і прибирається `files:prune`.

### D5. Запит «Отримати дані»: окремий ендпоінт і сервіс

- Маршрут `POST /admin/youtube/lookup` (ім'я `youtube.lookup`) у групі `auth` + `verified` поруч з `files.store`; `YoutubeLookupController` з `FormRequest` (`url` обов'язковий рядок).
- Сервіс `App\Youtube\YoutubeLookup` робить: розбір посилання (та сама функція, що й у типі; Shorts переписується на звичайне), з нього `id` → `GET https://www.googleapis.com/youtube/v3/videos?part=snippet&id={id}&key=…` через `Http` з таймаутом → вибір найбільшого скріна (`maxres`, `standard`, `high`, `medium`, `default`; при невдалому завантаженні наступний менший) → завантаження в тимчасовий файл → `FileStorage::store()` через `UploadedFile` з тимчасового файлу (профіль `image`, користувач запиту), після чого тимчасовий файл видаляється. Окремий `FileStorage` метод для байтів не потрібен.
- Ключ: `config('services.youtube.key')` (`env('YOUTUBE_API_KEY')`); в `.env.example` додати ключ без значення. Відповідь і Inertia-пропси ключа не містять.
- Відповідь `200`: `{ url, title, description, screen: { value, uuid, name, mime, size, url } }`. Помилки: `422 { message, reason }` для `invalid_url` і `not_found`; `503 { message, reason }` для `not_configured` і `unavailable` (мережа, квота, 403/5xx). Тексти — через `__()`, ключі в `lang/en.json` і `lang/uk.json`. Збереження скріна в медіатеку — останній крок, тому при будь-якій помилці нічого не створюється й не змінюється.

Відкинуто: виклик API в `saving`/Writer, як було в старій CMS (залежність запису від мережі, неочікуване перезаписування ручних правок), та oEmbed (немає опису).

### D6. Завантаження власного скріна: спільний `HasUploadProfile`

Для заміни скріна віджет використовує наявний `FileUpload` поля (`POST /admin/files` з `content_type` + `field_key`). Щоб не додавати четверту гілку `instanceof`, вводиться маленький інтерфейс `HasUploadProfile { uploadProfile(): string }`, який реалізують `RichTextType` та `YoutubeType`; `FileController`, `UploadRules::forField()` і `StoreFileRequest` замінюють `instanceof RichTextType` на нього. Поведінка richtext не змінюється. Побічний ефект: `ContentNodeController::formFields` дає тим полям `mimes`/`max_size` профілю (для richtext вони не використовуються).

### D7. Форма запису й таблиця

- `NodeFieldInput` отримує гілку `case 'youtube'` з компонентом `YoutubeField`: список карток відео (скрін, заголовок-посилання, опис) з кнопками «Додати відео», «Редагувати», «Видалити». Значення форми — об'єкт `{ url, title, description, screen }` (`video_id` форма не надсилає, сервер визначає його сам). Скрін картки береться з наявного `files` (`fileInfo()`).
- Заголовок картки — звичайний `<a href={url} target="_blank" rel="noopener noreferrer">` (не кнопка); без заголовка текстом є адреса.
- Додавання й редагування — у `YoutubeFieldDialog` на `ui/dialog`. Вікно тримає локальну чернетку `{ url, title, description, screen }` і віддає її у форму лише по «Готово»; «Скасувати» чи закриття відкидає чернетку. У вікні: `Input` посилання з кнопкою «Отримати дані», `Input` заголовка, `Textarea` опису, блок скріна на `FileUpload`. Кнопка викликає `lookup` через `fetch` (як `FileUpload`), стан завантаження й помилку тримає вікно; успіх перезаписує `title`, `description`, `screen` чернетки, помилка нічого не змінює. Зміна `url` без натискання кнопки не торкається решти полів. Серверна частина не змінюється.
- `ContentNodeController`: `fileInfo()` додатково збирає `screen` значень `youtube`, щоб форма редагування мала прев'ю без додаткових запитів; `text()` для `youtube` повертає `title` або посилання; `sortable()` для `youtube` = `false`.
- Записи, що вже зберігають складені значення, форма отримує як об'єкти (`formValue()` не змінює масиви).

## Risks / Trade-offs

- [Три місця Writer змінюються, ризик регресу для наявних типів] → зміна лише додає гілку для `ComposedValue`; обов'язково прогнати наявні тести запису/читання й `FieldTypeExtensibilityTest`.
- [Квота YouTube Data API (10000 одиниць/добу, `videos.list` коштує 1)] → запит виконується лише за явним натисканням, повідомлення про квоту розрізняється; кешу не робимо.
- [Скріни, які користувач отримав, але не зберіг, засмічують медіатеку] → вони вільні файли без зв'язків; `files:prune` прибирає їх за стандартним правилом. Масовий збір скрінів сторонніми не можливий: запит лише для автентифікованих.
- [SSRF: сервер завантажує зображення за URL з відповіді API] → адреса береться лише з відповіді YouTube API, не з вводу користувача; додатково дозволяємо тільки хост `i.ytimg.com` (та `img.youtube.com`) і `https`.
- [Тип скріна: YouTube віддає JPEG, `FileStorage` дивиться на вміст і профіль] → якщо вміст не зображення або перевищує ліміт профілю, це невдале завантаження скріна, тобто «відео недоступне» без часткового результату (зафіксовано в spec).
- [Скрін, отриманий у модальному вікні й скасований, лишається вільним файлом] → `files:prune` прибирає його за стандартним правилом.
- [Редагований title/description не оновлюється при зміні на YouTube] → свідомо: оновлення лише повторним «Отримати дані».

## Migration Plan

Міграцій немає: використовуються наявні таблиця `content_values_string` і колонка `options`. Розгортання: додати `YOUTUBE_API_KEY` у середовище (на цьому стенді він уже є). Відкіт: прибрати рядок `youtube` з `config/content.php`; значення в БД залишаються нешкідливими, але поля цього типу після відкоту не працюватимуть, тому перед відкотом їх треба видалити.

## Open Questions

- Межі довжини `title` (255) і `description` (10000) обрані як розумні значення за замовчуванням; змінюються одним рядком, не впливають на специфікації.
