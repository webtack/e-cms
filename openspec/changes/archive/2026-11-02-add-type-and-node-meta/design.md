# Design

## Context

Мотивація й обсяг: [proposal.md](proposal.md). Поточний стан, від якого відштовхується підхід:

- Значення полів лежать у `content_values_{string,text,integer,decimal,boolean,date,datetime}` і прив'язані до запису композитним FK `(content_node_id, content_type) -> content_nodes(id, content_type)` та до визначення поля FK `(content_type, field_key) -> content_fields(content_type, key)`; унікальність `(content_node_id, content_type, field_key, lang, weight)` ([content-values.md](../../../docs/content-values.md)).
- Файли в значеннях `image`/`file` лежать у `content_values_string` як `uuid` файлу, а їх облік веде поліморфна `media_relations (owner_type, owner_id, role, lang)`; `FileRelations` приймає довільний `owner_type`, а `MediaOwner` описує власника медіатеці ([media-library.md](../../../docs/media-library.md)). Сьогодні є лише власник `content_node`.
- `ContentValueWriter` і `ContentValueReader` приймають `ContentNode`; всі запити вибірки (`ContentNodeQuery`) і `ContentNodeOwner` з'єднуються зі значеннями через `content_node_id`, тож рядки без запису їх не зачіпають.
- Системне поле `title` створюється зашитим кодом у `ContentType::booted()` (`created`), `ContentField::RESERVED_KEYS` забороняє створювати лише ключі службових колонок ([content-model.md](../../../docs/content-model.md)).
- `ContentNodeForm` редагує лише базову мову; інтерфейсу перекладів запису немає. Сторінка налаштувань типу — `Pages/Admin/ContentTypes/Edit.tsx` з `ContentTypeForm` ([admin-content-types.md](../../../docs/admin-content-types.md)).
- Тести йдуть на SQLite `:memory:`, застосунок працює на MySQL 8.4: міграції мають працювати на обох (як у наявній міграції з колацією).

## Goals / Non-Goals

**Goals:**
- Одне сховище значень і для записів, і для типів; ті ж `FieldType`, переклади, валідація та облік файлів.
- Системні поля метаданих і розділу описані в одному місці в коді; створення, бекфіл, зарезервовані ключі та визначення власника виводяться з нього.
- Жодних змін у вибірці, фільтрах, сортуванні й пошуку записів.

**Non-Goals:**
- Узагальнення сховища до довільних сутностей (користувачі, меню): поля типу прив'язані до `content_types`, а поліморфний власник без FK втратив би каскад видалення запису.
- Користувацькі поля рівня типу, колонка `scope` у `content_fields`.
- Публічне відображення, `og:`-розмітка, резервні значення (`section_title` -> `name`).
- Багатомовність в інтерфейсі: перемикач мови, переклад окремих полів, зокрема зображень (див. [Рішення 8](#decisions)); сховище до цього готове.
- Інтерфейс перекладу записів.

## Decisions

**1. Власник значення в тих самих таблицях.** У кожній `content_values_*`: `content_node_id` і `content_node_uuid` стають nullable, додається `entity` (`'node'` за замовчуванням для наявних рядків, `'type'` для рядків типу). Рядок типу: `content_node_id IS NULL`, `content_type` = ключ типу. Композитний FK на `content_nodes` при `NULL` не перевіряється (MATCH SIMPLE), FK на `content_fields` лишається й діє для обох власників. *Альтернативи:* (а) дзеркальні таблиці `content_type_values_*`, відхилено через дубль writer/reader і запитів; (б) поліморфні `entity_type`/`entity_id`/`entity_uuid` замість зв'язку з записом, відхилено, бо втрачається FK і каскад видалення запису, а `content_type` одночасно є якорем визначення поля й не може стати поліморфним; (в) синглтон-запис «індексу» типу, відхилено, бо ламає `nodes_count`, унікальність slug і списки.

**2. Цілісність: CHECK і функціональний унікальний індекс.** `CHECK ((entity = 'node' AND content_node_id IS NOT NULL AND content_node_uuid IS NOT NULL) OR (entity = 'type' AND content_node_id IS NULL AND content_node_uuid IS NULL))`. Існуючий unique з `NULL` не обмежує рядки типу, тому додається `UNIQUE ((COALESCE(content_node_id, 0)), content_type, field_key, lang, weight)` (функціональний індекс; MySQL ≥ 8.0.13, SQLite підтримує індекс на вираз). Blueprint не вміє ні CHECK, ні вирази, тому міграція використовує сирий SQL з гілкою за драйвером, як наявна міграція з колацією. Наявний unique лишається (для записів він ефективний, а новий його підсилює). MySQL 8.4 у `docker-compose.yml` підтримує обидві можливості. *Альтернатива:* лишити лише `entity` без CHECK, відхилено, бо таблиця допустила б суперечливі рядки.

**3. Значення типу не потрапляють у вибірку записів.** Запити `ContentNodeQuery` та `ContentNodeOwner` з'єднуються через `content_node_id`, тож змін там немає (перевіряється тестом). Два місця без прив'язки до запису змінюються свідомо: `ContentField::hasStoredValues` лишається на обох власників (поле зі значенням типу не видалити), а `ContentFieldController::valuedKeys` отримує `entity = 'node'`. Правило для майбутнього коду: запит «усі значення поля» мусить явно обирати власника.

**4. Власник у writer і reader — невеликий об'єкт.** Вводиться значення-об'єкт власника з двома іменованими конструкторами (запис, тип); він дає `entity`, `content_node_id`, `content_node_uuid`, `content_type`, `owner_type`/`owner_id` для `FileRelations` і перелік підходящих полів. `ContentValueWriter::write/validate` і `ContentValueReader::load` приймають запис (як зараз) або власника-тип; `replace()` будує рядки з об'єкта. Публічні сигнатури для записів лишаються сумісними. Для типу reader читає `entity = 'type' AND content_type = ?` у потрібній мові. *Альтернатива:* окремий `ContentTypeValueWriter`, відхилено через дубль.

**5. Реєстр системних полів у коді.** Один клас (поряд із `FieldTypeRegistry`) містить для кожного системного поля: ключ, тип значення, назву, види типів, власників (`node`, `type`), перекладність, обов'язковість і вагу. Він:
- створює поля разом із типом (замінює зашитий `title` у `ContentType::booted()`; усе виконується в тій самій транзакції `save()`);
- віддає перелік ключів для `RESERVED_KEYS`-перевірок (`StoreContentFieldRequest` і `ContentField::assertValid()` відхиляють нове несистемне поле з ключем будь-якого системного поля; створення самої системної строки це правило обходить, бо `is_system = true`);
- відповідає, чи належить поле власнику (`title` і несистемні лише записам).
Колонки `scope` немає: скоуп потрібен лише системним полям. *Альтернатива:* колонка `scope` (`node/type/both`), відхилено як зайву сутність. Назви системних полів (`name`) — англійською, як у `title`; переклад підписів інтерфейсу робиться клієнтською частиною за ключем, а не назвою з БД.

**6. Бекфіл у міграції.** Окрема міграція вносить сім полів наявним типам за матрицею видів, зі знімком переліку всередині (не залежить від еволюції класу реєстру), у транзакції, з `weight` після найбільшої ваги типу. Якщо тип уже має користувацьке поле з ключем системного, міграція до будь-яких змін падає з переліком конфліктів (як міграція `user_id`) і користувач перейменовує поле. Відкат видаляє системні поля метаданих разом зі значеннями.

**7. Файли значень типу.** `FileRelations::sync` викликається з `owner_type = 'content_type'`, `owner_id = content_types.id`, роль — ключ поля. У `config('files.owners')` реєструється `ContentTypeOwner` (мітка — назва типу, URL — сторінка налаштувань виду `content`). Хук `deleted` типу викликає `forgetOwner('content_type', $id)`; оскільки каскад типу виконує БД і події не спрацьовують, хук ставиться на `deleting`, коли тип ще існує (поряд із наявним `nodes_count`-обмеженням).

**8. Мови: лише `default` в UI.** Усі сім полів мають `is_translatable = true`, а сховище значень і облік файлів уже підтримують `lang`, тому writer і reader приймають мову, а `lang = default` є значенням за замовчуванням і закладкою на майбутнє. Жоден екран цієї зміни не має перемикача мови й не передає іншу мову: форми запису і типу редагують лише базові значення. Як виглядатиме переклад кожного поля (зокрема зображень), вирішується окремою зміною про багатомовність.

**9. Поля форми запису.** `ContentNodeController::formFields()` повертає поля, що належать запису (`SystemFields` відфільтровує `section_*`), і позначає `meta_*` ознакою панелі (`panel: 'seo'`). `ContentNodeForm` рендерить такі поля в панелі «SEO» тими самими `NodeFieldInput`/`NodeFieldList`; дані й збереження не змінюються, бо метаполя — звичайні поля запису. Сторінка полів типу (`/fields`) показує системні поля як інші системні (без видалення).

**10. Панелі типу.** `ContentTypeController::edit` додає для виду `content` пропс `typeFields` (визначення полів `section_*` і `meta_*` та їхні базові значення). Збереження — окремий маршрут `PUT /admin/content-types/{key}/values` (запит із `values`; мова завжди `default`), який викликає writer із власником-типом; основна форма типу й `UpdateContentTypeRequest` не змінюються. Панелі використовують спільний компонент з панеллю «SEO» запису; як саме перевикористати `NodeFieldInput` (його вхідні пропси прив'язані до запису), визначається на початку відповідного завдання.

**11. Читання значень типу.** Публічний метод на сервісі читання (`ContentValueReader::loadForType`) повертає значення типу для мови, відсутні як `null`, без підстановки базової; невідомий або чужий власнику ключ дає `ValidationException`, як для записів.

## Risks / Trade-offs

- [Міграція змінює nullable та індекси в семи таблицях; SQLite перебудовує таблиці] → міграція має гілки для MySQL та SQLite, перевіряється на `migrate:fresh` у SQLite-тестах і вручну `docker compose exec app php artisan migrate:fresh` проти MySQL; відкат (`down`) видаляє рядки типу, `entity`, CHECK та функціональний індекс.
- [FK на запис не перевіряється для рядків типу, CHECK і функціональний індекс — сирий SQL] → тести на обох драйверах де можливо; документація описує інваріант; будь-який майбутній запит «усі значення поля» мусить обирати власника.
- [Користувацьке поле з ключем системного вже існує] → міграція падає до змін з переліком конфліктів; користувач перейменовує поле.
- [Поле зі скоупом лише типу показується в налаштуваннях полів] → це системне поле, його не можна видалити.
- [Два місця правди про системні поля: реєстр та знімок у міграції] → знімок навмисно незмінний; новий ключ потребує нової міграції бекфілу.
- [Форма запису перекладів не має, тож `meta_*` запису редагуються лише в базовій мові] → сховище перекладів готове, UI — окрема зміна.

## Migration Plan

1. Міграція схеми `content_values_*` (nullable власник, `entity`, CHECK, функціональний unique).
2. Міграція бекфілу системних полів.
3. Код: реєстр, власник, writer/reader, `ContentType`/`ContentField`, контролери, UI.
4. Відкат: зворотний порядок; рядки типу й системні поля метаданих видаляються.

## Open Questions

Немає блокуючих. Дрібні деталі (назви класів, перевикористання `NodeFieldInput` у панелях типу) вирішуються на початку відповідних завдань.
