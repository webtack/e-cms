# Proposal

## Why

Для публічного сайту записи й розділи потребують метаданих (`title`, `description`, `image` для SEO та соцмереж), а розділ типу контенту ще й власного видимого опису (заголовок, текст, обкладинка). Сьогодні система вміє зберігати значення лише для запису, а тип має тільки службові колонки й `settings`, тож метаданих типу з перекладами та файлами ніде зберегти. Системне поле створюється лише одне, `title`, і воно зашите в `ContentType::booted()`.

## What Changes

- **Системні поля метаданих.** Нове джерело істини в коді, реєстр системних полів, описує ключ, тип значення, назву, види типів, власників (запис, тип) і перекладність. Реєстр створює поля разом із типом (нині це робить зашитий `title`) і бекфілом для наявних типів.

  | поле | значення | `content` | `page` | `block` |
  | --- | --- | --- | --- | --- |
  | `title` (є) | string, обов'язкове | запис | запис | запис |
  | `meta_title` | string | запис і тип | запис | - |
  | `meta_description` | text | запис і тип | запис | - |
  | `meta_image` | image | запис і тип | запис | - |
  | `section_title` | string | тип | - | - |
  | `section_description` | richtext | тип | - | - |
  | `section_cover` | image | тип | - | - |

  Усі нові поля необов'язкові, немножинні, системні (не видаляються, `type`, `is_multiple`, `is_required` не змінюються) і перекладні. Власник поля, запис чи тип, виводиться з реєстру, а не з колонки; несистемне поле завжди належить запису.
- **Значення типу в тих самих таблицях значень.** У всіх `content_values_*` колонки `content_node_id` і `content_node_uuid` стають nullable, додається колонка `entity` (`node`/`type`). Рядок типу не має запису, а його `content_type` дорівнює ключу цього типу. Узгодженість `entity` з `content_node_id` захищає CHECK, унікальність рядків типу функціональний індекс (міграція з гілкою для MySQL і SQLite).
- **Запис і читання для двох власників.** `ContentValueWriter` і `ContentValueReader` приймають запис або тип; поле, що не належить власнику за реєстром, відхиляється. Читання значень типу (за мовою, без підстановки базової) стає частиною API.
- **Файли значень типу.** `meta_image` і `section_cover` обліковуються в `media_relations` з `owner_type = 'content_type'`; видалення типу прибирає ці зв'язки.
- **Зарезервовані ключі.** `ContentField::RESERVED_KEYS` розділяється на ключі службових колонок і ключі системних полів, які заводить лише система (`meta_*`, `section_*`): користувач нове поле з таким ключем створити не може.
- **Форма запису.** Поля `meta_*` виходять з основного списку полів в окрему панель «SEO».
- **Налаштування типу `content`.** На сторінці налаштувань з'являються панелі «Розділ» (`section_*`) і «SEO» (`meta_*`) (лише базова мова).
- **`valuedKeys`** (поля зі значеннями) рахує лише значення записів.

**Не входить:** публічне відображення (вибір запасного заголовка розділу, `og:`-розмітка), додаткові метаполя (`og_*`, `canonical`, `robots`), поліморфні сутності за межами запису й типу (користувачі, меню), користувацькі поля рівня типу. Багатомовність в інтерфейсі (перемикач мови, переклад окремих полів, зокрема зображень, підстановка базового значення) проєктується окремо: тут усі форми працюють лише з базовою мовою `default`, а сховище вже підтримує `lang` (`content_values_*.lang`, `media_relations.lang`).

## Capabilities

### New Capabilities

Немає.

### Modified Capabilities

- `content-model`: реєстр системних полів замість зашитого `title`; поля метаданих і розділу та їхня видимість за видом; зарезервовані ключі системних полів; значення типу в каскаді видалення.
- `content-values`: спільні таблиці значень мають двох власників (запис, тип) з CHECK та унікальністю; запис і читання для типу; відхилення поля, що не належить власнику.
- `media-library`: власник файлу `content_type`; облік і прибирання зв'язків значень типу.
- `admin-content-fields`: ключі системних полів метаданих і розділу входять до зарезервованих при створенні поля.
- `admin-content-types`: панелі «Розділ» і «SEO» на сторінці налаштувань типу `content`.
- `admin-content-nodes`: панель «SEO» у формі запису; `meta_*` не потрапляють до основного списку полів форми.

## Impact

- **Код:** міграції (nullable власник і `entity`, CHECK, функціональний unique для `content_values_*`), новий клас реєстру системних полів і бекфіл-міграція, `app/Models/ContentType.php` (створення полів з реєстру), `app/Models/ContentField.php` (`RESERVED_KEYS`, видалення, хук файлів), `app/Content/ContentValueWriter.php` і `ContentValueReader.php` (власник), `app/Files/FileRelations.php` та `app/Files/Owners/*` (власник `content_type`), `app/Http/Controllers/Admin/ContentTypeController.php` (передача й збереження значень), `ContentNodeController.php` (поділ полів форми), `ContentFieldController.php` (`valuedKeys`), запити валідації, React: сторінка налаштувань типу, `ContentNodeForm`, спільний компонент панелі полів, переклади `lang/en.json` і `lang/uk.json`.
- **Тести:** Feature-тести схеми й власників, реєстру та бекфілу, запису/читання типу, прибирання файлів, форм типу й запису; e2e спеки областей «типи контенту» і «записи» (точний набір за таблицею `docs/e2e-testing.md`).
- **Документація (docs/, українською):** оновити `content-model.md`, `content-values.md`, `content-querying.md` (читання типу, ізоляція за власником), `media-library.md`, `admin-content-types.md`, `admin-content-nodes.md`, `admin-content-fields.md` (зарезервовані ключі), `e2e-testing.md`; індекс `docs/README.md` лишається чинним, нових файлів не очікується.
- **Залежності:** нових немає. Міграції змінюють усі сім таблиць `content_values_*`; на непорожній БД бекфіл додає поля наявним типам.
