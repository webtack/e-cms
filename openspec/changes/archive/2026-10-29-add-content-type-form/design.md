# Design

## Context

The `ContentType` model validates itself in `saving` (`assertValid`): the format of `key`, `kind` from `config('content.kinds')`, immutability of `key`/`kind`, the rules for `parent_type` (the same kind, no cycles) and `settings.list`; on creation it adds the system field `title` (see [docs/content-model.md](../../../docs/content-model.md)). In the DB the fields and nodes of a type are deleted by cascade, child types — `restrictOnDelete`. The list page is `Admin\ContentTypeController::index` on `TablePage::fromCollection()` ([docs/admin-content-types.md](../../../docs/admin-content-types.md), [docs/admin-data-table.md](../../../docs/admin-data-table.md)); rows are returned whole, so they may contain keys outside the columns. `Column` has an optional `cell`. The row menu is `ContentTypeRowActions` (all items `disabled`). The motivation is in proposal.md.

Shared in the interface: Inertia (`useForm`, `router`), shadcn `Input`/`Label`/`Select`/`Button`, toasts from `flash.success`/`flash.error` (`FlashToaster`), translations `t()` from `lang/*.json`. The project does not yet have `FormRequest`s; there is no dialog component in `Components/ui`, but `radix-ui` is among the dependencies.

## Goals / Non-Goals

**Goals:**
- Working creation, editing and deletion of types of the `content` kind with server-side validation and errors next to the fields.
- Storing a public `slug` of a type (only `content`) with format and uniqueness guarantees in the model.
- A list of `content` only, without the kind and description columns; the description is under the name.

**Non-Goals:**
- The fields page, forms for `page`/`block`, the public site route by `slug`, reservation of service paths.
- Changing `key`/`kind`, cascade deletion of nodes from the admin, changing the contract of `DataTable`/`TablePage`.

## Decisions

1. **Validation of the slug — in the model.** `assertValid()` gets the rules for `slug`: `nullable`, `regex:SLUG_PATTERN` (`/^[a-z0-9]+(-[a-z0-9]+)*$/`), `max:190`, `unique` on `content_types.slug` excluding the record itself, and a ban on a slug for `kind !== 'content'`. The rule applies to seeders, tinker and forms. Alternative — only a `FormRequest`: it would miss other paths of creation.
2. **Case-insensitive uniqueness — through the collation.** A `string(190)` column with the default ci collation of MySQL; `NULL` allows many types without a slug. The format requires lowercase letters, so in a cs collation there would be no case-duplicates anyway.
3. **Migration** `add_slug_to_content_types_table`: `string('slug', 190)->nullable()->unique()` after `name`; existing rows get `NULL`; `down()` removes the index and the column.
4. **The type is looked up by key.** The route parameter `{contentType:key}` (binding by `key`, not `id`) and the same `ContentTypeController`: `create`, `store`, `edit`, `update`, `destroy`. Types of a kind other than `content` give 404 on these routes: either a `scopeBindings`-like restriction via `Route::bind`, or an explicit `abort_unless($type->kind === 'content', 404)` in one private `resolve()` method. Names: `admin.content-types.create|store|edit|update|destroy`.
5. **The server sets and keeps `kind` and `key`.** `store` calls `ContentType::create([...validated, 'kind' => 'content'])`; `update` updates only `name`, `slug`, `parent_type`, `description` (from `validated()`, without `key`/`kind`). The `kind` field and (in `update`) `key` are not part of the rules, so values from the request are discarded.
6. **`FormRequest`s.** `StoreContentTypeRequest` (`name` required/max:255; `key` required/`KEY_PATTERN`/max:64/`unique`; `slug` nullable + the rules of item 1; `parent_type` nullable + `Rule::exists('content_types','key')->where('kind','content')`; `description` nullable/string) and `UpdateContentTypeRequest` (without `key`; `slug` with `Rule::unique(...)->ignore($type)`; `parent_type` additionally is not equal to the type's key and does not belong to its descendants). The shared rules are in one place (a trait or a static method), so that Store and Update do not diverge. The rules duplicate the model's deliberately: the form returns field-level errors, the model remains the last barrier. The list of descendants is given by `ContentType::descendantKeys()`: a helper method in the model (a breadth-first traversal of `children`), which also feeds `parentOptions` in `edit`.
7. **Deletion: the ban for nodes and children — at the controller level.** `destroy` checks `$type->nodes()->exists() || $type->children()->exists()` and then returns `back()->with('error', ...)` without changes; otherwise `$type->delete()` (fields go by cascade) and a redirect to the list with `success`. The model requirement of cascade (deleting a type deletes its nodes) does not change: the ban applies at the admin level, not the model level, because other scenarios (seeders, future operations) may deliberately delete a type together with its data. Alternative — a `deleting` hook in the model: it would change the shared behaviour of the model, which goes beyond this change.
8. **Delete dialog.** Add the shadcn `alert-dialog` (`Components/ui/alert-dialog.tsx` on `radix-ui`). The "Delete" item opens a dialog with the type name. The rows provide `nodes_count` and a new service `children_count` (not a column; `TablePage` does not trim rows). If either of them is > 0, the dialog shows the reason and has no active confirm button; otherwise the confirmation performs `router.delete(route)`. The server checks the ban itself (item 7), so the dialog is only a convenience.
9. **Row menu.** `ContentTypeRowActions` receives `row`; "Edit" — a `DropdownMenuItem asChild` with an Inertia `Link` to `edit`; "Delete" opens the dialog (the state is in the parent component, so that the dialog does not close together with the menu); "Fields" stays `disabled`.
10. **The list is `content` only, without filters.** `index` adds `->ofKind('content')`, removes `kind` from the rows and from `columns()`, adds `slug` and `children_count` (service). No column is `filterable`: `TableRequest` rejects filters with the reason `not_filterable`, so filters in the address (including a stale `kind`) are ignored. The search `q` goes over the `text` columns: `name`, `description`, `slug`, `key`; `description` remains a server column without a client counterpart, while `parent_type` and the counters do not take part in the search (`searchable: false` / type `number`).
11. **Description under the name.** The `name` column in `Index.tsx` gets a `cell`: the name, and under it (if the description is not empty) a `<div className="text-xs text-muted-foreground">` with the description, trimmed to two lines (`line-clamp-2`), the full text in `title`. Sorting of the `name` column remains by name.
12. **Filters are enabled by the table prop `filterable`.** Currently `DataTableToolbar` always renders `DataTableFilters`. An optional prop `filterable?: boolean` is added to `DataTableBaseProps` (default `false`): only with `filterable` does the toolbar render the filter button, otherwise there is none. The column-level `filterable` remains and defines which columns can be filtered. This is a change of the default behaviour, so the existing tables (the demo `DataTableDemo`, server and client) receive `filterable` explicitly, and their markup does not change; the new table of types does not pass the prop. Alternative — auto-hiding when there are no filterable columns: implicit, and does not allow turning filters off for a table whose columns are filterable.
13. **Forms.** A shared component `ContentTypeForm` (`useForm`; mode `create`/`edit`) and the pages `Create.tsx`, `Edit.tsx`. In `edit` mode the key is an `Input` with `readOnly` and a hint about its immutability; `PUT` via `form.put`. A `Select` of the parent type with the option "no parent type" (an empty value → `null`). The key is not generated automatically from the name: its immutability makes a silent substitution risky; the field has a hint about the format. Breadcrumbs: `extraTitles` in `navigation.ts` gets a title for `/create`; for `/{key}/edit` the breadcrumb is taken from the pattern `/admin/content-types/*/edit` (check whether `getBreadcrumbs` supports this, otherwise extend it).
14. **Documentation.** Update [docs/admin-content-types.md](../../../docs/admin-content-types.md), [docs/content-model.md](../../../docs/content-model.md) and [docs/admin-data-table.md](../../../docs/admin-data-table.md); [docs/e2e-testing.md](../../../docs/e2e-testing.md) — if new limits appear.

## Risks / Trade-offs

- [The slug of a type may coincide with a node slug or a service path (`admin`, `login`)] → there is no routing by slug yet; the conflict check and reservation are in the change with the public route (a Non-Goal).
- [`key` does not change, a mistake in the key cannot be fixed] → a hint next to the field; after a mistake the type can be deleted and created again, if it is empty.
- [Deleting a type without nodes still destroys its fields] → the confirmation dialog names the type; deletion with nodes is forbidden.
- [The ban on deletion only in the controller: other paths may delete nodes by cascade] → this is already the model's behaviour under the current `content-model` specification; we do not plan to change it here.
- [Changing the parent in `update` may create a cycle] → exclusion of itself and its descendants in the form, a check in `UpdateContentTypeRequest`, and the model's cycle check as the last barrier.
- [Duplication of rules in the `FormRequest` and the model] → shared format constants, Feature tests on both paths.
- [Removing `kind` from the list hides the existing `page`/`block`] → expected; their pages are separate changes.

## Migration Plan

`docker compose exec app php artisan migrate`; rollback — `migrate:rollback --step=1`. The data does not change; existing types get `slug = NULL`.
