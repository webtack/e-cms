# Design

## Context

See `proposal.md` (Why). The current state that determines the approach:

- The originals lie in the root of the disk of the profile `image` (`public`) as `{uuid}.{ext}`; `public/storage` is a symlink to `storage/app/public`, the URL of the disk is `APP_URL/storage`. `FileStorage::url()`/`urlForValue()` build the URL from the disk.
- The templates of the theme receive a **ready URL** of the image (`present()` of the type `image`, `$meta['image']`, `$logoUrl`), and not a `File`; therefore the helper must work from the URL, without the DB.
- `ImageResizer::resize($path, $mime, $maxW, $maxH)` already scales proportionally without enlargement, applies the EXIF, skips the animated GIF/WebP and returns `null` when no change is needed; for the styles its calculation of the size and the detection of the animation are reused, and the composition with the blurred background is added by a new method.
- There is no access to the configuration of the web server on the hosting. But both `public/.htaccess` (Apache) and `docker/nginx/default.conf` (`try_files $uri … /index.php`) by default give the request of a non-existent file to the front controller — this is the only requirement of the environment.
- The description of the file storage: `docs/file-storage.md`; the media library: `docs/media-library.md`; the templates of the theme: `docs/theme-templates.md`. The new document — `docs/image-styles.md`.

## Goals / Non-Goals

**Goals:**
- A helper without I/O that returns the address of a style; the preset `thumb` is ready right after the upload, the rest is created on request; it works without the rules of the web server.
- A style with two sides always gives an image of exactly the set size, without cropping the original.
- Arbitrary sizes without the possibility for a third party to load the server with sizes.

**Non-Goals:**
- Cropping, `srcset`, a change of format, watermarks, a queue, mass generation in advance.
- Moving the templates of `default` to the helper; other styles in the admin besides `thumb`; the details of the file in the media library and the screenshot of YouTube.
- Styles for the files outside the profile `image` (other disks).

## Decisions

**1. The address and the file: `{disk}/styles/{style}/{uuid}.{ext}`.** The directory by the requirement of the owner; the `uuid` is the same as the original's, the extension — by the format of the style (see the decision about the format), so the helper inserts the segment before the file name and changes the extension deterministically, without I/O. The alternative — a suffix in the name (`{uuid}--thumb.jpg`) was rejected: the requirement of the directories `styles/{name}`, and the deletion/clearing of a style = the deletion of a directory.

**2. `thumb` at the upload, the rest lazily through a Laravel route.** The preset with the mark `upload` in the configuration `FileStorage::store()` creates it right after the writing of the original (in the same request), by the same algorithm as the lazy one, so the admin always has a ready thumbnail. A failure of the creation (an exception) is caught and logged, the upload is not rejected: the preset will be created lazily by the route. For everything else — arbitrary sizes, presets without `upload`, files uploaded before this change, and after `image-styles:flush` — the lazy creation below works.

**Lazily through the Laravel route `GET {URL path of the disk}/styles/{style}/{file}`.** When the file already lies on the disk, the web server gives it statically and the request does not reach PHP; when it does not exist — the standard fallback (`.htaccess`, `try_files`) gives the request to Laravel. The path of the route is taken from the URL of the disk of the profile `image` (`parse_url(Storage::disk(...)->url('styles'), PHP_URL_PATH)`), not hard-coded. The controller: validates `file` by `FileValue::PATTERN`, parses and checks the style and the signature, finds the original by `uuid` (iterates over the allowed extensions of the profile; the extension of the requested file must match `ImageStyles::extension()` of the found original, otherwise 404), calls `ImageResizer`, writes the result (atomically: writing to a temporary name and renaming, so that parallel requests do not give an unfinished file), gives the response. When the processing is not needed (animation), the contents of the original is copied into the file of the style: the next requests are static, and the helper does not need to know whether the processing is needed. An error of decoding → 404 and nothing is written. The alternative — the generation at the upload: requires a migration of the old files, and the helper would not know whether the file exists (it would need a request to the DB or the disk).

**3. The parsing of a style — `App\Files\ImageStyles`.** The style `thumb` is searched in `config('files.styles.presets')` (`['thumb' => ['width' => 200, 'height' => 200]]`, the values from `.env`), otherwise it matches `^(\d+)?x(\d+)?$` (only the Latin `x`, case-insensitive; the capital one is normalized to the lower case), at least one side is required, each one within `1..files.styles.max_dimension` (4096). The normalized name `{w}x{h}`, `{w}x`, `x{h}` — the name of the directory. The name of a preset must not match this format (it is checked when reading the configuration; a violation — an exception).

**The composition of a style with two sides (`ImageResizer::fit()`).** `scale = min(W/w, H/h)` **without the limit 1**: a smaller original is enlarged (the styles differ from the upload, which does not enlarge); `fg` = the original, scaled by this coefficient, so it always touches the canvas by at least one side. If `fg` is exactly W×H — it is an ordinary resize. Otherwise a canvas W×H is built: the background is the same original, scaled «to cover» (cover, the excess is cropped in the centre), blurred (`blur`, the strength `files.styles.blur`, by default 30; the background is built from a reduced copy and then stretched, because blurring is cheaper this way than a full-size one), on top, in the centre, `fg`. If the image has transparent pixels, there is no background: the canvas is transparent, `fg` stands in the centre. The presence of transparency is determined by the actual pixels (the alpha channel is used), not by the format of the file: a PNG without transparency gets the background. For the check the native `Imagick` through the driver of Intervention is used. A style with one side — `scale` by this side (with the allowed enlargement), without the background. Alternatives: a monochrome background, crop (the original must stay visible whole), a blurred background under the transparent areas (gives a dirty «halo» around logos and PNG illustrations).

**The format of the file of a style (`files.styles.format`, `.env` `FILES_STYLE_FORMAT`).** `webp` (by default) or `original`. In the mode `webp` the JPEG, PNG and WebP originals are served as WebP with the quality `files.image.quality.webp` (WebP is smaller than JPEG, supports transparency, is read by all modern browsers), the extension of the file of the style — `webp`. GIF originals remain GIF in both modes: the helper without I/O does not know whether a GIF is animated, and the animation cannot be converted, so the extension must be predictable. An animated WebP original is copied as it is under the name `{uuid}.webp`. In the mode `original` the extension matches the original. An unknown value of the setting — an exception when reading the configuration. The signature: `ImageStyles::extension(string $originalExt): string`.

**4. The signature of arbitrary sizes — `itok` = the first 16 hex characters of `hash_hmac('sha256', "{style}|{file}", APP_KEY)`.** Without it anyone could request thousands of sizes and fill the disk/CPU. The helper knows the key and adds the token; the presets are not signed, because their number is finite. The token lies in the query: the web server ignores the query for a static file, and Laravel checks with `hash_equals`. The token is bound to the style and to the file name, but not to the user and has no expiry (the goal is to limit the list of sizes, not to hide the file). Alternatives: a signed URL of Laravel (an expiry, a long signature, depends on the full URL with the host) — not suitable: the address must be stable and cacheable; a whitelist of sizes — contradicts the requirement of arbitrary values.

**5. The helper `image_style(?string $url, string $style): ?string`.** A global function, connected through `autoload.files` in `composer.json` (the file `app/helpers.php`), and it delegates to `ImageStyles::url()`. The algorithm without I/O: `null`/empty → `null`; if the file name (`basename` of the path without the query) does not match `FileValue::PATTERN`, or the style is incorrect — return the input without changes; the value `{uuid}.{ext}` without `/` is converted into the URL of the disk of the profile through `FileStorage::urlForValue`; otherwise insert `styles/{style}/` before the file name into the saved beginning of the URL (the scheme, the host, the directory), replace the extension by `ImageStyles::extension()` and add `?itok=` for an arbitrary size (the signature is computed from the name of the file of the style, with the new extension). For an original that lies not in the storage of the profile `image` (another directory), the address will have the wrong directory — this gives 404 from the route: acceptable, because the field `image` always writes to the disk of the profile `image`.

**6. The deletion.** `FileStorage::delete()` after the deletion of the original calls `ImageStyles::forget($disk, $path)`: for each directory from `Storage::disk($disk)->directories('styles')` it deletes all files `{directory}/{uuid}.*` (the extension of the style may differ from the original one); a missing one is not an error. The order «the row first (the FK may refuse), the disk then» is kept, so a refused deletion does not touch the styles.

**7. The command `image-styles:flush {style?}`.** Deletes `styles/{style}` or all of `styles` on the disk of the profile `image` (`deleteDirectory`). After a change of the size of a preset the styles would otherwise remain old. It deletes nothing except `styles/`; the name of the style passes the same check as in the route, so that `..` does not leave the directory.

**8. The media library.** `MediaController::row()` returns in `preview` `image_style($this->storage->url($file), 'thumb')` for images; the details (`url`) remain the original. The column Preview in `Pages/Admin/Media/Index.tsx` becomes `<a href={original} target="_blank" rel="noopener noreferrer">` with `<img src={preview} className="cursor-pointer …">`; the row receives the address of the original (`url`, `$this->storage->url($file)`) together with `preview`. The document remains an icon without a link.

**9. `thumb` in the list of records and in `FileUpload`.** The data of the file for the client receives the field `preview`: the address of the style `thumb` for `image/*` (through `image_style()`), otherwise `null`. The sources: the response of the upload `FileController`, the collection of the known files `ContentNodeController::fileInfo` (the field `files`), `TermController`, `MenuItemController`, `SiteSettingsController`; the cell `image` in the list (`ContentNodeController::item`) gives `Arr::only($file, ['url', 'name', 'preview'])`. The type `ImageFile`/`UploadedFile` on the client receives `preview: string | null`; the client assemblies of the value (`TermForm`, `MenuItemForm`, `NodeFieldInput`) copy it from the object of the file. The components show `preview ?? url` (a fallback when `preview` is absent, e.g. in old data), and the link always leads to the `url` of the original. The cell of the list is already a link, to it only `cursor-pointer` and `thumb` are added; in `FileUpload` the bare `<img>` is wrapped in `<a target="_blank" rel="noopener noreferrer">`. The alternative — the client itself assembles the address of `thumb` — was rejected: the signature and the format live on the server.

## Risks / Trade-offs

- [The first visitor waits for the generation] → the thumbnails are small, `ImageResizer` is fast; the result is cached on the disk forever.
- [Parallel first requests generate one file twice] → an atomic writing (a temporary name + renaming), the result is the same.
- [The directory of styles grows, excess arbitrary sizes] → the signed sizes are limited by what is set in the templates; `image-styles:flush` clears; the limit of the side.
- [The signature depends on `APP_KEY`] → after a change of the key the old arbitrary addresses give 404 for the files not yet created; the created files are served statically. The helper forms new addresses at the next rendering.
- [An environment where the front controller does not intercept non-existent files] → the requirement of the standard setup of Laravel (Apache `.htaccess`, nginx `try_files`) is described in `docs/image-styles.md`; without it the route will not work.
- [The copy of the original in `styles/` for the animation duplicates the bytes] → accepted: simplicity and static serving matter more than the space.
- [Blurring is more expensive than a simple resize] → the background is built from a reduced copy; the result is cached; `thumb` is created at the upload, not during the viewing.
- [Enlarging a small original gives a soft image] → the choice of the owner; a style does not enlarge beyond `max_dimension`, and the uploads of the originals do not change.
- [Determining the transparency is more expensive than checking the format] → it is done once per file at the creation of the style; the result is cached.
- [WebP in the mode `webp` will not open in very old browsers] → the mode `original` in the setting; GIF is not converted.
- [The creation of `thumb` at the upload lengthens the upload response] → the thumbnail is small; a failure does not reject the upload.

## Migration Plan

There are no DB migrations, the existing files do not change. Deployment: update the code and `composer dump-autoload`, if needed add `FILES_STYLE_*` to `.env`. Rollback — remove the code; the `styles/` directories can be deleted manually or by `image-styles:flush`.
