# Design

## Context

Модель `ContentField` сама валідує себе в `saving` (`assertValid`): формат `key`, `name`, зареєстрований `type`, незмінність `key`/`content_type`, заборона зміни типу поля зі значеннями та заборона змін `key`/`type`/`is_multiple`/`is_required` системного поля; `deleting` не дає видалити системне поле (див. [docs/content-model.md](../../../docs/content-model.md)). Значення полів лежать у `content_values_*` з каскадним зовнішнім ключем на `content_fields`, тож видалення поля видаляє його значення. Реєстр типів (`FieldTypeRegistry`) дає ключі типів і таблицю значень кожного.

Сторінка типів: `Admin\ContentTypeController` з прив'язкою `{contentType}` за `key` лише для виду `content` ([docs/admin-content-types.md](../../../docs/admin-content-types.md)); меню рядка — `ContentTypeRowActions` з неактивним пунктом «Поля». Клієнтська `DataTable` (`mode="client"`, `rows`) уже існує, фільтри вмикаються лише пропом `filterable` ([docs/admin-data-table.md](../../../docs/admin-data-table.md)). Мотивацію див. у proposal.md.

## Goals / Non-Goals

**Goals:**
- Керування полями типу з адмінки з тими самими гарантіями, що й у моделі, і помилками біля полів форми.
- Таблиця полів у клієнтському режимі без фільтрів, за зразком сторінки типів.
- Зміна порядку полів перетягуванням (мишею й клавіатурою) із збереженням на сервері; загальна можливість `DataTable`, а не одноразове рішення сторінки.

**Non-Goals:**
- Серверна пагінація полів, редагування `settings`, поля для `page`/`block`.
- Зміна моделі `ContentField`, міграції; перетягування в серверному режимі `DataTable` і між сторінками пагінації.

## Decisions

1. **Маршрути вкладені під тип.** `GET /admin/content-types/{contentType}/fields` (`index`), `.../fields/create`, `POST .../fields` (`store`), `GET .../fields/{field}/edit`, `PUT .../fields/{field}` (`update`), `DELETE .../fields/{field}` (`destroy`), `PUT .../fields/order` (`reorder`, оголошується перед `{field}`-маршрутами, щоб `order` не прив'язувався як ключ поля); імена `admin.content-types.fields.*`. `{contentType}` уже прив'язаний лише до виду `content` (інші дають 404). `{field}` прив'язується явним `Route::bind('field', …)`, що шукає поле за парою (`content_type` з вже розв'язаного параметра, `key`) і повертає 404 для чужого чи відсутнього ключа. Альтернатива — прив'язка за числовим `id`: суперечить проєктній угоді, де сутності адресуються ключем.
2. **Окремий `ContentFieldController`.** Лишається поруч із `ContentTypeController`, не розростає його. Методи: `index`, `create`, `store`, `edit`, `update`, `destroy`, `reorder`.
3. **Список — клієнтська таблиця, без `TablePage`.** `index` повертає `fields` — масив усіх полів типу (`$type->fields`, вже впорядковані `weight`, `id`) з рядками `{key, name, type, is_multiple, is_required, is_translatable, is_system, weight, has_values}`. Сторінка відображає `<DataTable mode="client" rows={fields} …>` без пропа `filterable`, тож кнопки фільтрів немає. Порядок за замовчуванням — порядок масиву (клієнтський рушій без `sort` його зберігає). Серверна пагінація не потрібна: полів у типі десятки. `has_values` потрібен діалогу видалення й формі редагування; його дає один `exists` на таблицю значень типу поля (за `registry->get($type)->table()`), згрупований по типу, щоб не було запиту на кожен рядок: для кожної використаної таблиці одним запитом беруться пари `field_key` з `distinct`.
4. **Колонки.** `name` (з приміткою «Системне» під назвою, `hideable: false`), `key` (`hideable: false`), `type`, `is_multiple`, `is_required`, `is_translatable` (тип `boolean`, `cell` виводить «Так»/«Ні»), `weight` (`number`). Пошук — за `text`-колонками (назва, ключ, тип).
5. **Форма — спільний `ContentFieldForm`** (режими `create`/`edit`, `useForm`, за зразком `ContentTypeForm`): ключ (у `edit` — `readOnly`), назва, `Select` типу (опції — `typeOptions` з реєстру), три прапорці (shadcn `Checkbox`; додати компонент, якщо його ще немає в `Components/ui`), вага (`type="number"`). У `edit` блокуються: для системного поля — тип, «множинне», «обов'язкове»; для поля з `has_values` — тип. Заблоковане поле в запиті не надсилається значущим: сервер у будь-якому разі перевіряє.
6. **Ключ і прапорці з запиту.** `StoreContentFieldRequest`: `key` (required, `KEY_PATTERN`, max:64, `Rule::unique('content_fields','key')->where('content_type', $type->key)`), `name` (required, max:255), `type` (`Rule::in(registry->keys())`), `is_multiple`/`is_required`/`is_translatable` (`boolean`), `weight` (`integer`, 0–65535). `is_system` не входить у правила, тож відкидається, а `store` викликає `$type->fields()->create(...)` — `content_type` задає зв'язок. `UpdateContentFieldRequest` використовує ті самі спільні правила без `key`. Правила дублюють модельні навмисно (помилки по полях; модель — останній бар'єр), спільна частина — статичний метод у `Store…Request`, як у типах.
7. **Захист системного поля й полів зі значеннями — через модель.** `update` викликає `$field->update($validated)`; `ValidationException` моделі (зміна типу поля зі значеннями, заборонені зміни системного поля) перетворюється Laravel на редірект назад з помилками біля поля, тож окремої логіки в контролері немає. `destroy` для `is_system` і для поля з `has_values` повертає `back()->with('error', …)` до виклику `delete()` (системне — щоб не покладатися на виняток із події `deleting`; поле зі значеннями — бо БД каскадно стерла б значення, тож заборона живе в адмінці, як для типу з вузлами, а не в моделі); інакше `delete()` і редірект на список із `success`. Прапорці заблоковані в UI лише як зручність.
8. **Діалог видалення.** За зразком `ContentTypeRowActions`: `ContentFieldRowActions` із `AlertDialog` (компонент уже є); стан діалогу в батьківському компоненті. Для `has_values` діалог показує причину («спочатку видаліть значення поля») і не має кнопки підтвердження, як `ContentTypeRowActions` для типу з вузлами. Для `is_system` пункт «Видалити» `disabled`.
9. **Вага за замовчуванням.** `create` віддає `defaultWeight = max(weight) + 1` (якщо полів немає — 0). Альтернатива — автопризначення на сервері, коли поле порожнє: форма показує вагу явно, що простіше й передбачуваніше.
10. **Підпис типу в таблиці й формі** — ключ типу з реєстру (`string`, `integer`, …) як є, без перекладу: ключі технічні, і окремих локалізованих назв типів у системі поки немає.
11. **Навігація.** `ContentTypeRowActions`: пункт «Поля» — `DropdownMenuItem asChild` з `Link` на `/admin/content-types/{key}/fields`. У `navigation.ts` у `patternTitles` додаються шаблони для `…/fields` («Fields»), `…/fields/create` («Create field»), `…/fields/*/edit` («Edit field»); крихти будуються за наявним правилом «Admin → Content Types → заголовок». Посилання назад до списку типів — у самій сторінці.
12. **Документація.** Новий [docs/admin-content-fields.md](../../../docs/admin-content-fields.md) (маршрути, таблиця, форма, обмеження); оновити [docs/admin-data-table.md](../../../docs/admin-data-table.md) (проп `reorder`, слот `rowHandle`), [docs/admin-content-types.md](../../../docs/admin-content-types.md) (меню рядка), [docs/content-model.md](../../../docs/content-model.md) (посилання на адмін-сторінку полів) і [docs/README.md](../../../docs/README.md).
13. **Перетягування — можливість `DataTable` (`reorder`).** Необов'язковий проп `reorder?: { onReorder(orderedIds: string[]): void }` лише в клієнтському режимі (типи `ClientProps`). Із ним `DataTableView` обгортає тіло таблиці в `DndContext` + `SortableContext` (`@dnd-kit/core`, `@dnd-kit/sortable`; `PointerSensor` і `KeyboardSensor` із `sortableKeyboardCoordinates`), а `DataTableRow` стає sortable-рядком і через наявний слот `rowHandle` виводить ручку (`GripVertical`, `aria-label` з перекладу). Без пропа розмітка й залежності вибору не змінюються. Альтернативи: окремий рядок лише на сторінці полів (дублював би розмітку таблиці й розійшовся б з нею); HTML5 drag-and-drop без бібліотеки (немає клавіатури й доступності).
14. **Коли ручки активні.** Лише коли `state.search === ''`, `state.sort === null` і `meta.total <= state.perPage` (весь список на одній сторінці). Інакше ручки `disabled` з підказкою (`title`). Порядок після `onReorder` тримає сама таблиця: клієнтський стан отримує новий масив `rows`, тож без запиту видно результат; у `Index.tsx` сторінка зберігає локальну копію `fields`, оновлює її оптимістично й відкочує при помилці.
15. **Збереження порядку.** `ReorderContentFieldsRequest` приймає `order` — масив рядків; правила: `required|array`, елементи `string|distinct`; перевірка набору в `after`-хуку: множина ключів дорівнює множині ключів полів типу. `reorder` у транзакції виставляє `weight = index` оновленням потрібних рядків напряму (`ContentField::query()->where(...)->update(...)`), без `saving`-перевірок моделі, бо змінюється лише вага, а повна перевірка ключів уже зроблена; відповідь — редірект назад (`router.put` з `preserveScroll`, `only: ['fields']`). Помилка валідації повертається у `errors.order`, і сторінка відкочує порядок та показує її тостом. Поле `weight` у формі лишається, з підказкою, що порядок зручніше міняти перетягуванням.

## Risks / Trade-offs

- [Поле зі значеннями не можна видалити, доки значення не стерто] → свідомий вибір: діалог називає причину; видалення значень окремою дією поза цією зміною.
- [Паралельне додавання/видалення поля іншим користувачем зробить набір ключів у `order` застарілим] → сервер відхиляє неповний набір, сторінка відкочує порядок і показує помилку; перезавантаження дає свіжий список.
- [Нова залежність `@dnd-kit`] → вона лише для `reorder`; без нього таблиця її не використовує.
- [Зміна «множинне»/«обов'язкове» поля, що вже має значення, може зробити наявні вузли невалідними] → модель цього не забороняє, і ця зміна її не змінює; поведінка лишається за моделлю, у UI — без додаткових блокувань.
- [`has_values` додає запити на сторінці списку] → один запит на використану таблицю значень, а не на поле.
- [Клієнтська таблиця не масштабується на сотні полів] → для типів контенту це нереалістично; за потреби перейти на серверний режим без змін форми.
