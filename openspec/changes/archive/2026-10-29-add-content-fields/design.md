# Design

## Context

The `ContentField` model validates itself in `saving` (`assertValid`): the format of `key` and `name`, a registered `type`, immutability of `key`/`content_type`, a ban on changing the type of a field that has values, and a ban on changing `key`/`type`/`is_multiple`/`is_required` of a system field; `deleting` does not allow deleting a system field (see [docs/content-model.md](../../../docs/content-model.md)). Field values live in `content_values_*` with a cascading foreign key to `content_fields`, so deleting a field deletes its values. The type registry (`FieldTypeRegistry`) provides the type keys and the value table of each.

The types page: `Admin\ContentTypeController` with the `{contentType}` binding by `key` only for the `content` kind ([docs/admin-content-types.md](../../../docs/admin-content-types.md)); the row menu is `ContentTypeRowActions` with an inactive "Fields" item. The client `DataTable` (`mode="client"`, `rows`) already exists; filters are enabled only by the `filterable` prop ([docs/admin-data-table.md](../../../docs/admin-data-table.md)). The motivation is in proposal.md.

## Goals / Non-Goals

**Goals:**
- Managing the fields of a type from the admin with the same guarantees as in the model, and errors next to the form fields.
- A fields table in client mode without filters, modelled on the types page.
- Changing the order of fields by dragging (with the mouse and the keyboard) with saving on the server; a general capability of `DataTable`, not a one-off solution of the page.

**Non-Goals:**
- Server-side pagination of fields, editing of `settings`, fields for `page`/`block`.
- Changing the `ContentField` model, migrations; dragging in server mode of `DataTable` and between pagination pages.

## Decisions

1. **Routes nested under the type.** `GET /admin/content-types/{contentType}/fields` (`index`), `.../fields/create`, `POST .../fields` (`store`), `GET .../fields/{field}/edit`, `PUT .../fields/{field}` (`update`), `DELETE .../fields/{field}` (`destroy`), `PUT .../fields/order` (`reorder`, declared before the `{field}` routes so that `order` is not bound as a field key); names `admin.content-types.fields.*`. `{contentType}` is already bound only to the `content` kind (others give 404). `{field}` is bound by an explicit `Route::bind('field', …)` that looks up the field by the pair (`content_type` from the already resolved parameter, `key`) and returns 404 for a foreign or missing key. Alternative — binding by numeric `id`: contradicts the project convention, where entities are addressed by key.
2. **A separate `ContentFieldController`.** It stays next to `ContentTypeController` and does not bloat it. Methods: `index`, `create`, `store`, `edit`, `update`, `destroy`, `reorder`.
3. **The list is a client table, without `TablePage`.** `index` returns `fields` — an array of all fields of the type (`$type->fields`, already ordered by `weight`, `id`) with rows `{key, name, type, is_multiple, is_required, is_translatable, is_system, weight, has_values}`. The page renders `<DataTable mode="client" rows={fields} …>` without the `filterable` prop, so there is no filter button. The default order is the array order (the client engine keeps it when there is no `sort`). Server pagination is not needed: a type has dozens of fields. `has_values` is needed by the delete dialog and the edit form; it is provided by one `exists` per value table of the type's field (via `registry->get($type)->table()`), grouped by type so that there is no query per row: for each used table, the pairs `field_key` are taken in one query with `distinct`.
4. **Columns.** `name` (with a "System" note under the name, `hideable: false`), `key` (`hideable: false`), `type`, `is_multiple`, `is_required`, `is_translatable` (type `boolean`, `cell` renders "Yes"/"No"), `weight` (`number`). Search — over the `text` columns (name, key, type).
5. **Form — a shared `ContentFieldForm`** (modes `create`/`edit`, `useForm`, modelled on `ContentTypeForm`): key (in `edit` — `readOnly`), name, a `Select` for the type (options — `typeOptions` from the registry), three checkboxes (shadcn `Checkbox`; add the component if it is not yet in `Components/ui`), weight (`type="number"`). In `edit` these are blocked: for a system field — the type, "multiple", "required"; for a field with `has_values` — the type. A blocked field is not sent meaningfully in the request: the server checks anyway.
6. **Key and flags from the request.** `StoreContentFieldRequest`: `key` (required, `KEY_PATTERN`, max:64, `Rule::unique('content_fields','key')->where('content_type', $type->key)`), `name` (required, max:255), `type` (`Rule::in(registry->keys())`), `is_multiple`/`is_required`/`is_translatable` (`boolean`), `weight` (`integer`, 0–65535). `is_system` is not part of the rules, so it is discarded, and `store` calls `$type->fields()->create(...)` — the relation sets `content_type`. `UpdateContentFieldRequest` uses the same shared rules without `key`. The rules deliberately duplicate the model's (field-level errors; the model is the last barrier), the shared part is a static method in `Store…Request`, as for types.
7. **Protection of a system field and of fields with values — via the model.** `update` calls `$field->update($validated)`; the model's `ValidationException` (changing the type of a field with values, forbidden changes of a system field) is turned by Laravel into a redirect back with errors next to the field, so there is no separate logic in the controller. `destroy` for `is_system` and for a field with `has_values` returns `back()->with('error', …)` before calling `delete()` (for a system field — so as not to rely on an exception from the `deleting` event; for a field with values — because the DB would cascade-delete the values, so the ban lives in the admin, as for a type with nodes, not in the model); otherwise `delete()` and a redirect to the list with `success`. The flags are blocked in the UI only as a convenience.
8. **Delete dialog.** Modelled on `ContentTypeRowActions`: `ContentFieldRowActions` with an `AlertDialog` (the component already exists); the dialog state is in the parent component. For `has_values` the dialog shows the reason ("delete the field's values first") and has no confirm button, like `ContentTypeRowActions` for a type with nodes. For `is_system` the "Delete" item is `disabled`.
9. **Default weight.** `create` provides `defaultWeight = max(weight) + 1` (0 if there are no fields). Alternative — automatic assignment on the server when the field is empty: the form shows the weight explicitly, which is simpler and more predictable.
10. **The type label in the table and the form** — the registry type key (`string`, `integer`, …) as is, without translation: the keys are technical, and there are no separate localized type names in the system yet.
11. **Navigation.** `ContentTypeRowActions`: the "Fields" item — `DropdownMenuItem asChild` with a `Link` to `/admin/content-types/{key}/fields`. In `navigation.ts`, `patternTitles` gets templates for `…/fields` ("Fields"), `…/fields/create` ("Create field"), `…/fields/*/edit` ("Edit field"); breadcrumbs are built by the existing rule "Admin → Content Types → title". The link back to the types list is on the page itself.
12. **Documentation.** A new [docs/admin-content-fields.md](../../../docs/admin-content-fields.md) (routes, table, form, limits); update [docs/admin-data-table.md](../../../docs/admin-data-table.md) (the `reorder` prop, the `rowHandle` slot), [docs/admin-content-types.md](../../../docs/admin-content-types.md) (the row menu), [docs/content-model.md](../../../docs/content-model.md) (a link to the admin page of fields) and [docs/README.md](../../../docs/README.md).
13. **Dragging — a `DataTable` capability (`reorder`).** An optional prop `reorder?: { onReorder(orderedIds: string[]): void }` only in client mode (types `ClientProps`). With it, `DataTableView` wraps the table body in `DndContext` + `SortableContext` (`@dnd-kit/core`, `@dnd-kit/sortable`; `PointerSensor` and `KeyboardSensor` with `sortableKeyboardCoordinates`), and `DataTableRow` becomes a sortable row and renders a handle (`GripVertical`, `aria-label` from a translation) through the existing `rowHandle` slot. Without the prop the markup and the choice of dependencies do not change. Alternatives: a separate row only on the fields page (would duplicate the table markup and drift from it); HTML5 drag-and-drop without a library (no keyboard support and no accessibility).
14. **When the handles are active.** Only when `state.search === ''`, `state.sort === null` and `meta.total <= state.perPage` (the whole list on one page). Otherwise the handles are `disabled` with a hint (`title`). The order after `onReorder` is held by the table itself: the client state receives a new `rows` array, so the result is visible without a request; in `Index.tsx` the page keeps a local copy of `fields`, updates it optimistically and rolls back on error.
15. **Saving the order.** `ReorderContentFieldsRequest` accepts `order` — an array of strings; the rules: `required|array`, the elements `string|distinct`; a check of the set in an `after` hook: the set of keys equals the set of keys of the type's fields. `reorder` in a transaction sets `weight = index` by updating the rows directly (`ContentField::query()->where(...)->update(...)`), without the model's `saving` checks, because only the weight changes and the full key check is already done; the response is a redirect back (`router.put` with `preserveScroll`, `only: ['fields']`). A validation error is returned in `errors.order`, and the page rolls back the order and shows it as a toast. The `weight` field stays in the form, with a hint that the order is more convenient to change by dragging.

## Risks / Trade-offs

- [A field with values cannot be deleted until the values are erased] → a deliberate choice: the dialog names the reason; deleting the values with a separate action is outside this change.
- [A parallel addition/deletion of a field by another user makes the set of keys in `order` stale] → the server rejects an incomplete set, the page rolls back the order and shows an error; a reload gives a fresh list.
- [A new dependency `@dnd-kit`] → it is used only for `reorder`; without it the table does not use it.
- [Changing "multiple"/"required" of a field that already has values may make existing nodes invalid] → the model does not forbid this, and this change does not alter it; the behaviour stays with the model, with no additional blocks in the UI.
- [`has_values` adds queries on the list page] → one query per used value table, not per field.
- [The client table does not scale to hundreds of fields] → for content types this is unrealistic; if needed, switch to server mode without changing the form.
