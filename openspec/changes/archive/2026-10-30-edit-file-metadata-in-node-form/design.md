# Design

## Context

Форма запису — `ContentNodeForm.tsx`; файлові поля малює `NodeFieldInput` (одиночне) і `NodeFieldList` (множинне) через віджет `FileUpload`. Сторінка `Edit` отримує проп `files` (`ContentNodeController::fileInfo()`: ім'я, mime, розмір, url за значенням `{uuid}.{ext}`); форма запам'ятовує їх у стані `known`. Збереження — `PUT …/nodes/{node}` (`UpdateContentNodeRequest` → `ContentNodeController::update()` → `ContentValueWriter::write()` у транзакції). Ім'я файлу живе в `media.original_name`; опису немає. `ContentField` теж не має опису; поля передаються формі запису через `ContentNodeController::formFields()`, а форми поля — `ContentFieldForm.tsx` (правила спільні в `StoreContentFieldRequest::sharedRules()`). Файл у `media` спільний для всіх власників (`media_relations`). Описано в [`docs/admin-content-nodes.md`](../../../docs/admin-content-nodes.md), [`docs/file-storage.md`](../../../docs/file-storage.md), [`docs/media-library.md`](../../../docs/media-library.md), [`docs/admin-content-fields.md`](../../../docs/admin-content-fields.md).

## Goals / Non-Goals

**Goals:**
- Назва й опис файлу редагуються у формі редагування запису і зберігаються атомарно разом із записом.
- Прибрати «Додати елемент» у файлових множинних полях та хрестик блоку файлу в рядку множинного поля.

**Non-Goals:**
- Редагування метаданих у самій медіатеці; форматування (markdown/HTML) в описі поля.
- Зміна розширення, шляху чи вмісту файлу; перейменування файлу на диску.
- Права доступу: поки немає ролей, будь-який адміністратор, що редагує запис, змінює метадані файлу.

## Decisions

1. **Метадані їдуть у тому ж запиті збереження (`POST` створення чи `PUT` оновлення), а не окремим.** Форма додає ключ `file_meta`: `{ [uuid]: { name, description } }` для файлів, що є у значеннях форми. `update()` після `writer->write()` у тій самій `DB::transaction`, а `store()` — обгортає `ContentNodeCreator::create()` і застосування метаданих власною `DB::transaction` (вкладена транзакція creator-а стає savepoint) і оновлюють `media.original_name` / `description`. Рішення: одна кнопка «Зберегти», один тост, помилка валідації запису не лишає частково збережених метаданих (і навпаки). *Альтернатива:* `PATCH /admin/media/{uuid}` на blur — відкинуто: частковий стан (файл перейменовано, запис не збережено) і нові маршрути.
2. **Сервер змінює лише файли, що справді є у значеннях запису.** Застосування однакове для `store()` і `update()` (спільний метод). Сервер бере `fileUuids()` зі збережених значень файлових полів (`TracksFiles`) і застосовує метадані лише для перетину; чужі uuid мовчки ігноруються. Інакше будь-хто міг би перейменувати довільний файл, знаючи uuid. Файл, щойно завантажений у цій формі, теж є у значеннях, тож перетин його охоплює.
3. **Валідація в `StoreContentNodeRequest` і `UpdateContentNodeRequest` (спільні правила):** `file_meta` — `sometimes|array`; ключі — 32 символи `0-9a-f`; `file_meta.*.name` — `required|string|max:255`; `file_meta.*.description` — `nullable|string|max:2000`. Назва очищається так само, як при завантаженні (`basename`, без `\`, обрізання до 255). Порожній опис (`''`/пробіли) → `NULL`. Помилки адресуються ключем `file_meta.{uuid}.name`; форма показує їх під відповідним полем. Рядок із помилкою `values.*` і `file_meta.*` приходить разом, як і зараз.
4. **Стовпець `media.description`** — `text`, `nullable`, міграція `add_description_to_media_table`. `File` отримує `description` у `Fillable` і PHPDoc. `fileInfo()` та `MediaController::show()` віддають `description`; рядок таблиці медіатеки опис не показує.
5. **Віджет `FileUpload` лишається універсальним:** нові необов'язкові пропси `removable` (за замовчуванням `true`; `false` ховає хрестик «Видалити файл») і `details` (ReactNode, що малюється всередині блоку вибраного файлу). Демо-сторінка й інші споживачі не змінюються. Поля «Назва»/«Опис» будує `NodeFieldInput` і передає їх у `details`; вони є і в створенні, і в редагуванні.
6. **Стан метаданих у `ContentNodeForm`:** `useForm` отримує `file_meta`, ініціалізований з пропу `files` (ім'я/опис; у створенні порожній) для файлів, що вже в значеннях; для щойно завантаженого файлу запис додається при `rememberFile`. Надсилаються лише ті uuid, що лишилися у значеннях форми (заміна/видалення файлу прибирає його метадані із запиту). Змінювати `known` не потрібно — він лишається джерелом показу, `file_meta` — джерелом редагування.
7. **«Додати елемент»** ховається в `NodeFieldList` для `image`/`file`; нові елементи — лише зона множинного завантаження. Хрестик рядка («Видалити елемент») лишається, хрестик блоку файлу в рядку — `removable={false}`; в одиночному полі `removable` лишається `true`.
8. **Опис поля — `content_fields.description`** (`text`, `nullable`, міграція `add_description_to_content_fields_table`). Правило `description` (`nullable|string|max:1000`) додається в `StoreContentFieldRequest::sharedRules()`, тож його успадковує й форма редагування; порожній рядок → `NULL` (`ConvertEmptyStringsToNull` вже перетворює, пробіли обрізає `TrimStrings`). Системні поля можуть змінювати опис (він не входить у `SYSTEM_LOCKED`). `ContentFieldController` додає `description` у `only([...])` відповіді й у форму; `formFields()` додає `description` у `NodeField`. `ContentNodeForm` виводить його одразу під легендою (`text-sm text-muted-foreground`) для одиночних, множинних і булевих полів; без опису нічого не малюється. Опис — звичайний текст, виводиться як текст React (без HTML).

## Risks / Trade-offs

- [Спільність метаданих: перейменування у одному записі змінює назву у всіх, де файл використано] → прийнято свідомо (назва й опис — властивості файлу), зафіксовано у специфікації й документації.
- [Два адміністратори редагують один файл одночасно — виграє останній запис] → прийнятно, блокувань немає ні в інших полях.
- [Запит стає більшим на кількість файлів форми] → метадані невеликі; множинні поля обмежені розумними кількостями.
- [Без «Додати елемент» не додати порожній елемент у файловому полі] → не потрібно: порожній віджет не мав сенсу, завантаження додає елементи сама.

## Migration Plan

`docker compose exec app php artisan migrate` додає nullable-стовпець; наявні файли мають `description = NULL`. Відкат — `migrate:rollback` (стовпці видаляються разом з описами). Дані `original_name` не змінюються.
