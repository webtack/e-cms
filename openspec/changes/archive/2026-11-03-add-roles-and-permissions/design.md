# Design

## Context

Мотивація та перелік змін — у `proposal.md`, вимоги — у `specs/`. Поточний стан:

- Користувач (`User`) не має ролі; усі маршрути `/admin/*` стоять за `auth` + `verified`; policies і gates відсутні.
- Запис контенту має незмінного автора `content_nodes.user_id` (NOT NULL, `restrictOnDelete`), тож правило «свої записи» не потребує нових колонок. Файл має `media.user_id` (nullable, `nullOnDelete`).
- Маршрути типів і записів спільні для трьох видів і отримують `kind` із `defaults` маршруту; `Route::bind` вже відсікає чужий вид.
- Сторінки «Налаштування сайту» ще немає (пункт Settings у sidebar — макет), є лише сховище `AppSettings`.
- Стан компонентів описано в `docs/admin-auth.md`, `docs/admin-shell.md`, `docs/admin-content-nodes.md`, `docs/media-library.md`; нові компоненти документуються в `docs/access-control.md`, `docs/admin-users.md`, `docs/admin-roles.md`.

## Goals / Non-Goals

**Goals:**
- Один механізм перевірки прав для всіх розділів, що читається з коду й тестується.
- Матриця прав будується динамічно з наявних типів.
- Сервер завжди арбітр; клієнт лише ховає елементи.

**Non-Goals:**
- Кілька ролей на користувача, права на рівні окремого запису чи поля, окреме право «публікувати».
- Скидання пароля листом, самореєстрація, запрошення (адмін задає пароль сам).
- Логування дій користувачів (audit).
- Сторінка налаштувань сайту: право `settings.manage` визначається й зберігається, але точки застосування з'являться разом зі сторінкою.

## Decisions

**1. Схема даних.**
`roles(id, name unique, is_system bool)`, `role_permissions(role_id FK cascade, scope string, level string, unique(role_id, scope))`, `users.role_id` (FK `restrictOnDelete`, NOT NULL після бекфілу), `users.is_active` (default true).
`scope`: системні ключі `users`, `roles`, `menus`, `settings`, `taxonomy`, `types`; `node:{type_key}`; `media`. `level`: `allow` для системних, `own` | `any` для `node:*` і `media`. Відсутній рядок = `none`.
*Альтернатива:* JSON-колонка `roles.permissions` — простіше, але неможливо запитати «які ролі мають доступ до типу» і прибрати типи при видаленні. Рядки кращі. *Альтернатива:* `spatie/laravel-permission` — рівні `own/any` і динамічні `node:{type}` у ньому все одно довелося б робити вручну, тож залежність не виправдана.
`scope` для типу не FK (ключ типу незмінний); при видаленні типу рядки `node:{key}` видаляються в тій самій транзакції.

**2. Роль `admin`.**
Створюється міграцією (`is_system = true`) і не має рядків у `role_permissions`: сервіс перевірки трактує `is_system` як «усе дозволено, рівень `any` скрізь». Так нові типи автоматично доступні, а матриця `admin` лише для перегляду. Міграція призначає її всім наявним користувачам, потім робить `role_id` NOT NULL.

**3. Сервіс перевірки.**
Сервіс `AccessResolver` (на `User` — тонкі методи) вантажить права ролі одним запитом на запит і кешує в пам'яті екземпляра. Публічні операції: `can('users')`-подібна перевірка системного права, `level('node:article')`, `levelForMedia()`, `canEditAnyContent()` (є `own/any` хоча б на одному типі чи медіа).
Інтеграція з Laravel: `Gate::define` для системних прав і policies `ContentNodePolicy` та `MediaPolicy` (`viewAny`, `create`, `update`, `delete`; `update/delete` порівнюють `user_id` із рівнем `own`). Маршрути системних розділів захищаються middleware `can:…`, а записи й медіа — `$this->authorize(...)` у контролерах (там, де потрібна модель чи тип).
Файл без власника (`media.user_id = null`) доступний лише на рівні `any`.

**4. Типи, види й записи.**
Для записів перевірка бере тип із route-binding (`contentType`) і рівень `node:{key}`. Види `page`/`block` використовують ті самі рівні. Керування самими типами та їхніми полями (усі три види) — системне право `types`. Створення/зміна/видалення записів вимагає `own` чи `any`; перегляд списку теж (рівень `none` = 403).

**5. Активність користувача.**
Middleware `EnsureUserIsActive` у групі `web` після автентифікації: неактивного розлогінює, інвалідує сесію й перенаправляє на `/login`. `LoginRequest` відхиляє вхід неактивного з тим самим повідомленням про помилку. Окремого сховища сесій не потрібно — middleware спрацьовує на кожен запит.

**6. Захист останнього адміністратора.**
Перевірка в одному місці (метод на `User`/сервісі), що викликається з контролера користувачів і з зміни ролі: рахується кількість активних користувачів ролі `admin` у транзакції з блокуванням `lockForUpdate`, щоб паралельні запити не залишили нуль адмінів.

**7. Клієнт.**
`HandleInertiaRequests` додає в `auth.user` об'єкт `can`: системні булеві, мапа рівнів для типів і `media`. `navigation.ts`/`AppSidebar` фільтрують пункти за ним; кнопки зміни/видалення в списку запису враховують `own` (автор запису береться з уже переданих даних запису). Для цього список записів передає ознаку «можна змінювати» з сервера, а не обчислює її на клієнті, щоб правило було в одному місці.

**8. Допоміжні ендпойнти.**
`lookup/*` лишаються без перевірки прав (рішення власника продукту: «м'яко»). `files.store` і `youtube/lookup` — через `canEditAnyContent()`. `profile` і `dashboard` відкриті будь-якому активному користувачу.

**9. Користувачі.**
Створює адміністратор: ім'я, email, пароль, роль; `email_verified_at = now()` (листів верифікації немає). Видалення — лише без записів-автора; перевірка робиться наперед (запит `exists`), а FK `restrictOnDelete` лишається страховкою. Користувач не може змінити власну роль чи деактивувати себе.

## Risks / Trade-offs

- [Забуті маршрути без перевірки] → Feature-тест обходить усі маршрути `admin.*` і вимагає, щоб кожен (крім явного allow-list: dashboard, profile, lookup) повертав 403 для ролі без прав.
- [Користувач із правом `roles` фактично суперадмін, бо може дати собі будь-яке право] → припускається за моделлю; ризик зменшує те, що роль `admin` недоторкана, а право `roles` видається свідомо. Документувати в `docs/access-control.md`.
- [Рівні в `role_permissions` для видалених типів] → очищення при видаленні типу та перевірка в тесті; `scope` без відповідного типу ігнорується сервісом.
- [Додаткові запити на права] → один запит на запит, кеш в екземплярі.
- [Існуючі e2e-спеки логіняться адміністратором] → поведінка не змінюється, бо `admin` має всі права; повний прогін e2e не потрібен, але спеки sidebar/auth перевіряються окремо.

## Migration Plan

1. Міграція створює таблиці, додає `users.role_id` (nullable) і `users.is_active`, створює роль `admin`, призначає її всім наявним користувачам, потім робить `role_id` NOT NULL.
2. Сидер створює адміністратора вже з роллю `admin`.
3. Відкат: прибрати колонки та таблиці (дані ролей втрачаються).
