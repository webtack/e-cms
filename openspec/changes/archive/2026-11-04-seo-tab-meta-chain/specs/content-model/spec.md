# Spec Delta

## MODIFIED Requirements

### Requirement: Системні поля метаданих і розділу
Система SHALL створювати системні поля автоматично при створенні типу за переліком, який залежить від виду типу, і SHALL мати один перелік системних полів (ключ, тип значення, назва, види, власники значень, перекладність) як єдине джерело істини для створення, бекфілу, зарезервованих ключів і визначення власника поля. Усі системні поля метаданих і розділу SHALL бути необов'язковими, немножинними, перекладними та `is_system`; їх не можна видаляти, змінювати їхні `type`, `is_multiple`, `is_required` та ключ; назву, вагу, опис і налаштування змінювати дозволено.

Перелік:

| ключ | тип значення | `content` | `page` | `block` |
| --- | --- | --- | --- | --- |
| `meta_title` | «короткий текст» | запис і тип | запис і тип | немає |
| `meta_description` | «текст» | запис і тип | запис і тип | немає |
| `meta_image` | «зображення» | запис і тип | запис і тип | немає |
| `section_title` | «короткий текст» | тип | немає | немає |
| `section_description` | «форматований текст» | тип | немає | немає |
| `section_cover` | «зображення» | тип | немає | немає |

«Запис» означає, що поле має значення в записах цього типу; «тип» означає, що поле має значення самого типу. Поле, якого немає в колонці виду, для типів цього виду не створюється. Несистемне поле SHALL належати лише записам. Зміна власників не потребує нових полів: типи `page` уже мають `meta_*`.

#### Scenario: Тип контенту
- **WHEN** створюється тип виду `content`
- **THEN** він має поля `title`, `meta_title`, `meta_description`, `meta_image`, `section_title`, `section_description`, `section_cover`

#### Scenario: Тип сторінок
- **WHEN** створюється тип виду `page`
- **THEN** він має поля `title`, `meta_title`, `meta_description`, `meta_image` і не має полів `section_*`

#### Scenario: Тип блоків
- **WHEN** створюється тип виду `block`
- **THEN** він має лише поле `title`

#### Scenario: Заборонені зміни системного поля
- **WHEN** змінюється тип значення, множинність чи обов'язковість системного поля метаданих або воно видаляється
- **THEN** зміну відхилено, поле й значення лишаються

#### Scenario: Бекфіл наявних типів
- **WHEN** застосовується міграція до бази з наявними типами `content` і `page`
- **THEN** кожен тип отримує недостаючі системні поля за переліком свого виду, а наявні поля й значення не змінюються

#### Scenario: Конфлікт ключа при бекфілі
- **WHEN** наявний тип уже має користувацьке поле з ключем системного поля метаданих
- **THEN** міграція завершується помилкою з переліком конфліктних типів і ключів до будь-яких змін

### Requirement: Власники значень поля
Значення поля SHALL мати власника: запис або тип. Власників поля система SHALL визначати з переліку системних полів, а не зі стовпця: системне поле належить тим власникам, що вказані в переліку для виду його типу, будь-яке інше поле належить лише записам. Спроба записати значення поля власнику, якому воно не належить, SHALL відхилятися.

#### Scenario: Значення типу для поля запису
- **WHEN** записується значення типу для користувацького поля або для `title`
- **THEN** запис відхилено з помилкою валідації, значення не збережено

#### Scenario: Значення запису для поля розділу
- **WHEN** записується значення запису для `section_title`
- **THEN** запис відхилено з помилкою валідації

#### Scenario: Метаполе обох власників
- **WHEN** у типі виду `content` записується `meta_title` для запису й для самого типу
- **THEN** обидва значення збережено окремо й незалежно

#### Scenario: Метаполе типу сторінок
- **WHEN** у типі виду `page` записується `meta_description` для самого типу
- **THEN** значення збережено для типу й не змішується зі значеннями записів цього типу

#### Scenario: Метаполе типу блоків
- **WHEN** у типі виду `block` записується `meta_title` для самого типу
- **THEN** запис відхилено з помилкою валідації (поля в блока немає)
