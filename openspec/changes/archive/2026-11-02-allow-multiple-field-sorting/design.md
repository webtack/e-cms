# Design

## Context

Сортування (`ContentNodeQuery::applySort`) приєднує через `LEFT JOIN` рядок `weight = 0` одного немножинного поля; для множинного поля воно відхиляється з помилкою валідації. Таблиця записів в адмінці (`ContentNodeController::sortable()`, `listSettings`) має власний критерій: не множинне, не файлове (`instanceof AbstractFileFieldType`) і не `youtube` (за рядком ключа). Усі типи, зокрема файлові й `youtube`, зберігають значення в таблиці з колонкою `value` (`content_values_string` та інші), тож `LEFT JOIN` по ній технічно придатний для кожного; обмеження файлових типів потрібне лише адмінці, бо за іменем файлу чи URL змістовного порядку немає. Мотивація — у [proposal.md](proposal.md); опис вибірки — у [docs/content-querying.md](../../../docs/content-querying.md).

## Goals / Non-Goals

**Goals:**
- Одне правило ключа сортування для адмінки й сайту: перше значення (`weight = 0`), для множинного й немножинного поля.
- Прибрати обмеження за множинністю в контролері й вибірці; сортованість за типом лишається в адмінці.
- Зафіксувати, що фільтр однаково працює для множинного й немножинного поля (OR по значеннях), і додати оператор `in` (OR по переданих значеннях).

**Non-Goals:**
- Згортання значень множинного поля (`MIN`/`MAX`) і врахування фільтрів у ключі сортування.
- Зміна поєднання фільтрів (лишається AND), зміна пошуку, інші нові оператори; нові типи полів; сортування за кількома полями; метод `sortable()` у `FieldType`.
- Сортування за `published_at` не змінюється; slug і стан у таблиці адмінки лишаються несортованими (це не поля).

## Decisions

**1. Сортування за `weight = 0` для будь-якого поля.**
Існуючий `LEFT JOIN` рядка `weight = 0` (з `content_type`, `field_key`, `lang`) уже дає не більше одного рядка на запис, тож дублікатів у вибірці й лічильнику немає. Єдина зміна у вибірці — прибрати блок `if ($field->is_multiple) { throw … }`; перевірки типу не додаються (їх там і не було), тож вибірка сортує й за файловими полями та `youtube`. До порядку додається другорядний ключ за `title` (рішення 6): `ORDER BY (sort_value.value IS NULL), sort_value.value {напрямок}, (title_value.value IS NULL), title_value.value ASC, content_nodes.id`. Альтернативи — `MIN`/`MAX` зі згортанням і фільтрами, а також `FieldType::sortable()` для виключення файлових типів — відхилені як зайві для потреби.

**2. Адмінка не пропонує сортування за файловими полями й `youtube`.**
`ContentNodeController::sortable()` лишається, але втрачає умову `! $field->is_multiple`: `return ! $this->isFileField($field) && $field->type !== 'youtube';`. Колонки множинних полів стають `sortable: true`; колонки `file`, `image` і `youtube` лишаються `sortable: false`, а `sort` за ними в адресі ігнорується (`TableRequest`). `listSettings` зберігає `settings.list.sort`, якщо поле існує й `sortable()` для нього істинний (замість перевірки `! is_multiple`), тож посилання на файлове поле відкидається, як і колонка в таблиці.

**3. Службові колонки.**
`slug` і `status` — не поля, тому в `tableColumns` лишаються `sortable: false`; `published_at` — `true`. `TableRequest` продовжує ігнорувати `sort` для колонок із `sortable: false`.

**4. Фільтр не розрізняє множинні й немножинні поля.**
Поточний `EXISTS` по таблиці значень уже дає «хоча б одне значення відповідає»; логіка не змінюється, а правило записується у спеку. Кілька фільтрів по одному полю лишаються незалежними `EXISTS` (кожен може виконуватись іншим значенням запису); це описано окремим сценарієм. Фільтри й сортування навмисно не узгоджуються: фільтр дивиться на будь-яке значення, сортування — на перше.

**5. Оператор `in`.**
Значення — непорожній масив; кожен елемент перевіряється правилами типу поля (як для `eq`) і готується через `prepare`. У `filterValue` з'являється гілка `in` (за зразком `between`), у `valueCondition` — `whereIn("{table}.value", $значення)`. Оператор додається в `operators()` типів `string`, `text`, `richtext`, `integer`, `decimal`, `date`, `datetime`; `boolean` (два значення), `youtube` і файлові типи його не отримують. Альтернатива — OR між фільтрами (`match: any`) — відхилена: змінює семантику всіх фільтрів, а потреба «або/або» по одному полю покривається `in`.

**6. Другорядний порядок за `title`.**
Для явного сортування (за полем і за `published_at`) після основного ключа записи впорядковуються за `title`, далі за `id`. `title` — системне поле типу `string`, обов'язкове в мові `default`, немножинне, `weight = 0` ([content-model.md](../../../docs/content-model.md)), тож `LEFT JOIN` рядка `weight = 0` дає не більше одного рядка на запис. Напрямок другорядного ключа завжди `ASC` незалежно від напрямку основного. Мова — вказана в запиті; **fallback на `default` немає** (як і решта вибірки, [content-values.md](../../../docs/content-values.md)): запис без `title` у цій мові йде після записів із `title`, далі за `id`. Без явного сортування порядок не змінюється (з `settings.list.sort` або за створенням). Окремий випадок сортування за самим `title` не виділяється: другорядний `LEFT JOIN` лишається, він безпечний. Alias join — `title_value`. Альтернатива — `COALESCE` з `title` мови `default` — відхилена: вводить fallback, якого в системі немає; питання перекладів обговорюється окремо.

Документація, яку описує дизайн: `docs/content-querying.md` (розділи «Сортування» і «Оператори за типами»), `docs/admin-content-nodes.md` (сортування колонок).

## Risks / Trade-offs

- [Додатковий `LEFT JOIN` на таблицю значень `title` при кожному явному сортуванні] → колонка `value` індексована, ціна мала; прибрати join можна лише окремим випадком (сортування за `title`), що не вводиться заради простоти.
- [Записи з рівними ключами змінюють порядок: раніше за `id`, тепер за `title`] → навмисно; стосується лише явного сортування, а порядок за замовчуванням не змінюється.
- [Перше значення — не обов'язково найближча дата] → прийнятий наслідок; редактор мусить вводити значення по порядку. Автосортування значень при збереженні — окрема зміна, якщо знадобиться.
- [Вибірка `ContentNodeQuery` сортує за файловим полем і `youtube` за збереженим рядком (`{uuid}.{ext}`, URL), змістовного порядку це не дає] → прийнято: адмінка таке сортування не пропонує, а окрема заборона у вибірці потребувала б критерію сортованості типу, якого там не було й раніше.
- [Зміна зачіпає адмінку, а не лише сайт] → навмисно, правило спільне; е2е-перевірка `?sort=tags` оновлюється разом зі змінною спекою.
- [Масив `in` без верхньої межі кількості значень] → `whereIn` по індексованій колонці `value` дешевий для звичних розмірів; окремий ліміт не вводимо, поки немає потреби (зміна конфігурації — окрема зміна).
- [Кілька фільтрів по одному множинному полю можуть виконуватись різними значеннями] → прийнято й закріплено сценарієм; для «обидві умови одним значенням» немає оператора, що не входить у цю зміну.
- [`settings.list.sort` на множинне поле перестає відкидатися] → навмисно; посилання на файлове поле, `youtube` чи відсутнє поле відкидається. Для файлових полів і `youtube` це нова поведінка: раніше `listSettings` відкидав лише множинні поля.
