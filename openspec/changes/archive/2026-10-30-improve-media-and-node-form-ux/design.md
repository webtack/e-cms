# Design

## Context

Профілі в `config/files.php` уже задають `mime => розширення` (`FileStorage` пише файл як `{uuid}.{ext}`), тож джерело коротких позначень існує. `File.mime` у `media` — повний MIME. Сьогодні MIME виводиться у: колонці «Тип» (`Pages/Admin/Media/Index.tsx`, рядок з `MediaController::row`), підзаголовку `MediaDetails` (JSON `MediaController::show`) і чекбоксах у `ContentFieldForm` (`fileTypes[].mimes` з `ContentFieldController::fileTypes`). `FileUpload` MIME не показує.

`DataTable` у серверному режимі вже вміє фільтри: проп `filterable` і колонки з `filterable: true`; тип `select` з `options: {value, label}[]` дає випадний список значень, сервер розбирає `filters[N][c|o|v]` у `TableRequest`. `MediaController` фільтри поки не застосовує. Форма запису (`ContentNodeForm`) малює slug і поля як окремі блоки `space-y-2`; блок налаштувань файлу в `ContentFieldForm` — `fieldset.rounded-md.border.p-4` з `legend`. Множинне поле — `NodeFieldList` (елемент = один `NodeFieldInput`, для `image`/`file` — `FileUpload`); завантаження — `POST /admin/files` по одному файлу.

## Goals / Non-Goals

**Goals:**
- Одне джерело істини для коротких позначень, яке використовують і бекенд, і фронтенд.
- Фільтр типу без нових компонентів DataTable.
- Множинне завантаження без зміни API завантаження.

**Non-Goals:**
- Конструктор складних фільтрів у медіатеці (кнопка «Фільтр» лишається вимкненою).
- Зміна збереженого значення `mime`, `settings.mimes` чи правил перевірки (усе лишається повними MIME).
- Паралельне завантаження, прогрес у байтах, скасування черги.
- Нова сторінка вибору файлів із медіатеки.
- Один спільний контейнер для всієї форми запису.

## Decisions

**1. Позначення типів на сервері: `App\Files\FileTypes`.** Клас читає `config/files.php` і дає `label(string $mime): string` (розширення з профілю, інакше частина після `/`), `labels(): array<mime, ext>` і `mimesFor(string $ext): list<string>` (зворотне відображення для фільтра; `image/jpeg` → `jpg`, кілька MIME можуть мати спільне розширення). Бекенд віддає готове `type` у рядках і деталях медіатеки та `labels` у `fileTypes` поля. *Альтернатива:* спільний Inertia-проп або TS-таблиця — відкинуто: дублювала б конфіг, а `MediaDetails` і так отримує дані з JSON. Якщо в профілях з'явиться два MIME з однаковим розширенням, мапа дає одне позначення, а фільтр знаходить обидва.

**2. Фільтр медіатеки — швидкий фільтр `DataTable` (селект поруч із пошуком).** Окремий `Select` у тулбарі, але керований загальним станом таблиці, а не локальним: `Column` отримує необов'язковий прапорець `quickFilter` (лише для `type: 'select'`). `DataTableToolbar` для кожної такої колонки виводить `Select` поруч із полем пошуку: значення береться зі `state.filters` (фільтр `eq` за цією колонкою або «Усі»), вибір значення викликає `controller.setFilters` (замінює/додає `eq`-фільтр колонки, «Усі» його знімає). Тому чіпи (`DataTableFilterChips`), «Скинути», адреса й скидання сторінки працюють без змін; знімання чіпа оновлює селект, бо той читає стан. Перевірити, що чіпи показують і фільтри колонок без `filterable`. Прапорець `filterable` самого `DataTable` у медіатеці НЕ вмикається (кнопка «Фільтр» не потрібна). На сервері колонка `mime` описується як `select`, `filterable: true` з `options` — коротке позначення; `MediaController::index` застосовує `whereIn('mime', FileTypes::mimesFor($value))` до підрахунку й до сторінки. Клієнтський режим підтримується тим самим кодом (стан у пам'яті). *Альтернатива:* штатний конструктор фільтрів (колонка → оператор → значення) — відкинуто: для одного очевидного фільтра надто багато кроків. *Альтернатива:* локальний `Select` на сторінці медіатеки з власним `router.get` — відкинута: дублювала б стан, чіпи й скидання.

**3. Тип у `select`-колонці й сортування.** Сортування лишається за `mime` у БД (порядок за повним MIME, не за коротким позначенням); для користувача різниця непомітна, а запит не ускладнюється.

**4. Множинний режим `FileUpload`.** Завантаження одного файлу виноситься з компонента в модульну функцію `uploadFile(file, target): Promise<UploadedFile>` (кидає помилку з повідомленням сервера), яку використовують і одиночний, і множинний режими. Проп `multiple` вмикає `<input multiple>`, перетягування кількох файлів і послідовний цикл `for … await uploadFile()`; результат — колбек `onUploadedMany(files)` (кожен успішний файл одразу, після кожного запиту), помилки збираються як `{name, message}[]` і показуються списком. У режимі `multiple` компонент не показує вибраного значення (форма сама малює список). *Альтернатива:* окремий компонент `MultiFileUpload` — відкинуто: дублювання завантаження, перевірок `accept`/`maxSize` і зони перетягування.

**5. Інтеграція в `NodeFieldList`.** Для множинних полів `image`/`file` над кнопкою «Додати елемент» з'являється multi-зона `FileUpload multiple`; успішні файли дописуються в `value` і в `ids` (клієнтські ключі), а `onFile` запам'ятовує метадані у `known` форми. Кнопка «Додати елемент» лишається (додає порожній одиночний віджет). Послідовні виклики `onChange` одного вибору мусять накопичувати значення, тож колбек отримує партію файлів після завершення черги, а не по одному, щоб не губити елементи через застарілий `value` у замиканні (альтернатива — `useRef` з актуальним значенням; вибрано партію).

**6. Контейнер кожного поля форми запису.** У `ContentNodeForm` блок slug і блок кожного поля типу стають `<fieldset className="space-y-2 rounded-md border p-4">` з `<legend className="px-1 text-sm font-medium">` — ті самі класи, що в `ContentFieldForm`. Легенда — назва поля з позначкою обов'язковості (`<Label>` зараз; для немножинних полів `htmlFor` зберігається, для множинних лишається `id` + `aria-labelledby`, `role="group"` можна прибрати, бо `fieldset` уже група). Булеве поле: прапорець і підпис в одному рядку всередині рамки без легенди. Підказки й повідомлення про помилки лишаються всередині рамки. Кнопки лишаються поза рамками. Нових ключів перекладів для рамки немає (легенда — назви полів); нові ключі потрібні для множинного завантаження: підпис зони, перебіг («Uploaded :done of :total») та помилка файлу («:name: :message»), та «All types» / «Усі типи» для швидкого фільтра.

**7. Документація.** Змінені компоненти описують `docs/file-storage.md` (позначення типів, множинний режим віджета), `docs/media-library.md` (колонка, фільтр), `docs/admin-data-table.md` (швидкий фільтр), `docs/admin-content-fields.md` (`fileTypes` з позначеннями), `docs/admin-content-nodes.md` (контейнер, множинне завантаження), `docs/e2e-testing.md` (сценарії й таблиці залежностей).

## Risks / Trade-offs

- [Два MIME з одним розширенням у профілях] → `mimesFor` повертає список, фільтр використовує `whereIn`; покрито Feature-тестом.
- [Файли зі збереженим MIME, якого вже немає в профілях, не з'являться в списку типів фільтра] → колонка показує запасне позначення; відфільтрувати їх неможливо, доки тип не додано в профіль (прийнятно: профілі змінюються розробником).
- [Застарілий `value` у замиканні при послідовних завантаженнях] → віддавати партію через один `onChange`, а не по одному файлу.
- [Довга черга блокує форму] → завантаження послідовне, віджет показує «оброблено N із M»; кнопку збереження не блокуємо, але частково завантажений список зберігається як є.
- [Порожні елементи в списку при відмові] → відхилений файл елементом не стає.
- [Зміна розмітки форми запису ламає e2e-селектори (`getByLabel`, `role=group`)] → оновити селектори у спеку; прогнати `admin-content-nodes`.
- [Швидкий фільтр розсинхронізується з чіпами або конструктором] → селект лише читає `state.filters` і пише через `setFilters`; покрито e2e `admin-data-table`.
