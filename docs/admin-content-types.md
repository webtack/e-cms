# Content types in the admin panel

The `GET /admin/content-types` page (`admin.content-types.index`) shows content types of kind `content` in the [data table](admin-data-table.md) in **server mode**: search, sorting, pagination, and page size are handled by the server, and the state lives in the address. Types of kind `page` have the same pages at the address `/admin/page-types` ([admin-page-types.md](admin-page-types.md)): the same controllers and React pages, with the kind taken from the route; types of kind `block` — at the address `/admin/block-types` ([admin-block-types.md](admin-block-types.md)); here they are not shown. There are no filters on the page. Access — `auth` + `verified` and the role right `types` (without it 403; the same for the SEO, "Display", type value, and field pages of all three kinds). The exception is the types table itself (`index`): without `types` it is opened by a user with the level `own`/`any` on a type of this kind, and it leads only to nodes (only the available types, the "Nodes" button, no "Create", settings, or deletion; the prop `canManage = false`), and if there are no available types — 403; a guest is redirected to `/login`. See [access control by roles](access-control.md). The type model is described in [content-model.md](content-model.md).

## Data source

The controller `Webtack\Ecms\Http\Controllers\Admin\ContentTypeController::index` takes `ContentType::ofKind('content')->withCount(['fields', 'nodes', 'children'])` in one query (no N+1), turns the types into rows with snake_case keys, and passes them to `TablePage::fromCollection()`. Dozens of types are expected, so everything is loaded into memory; the search and filter rules are the same as in the client engine. Switching to `TablePage::make()` with an SQL query does not change the page contract.

Without an explicit `sort`, the rows are ordered by name (case-insensitive); an explicit `sort` from the address overrides this.

## Columns

| Key | Type | Sorting | Notes |
| --- | --- | --- | --- |
| `name` | text | yes | always visible; under the name, in a smaller muted font — the description; the column has `width` `24rem`, so the name and the description are each cut into one line with an ellipsis (the full text in `title`); an empty description adds no line |
| `key` | text | yes | always visible |
| `slug` | text | yes | the public path of the type ([content-model.md](content-model.md#type-slug)); empty if not set; the column has `width` `16rem`, so a long slug is cut into one line with an ellipsis (the full slug in `title`) |
| `parent_name` | text | yes | the **name** of the parent type (the row keeps the key in `parent_type` for the link); sorted by the displayed name; does not take part in search; empty if there is no parent. With the `types` right the name is a link to the parent's node list `{basePath}/{parent_type}/nodes`, without it plain text. The names come from the loaded collection of the kind, so there is no query per row |
| `children_count` | number | yes | the number of **direct** child types; visible by default; with the `types` right a link to the ["Child types" tab](#child-types-tab) `{basePath}/{key}/children`; the server omits the column without `types` |
| `fields_count` | number | yes | including the system field `title` |
| `nodes_count` | number | yes | in all sections — a link to the list of nodes of the type `{basePath}/{key}/nodes` |

There are no kind and description columns: all types on the page are of kind `content`, and the description is shown under the name. `description` remains a server-side column without a client counterpart, so that search finds types by description.

The rows keep `parent_type` (the parent key) and `children_count` (also read by the deletion dialog) as values. The old sort address `sort=parent_type` is no longer a sortable column: it is reported in `ignored`.

Search (`q`) looks in the name, description, slug, and key (not by the parent type or by counters). **There are no filters:** no column is `filterable`, the table does not pass the `filterable` prop, there is no filter button in the toolbar, and filters in the address (including the obsolete `kind`) are ignored and get into `ignored` with the reason `not_filterable`.

## Row actions and the "Create" button

Above the table there is an active "Create" button (a link to `/admin/content-types/create`, visible also in the empty state). In each row — a group of buttons (`ButtonGroup`): the main button "Settings" (a link to the edit form `/admin/content-types/{key}/edit`) and next to it the "⋮" button with a menu: "Edit" (the same form), "Display" (`{basePath}/{key}/display`), "SEO" (`{basePath}/{key}/seo`; absent in the block section, which has no SEO tab), "Sitemap" (`{basePath}/{key}/sitemap`; absent in the block section), "Fields", "Nodes", "Child types" (`{basePath}/{key}/children`), "Preview", "Clone" (opens the [clone dialog](#cloning)), and "Delete" (destructive, separated by a divider). "Preview" (`Eye` icon) opens the public list page of the type, `/{slug}`, in a new tab; it is shown only for a `content` type with a non-empty slug (`typePublicUrl(section, row.slug)` from `section.ts`, the same rule as the "Preview" link of the [section menu](#type-section-menu)), so the page and block menus never have it. The other destinations come from the same list as the [type section tabs](#type-section-menu), so the menu and the tabs never differ. The "Fields" item is a link to the type's fields page `/admin/content-types/{key}/fields` ([admin-content-fields.md](admin-content-fields.md)); "Nodes" — to the node list `/admin/content-types/{key}/nodes` ([admin-content-nodes.md](admin-content-nodes.md)). The "Nodes" and "Child types" items are in the row menu of all three sections.

The button group is `resources/js/Components/Admin/ContentTypes/ContentTypeRowActions.tsx` (the primitive `Components/ui/button-group.tsx`); it receives the row (`row`), so it knows the type's key, name, and counters. The menu items (except "Delete") are rendered from `typeSectionItems(section.kind)`; the settings destination is labelled "Edit" in the menu (`menuLabel`) and "Settings" in the tabs. The deletion dialog is rendered next to the menu, not inside it, so that it does not close together with it. The mechanism `rowActions`/`toolbarActions` is described in [admin-data-table.md](admin-data-table.md#row-actions-and-toolbar).

## Creation

- `GET /admin/content-types/create` (`admin.content-types.create`) — the form; it passes `parentOptions` (types of kind `content`, sorted by name, each `{key, name, slug}`; the `slug` lets the form show the prefix a child slug needs) and `defaultParent`: the query parameter `?parent_type={key}` preselects the parent, but only when the key is among `parentOptions` (same kind); an unknown key or a key of another kind gives `null` and the form opens with no parent. The ["Child types" tab](#child-types-tab) uses it for its "Create" button; the slug-prefix hint then applies as for any selected parent.
- `POST /admin/content-types` (`admin.content-types.store`) — saving through `StoreContentTypeRequest`; after success a redirect to the list with a `success` message.

The form fields are the shared component `Components/Admin/ContentTypes/ContentTypeForm.tsx` (`useForm`, modes `create`/`edit`), the page `Pages/Admin/ContentTypes/Create.tsx`:

| Field | Rules |
| --- | --- |
| `name` | required, up to 255 characters |
| `key` | required, `^[a-z][a-z0-9_]*$`, up to 64 characters, unique, not one of the [reserved type keys](content-model.md#reserved-type-keys) (the error "This key is reserved" next to the field) |
| `slug` | optional, the format (one or more segments separated by `/`, for example `common/institutions`) and uniqueness as in the [type slug](content-model.md#type-slug); its first segment is not a [reserved path](content-model.md#reserved-paths) and the slug does not match the slug of a page or the address of a node (the rule `AvailablePublicPath`, the errors "This slug is reserved." / "This slug is already used by a page." / "This slug is already the address of a node." next to the field); with a parent type it must start with the parent's slug and `/`, and the parent must have a slug (the rule `TypeSlugHierarchy`, using `Webtack\Ecms\Content\TypeSlugs`: "The slug must start with \":prefix\"." / "The parent type must have a slug first.") |
| `parent_type` | optional, only an existing type of kind `content`; "No parent type" — an empty value |
| `description` | optional |

There is no kind field: `kind` is **always the kind of the section** (`content` on this page). The controller calls `ContentType::create([...$request->validated(), 'kind' => $this->kind($request)])`, and a `kind` passed in the request is dropped, because it is not in the rules. Empty optional fields are stored as `NULL`; spaces at the edges are trimmed by the framework. The system field `title` is added by the model. Errors are shown next to the fields, entered values are kept; "Save" is disabled during submission; "Cancel" leads to the list. The key is not generated from the name: it is immutable, so a silent substitution is risky; there is a hint next to the field about the format.

The `FormRequest` rules deliberately duplicate the model ones (the form gives field errors, the model remains the last barrier); the shared part is `StoreContentTypeRequest::sharedRules()`.

## Editing

- `GET /admin/content-types/{key}/edit` (`admin.content-types.edit`) — the form with the current values (`type`), `parentOptions` **without the type itself and its descendants** (`ContentType::descendantKeys()`), so as not to create a cycle, `listOptions` for the ["Node list" section](#node-list-in-the-form); the form does not provide public settings (`publicOptions`) — they are on the [Display tab](#display-tab-all-kinds).
- `PUT /admin/content-types/{key}` (`admin.content-types.update`) — `UpdateContentTypeRequest`; `name`, `slug`, `parent_type`, `description`, `settings.list` are updated ([see below](#node-list-in-the-form)); the edit request rejects `settings.public` (`settings` is narrowed to `array:list`). `key` and `kind` in the request are ignored (they are not in the rules). The key in the form is `readOnly` with the hint "The key cannot be changed.". The uniqueness of the slug is checked excluding the type itself; a collision with a page or a reserved path is checked only when the slug is changed (saving with an unchanged slug passes), an empty slug clears the value, the hierarchy rule is checked when the slug or the parent changes, changing or clearing the slug is rejected while a direct child type has a slug ("Change the slugs of the child types first."; there is no cascade), and the parent cannot be the type itself or its descendant (an error next to the field). After success the user stays on the edit form (`back()`) with a `success` message.

The route parameter `{contentType}` is bound by `key` and only in the kind's section (`Route::bind` in `routes/service.php` takes the kind from the default `kind` of the route: `content` for `/admin/content-types/**`, `page` for `/admin/page-types/**`, `block` for `/admin/block-types/**`): a non-existent key and types of another kind give 404 on all create/edit/delete routes. Breadcrumbs for `/create` and `/{key}/edit` are built by `getBreadcrumbs` (`navigation.ts`): "Admin → Content Types → Create/Edit content type".

### Node list in the form

The edit form (mode `edit`, all three kinds) contains the "Node list" section — the component `Components/Admin/ContentTypes/NodeListSettingsSection.tsx`, which edits the type's `settings.list` ([content-querying.md](content-querying.md#default-list-settings)). The create form has no such section: a new type has no fields yet (`ContentTypeForm` in `create` mode removes `settings` from the request via `transform`).

- **Columns.** A list of checkboxes: the selected ones come first in the saved order, followed by the unselected ones. The order is changed by dragging the handle (`@dnd-kit/sortable`, as in multiple fields; the handle is a button with `aria-label` "Change the position of the column «…»"), and from the keyboard: Space lifts the row, arrows move it, Space lowers it. `title` is an ordinary column in this list: its checkbox is marked and disabled (the column is always shown), but its position can be changed like the others. The available columns are `title`, the type's fields that have values in the nodes (without fields with reserved keys), and the service columns "Slug", "Status", "Active", "Creation date", "Update date", "Publication date", "Unpublishing date", "Views", "Author". A type without its own columns starts with `title`, "Slug", "Status", "Publication date", and "Author" (`NodeListSettings::DEFAULT_SERVICE_COLUMNS`); a type that already stores its own `visible` keeps it.
- **Search.** Checkboxes for the type's text fields (those that are `searchable()`, including `title`). The node `slug` is always searched in addition to the checked fields, so it is not a checkbox, and an empty selection still leaves the slug search.
- **Default sorting.** A `Select` of the field and direction. The field options: the service ones "Status", "Active", "Creation date", "Update date", "Publication date", "Unpublishing date", "Views", and the fields that can be sorted (not file fields, not `youtube`, not `term`); slug is not sortable. The initial choice for a type without settings is "Creation date" ascending.

`listOptions` is built by `Webtack\Ecms\Content\NodeListSettings::formOptions()` — the same class that cleans the settings for the list itself (`clean()`), so the form and the list do not diverge: `columns`, `searchFields`, `sortOptions` (`{key, name, service}`; the name of a service column is an English translation key) and `current` — the cleaned current state with the resolved default values (`slug`, `status`, `published_at`; all text fields; `created_at` ascending). References to deleted fields do not get into `current`.

**Saving.** The form sends `settings.list` `{visible, search, sort}` together with the other fields. `StoreContentTypeRequest::sharedRules()` checks only the form (arrays of strings without duplicates, `sort.direction` ∈ `asc`/`desc`, only the keys `visible`/`search`/`sort`), and the validity of keys is checked by `ContentType::assertValidListSettings()` (an error under the key `settings`; the form shows it next to the section together with `settings.list.*`). `ContentTypeController::update()` merges **only the key `list`** into the existing `settings` (`mergeListSettings()`), so the other `settings` keys remain. Default values are not stored: a `visible` with no columns besides `title` (then the default composition applies), empty `visible` and `search`, and the sorting "Creation date" ascending (which is the order without settings anyway) are discarded; an empty `list` is deleted, and empty `settings` become `NULL`. A request without `settings.list` leaves the settings unchanged. The default column composition set by the type applies in the [node list](admin-content-nodes.md#how-columns-are-built); personal hiding of columns in `localStorage` works on top of it.

### Display tab (all kinds)

The "Display" tab (`Display`) is in the type menu of **all three kinds** between "Settings" and "Fields" (for `content` and `page` — before "SEO"). It gathers everything that defines how the type looks on the site: for `content` — the block of section values (`section_title`, `section_description`, `section_cover`; the values of the **type itself**, not of its nodes) and the "Public display" block (`settings.public`); for `page` and `block` — only "Public display" (they have no own section values, `typeFields` is empty, the `section-panel` block is not shown). The section fields, their labels, hints, limits, and input element types are taken from the definitions of the system fields ([content-model.md](content-model.md#system-fields)).

- `GET {basePath}/{key}/display` (`admin.{section}.display`) — `ContentTypeController::displayTab()`, the page `Pages/Admin/ContentTypes/Display.tsx`; the route is in the shared kinds loop in `routes/service.php`, so a foreign kind gives 404. The former address `/admin/content-types/{key}/section` was removed without a redirect (404). Props: `type`, `section`, `publicOptions`, `typeFields` (the fields of the `section` panel with the `panel` mark; empty for `page`/`block`), `typeValues` (the base values by key) and `typeFiles` (information about files in the values). The values are read by `ContentValueReader::loadForType`.
- `PUT {basePath}/{key}/display` (`admin.{section}.display.update`, `ContentTypeDisplayController`, `UpdateContentTypeDisplayRequest`) — **one save** of the section values and `settings.public`. The request checks the form `values` (an array key → value) and the rules of `settings.public.*`. The controller performs both parts in one `DB::transaction`: `ContentValueWriter` writes `values` (only for `content`; for `page`/`block` the key is ignored), then `mergePublicSettings()` merges `settings.public`. An error in either part rolls back both — nothing is saved (including when `ContentType::assertValidPublicSettings()` throws after the values have been written). Value errors come as `values.{key}`, settings errors as `settings` / `settings.public.*`. The other `settings` keys (in particular `list`) are not touched by the controller; a request without `settings.public` keeps the saved public settings. After success — `back()` with the message "Display saved."
- The form — `Components/Admin/ContentTypes/TypeDisplayForm.tsx`: one `useForm` (`values` + `settings.public`), the block of section values (`NodeFieldFrame` in `NodeFieldsPanel`, `data-testid="section-panel"`; only for `content`), `PublicDisplaySettingsSection`, and **one** sticky `FormActionBar` ("Cancel" leads to the list of types) — the last child of the form. The base form saves the base values; for `content` types the [translation mode](#translation-mode-of-the-display-and-seo-tabs) is offered above it. Files are tracked with the owner `content_type` ([media-library.md](media-library.md#files-of-type-values)). Panel fields are not configured on the "Fields" tab: [admin-content-fields.md](admin-content-fields.md).

#### Public display

The "Public display" block is the component `Components/Admin/ContentTypes/PublicDisplaySettingsSection.tsx`, which edits the type's `settings.public` ([content-model.md](content-model.md#type-settings-settings), reading — [content-querying.md](content-querying.md#public-type-settings)). The create form of a type does not have it (there are no fields yet). Only the added fields are offered (`is_system = false`); `title`, service attributes, and meta fields are always available to the template and are not selected.

- **Page fields.** A toggle "All added fields" (enabled by default; the checkboxes are then marked and disabled) and the checkboxes of the fields. While the toggle is on, the key `page_fields` is not saved, so a new field appears on the page by itself; turning it off saves the list of checkboxes, and turning it back on deletes the key again. For `page` and `block` this is the only part of the block.
- **Meta data** is not edited here: the choice of fields for the page title, description, and image has moved to the "SEO" tab ([the "Meta data" block](#meta-data-block-on-the-seo-tab)). Saving "Display" does not change the saved `settings.public.meta`, and a request with `meta` is rejected with a validation error (`settings.public`).
- **Card fields** (`content`). Checkboxes of the added fields; if empty — only `title` appears in the card.
- **Sorting** (`content`). A `Select` of the field (the service ones "Status", "Active", "Creation date", "Update date", "Publication date", "Unpublishing date", "Views", and the sortable added fields) and the direction; the default is "Publication date" descending.
- **Archive** (`content`). A bordered `fieldset` (`FieldGroup`) whose `legend` "Archive" names it. The "Archive field" select offers "Do not use" (the default), the service dates "Unpublication date" and "Creation date", and the added fields of type `date` and `datetime` (`archiveOptions`); no other field. Only while a field is chosen, "Archive sort" (field, same options as the main sort) and "Direction" appear; choosing a field starts with the main sort as the archive sort. The public list is then split by that date ([public-site.md](public-site.md#archive-period-of-a-list)). The choice is saved with the rest of `settings.public`; "Do not use" removes the `archive` key. `page` and `block` have no such group.
- **Nodes per page** (`content`). An integer from 0 to `maxPerPage` (`content.max_per_page`); `0` — all nodes. A validation error is shown under the field.
- **Paginator** (`content`). The toggle is disabled while the count is `0`; the saved choice is not lost (returning `per_page > 0` restores it).

`publicOptions` is built by `Webtack\Ecms\Content\PublicDisplaySettings::formOptions()` (`fields`, `sortOptions`, `archiveOptions`, `current` with the resolved default values and `archive` (`null` without one), `maxPerPage`); it has no meta data.

**Saving.** `toPublicSettings()` skips `page_fields` when "All added fields" is on, `archive` while no field is chosen, and `meta` while nothing is selected; for `page`/`block` it sends only the page fields (and `meta`). `UpdateContentTypeDisplayRequest` checks the form (`array:list_fields,page_fields,sort,per_page,pagination,archive,meta`, `archive` — `array:field,sort` with the same sort rules as `sort`, `field` required with `sort`, arrays of strings without duplicates, `per_page` — an integer 0…`max_per_page`, `pagination` — boolean, `meta` — up to three optional strings `title`, `description`, `image`), the validity of keys, the types of meta fields (`PublicDisplaySettings::META_TYPES`), and the restrictions by kind (the key `meta` for `block` is rejected; `archive` is for `content` only), the archive field (an added `date` / `datetime` field, `created_at`, or `unpublished_at`) and its sort — `ContentType::assertValidPublicSettings()` (an error under the key `settings`; the form shows it next to the block). `ContentTypeDisplayController::mergePublicSettings()` replaces only the key `public` (via `ContentTypeController::replaceSetting()`), so `list` and the other `settings` keys remain. `archive` is stored only while its `field` is chosen (a cleared choice removes the key). Default values are not stored: empty `list_fields`, sorting "Publication date" descending, `per_page = 0`, and `pagination = true`; an empty `public` is deleted. For `page`/`block`, the list keys, if sent, remain in the request so that the model rejects them.

### Translation mode of the Display and SEO tabs

The values the two tabs edit (`section_*` on "Display", `meta_*` on "SEO") can be translated one language at a time, following the [translation mode contract](admin-translation-mode.md). The right is the type configuration right (`can:types`), as for the tabs themselves.

- `GET {basePath}/{key}/display?lang=en` and `GET {basePath}/{key}/seo?lang=en` — the tab in the translation mode: the same form, where only the values of the tab are editable (the public display settings and the "Meta data" choice keep their place, shown inert and dimmed with their base state), prefilled with the stored translation or else the base value. Props: the usual ones plus `translation` (`{lang, baseLang, languages, values, exists}`; `values` is keyed by field key, `exists` says that this tab has a stored value in `lang`; `typeFiles` describes the prefilled files). `translation` is `null` and `?lang=` answers 404 for a tab with no values: every `block` type and the "Display" tab of a `page` type. An unknown or inactive language answers 404.
- `PUT {basePath}/{key}/values/translations/{lang}` (`admin.{section}.values.translations.save`, `ContentTypeValuesTranslationController`, `SaveTypeValuesTranslationRequest`) — body `panel` (`section` for "Display", `seo` for "SEO") and `values`. It saves through `TranslationSaver` ([content-values.md](content-values.md#saving-one-language)): a value equal to the base is not stored, an emptied field loses its translation. Only the fields of the panel are accepted (a key of the other tab is an error `values.{key}`), so one tab never changes the other's translations. It redirects to the same tab with `?lang={lang}` and "Translation saved."
- `DELETE {basePath}/{key}/values/translations/{lang}` (`…values.translations.clear`) — body `panel`; removes only the translations of that tab's fields and returns to the tab with "Translation cleared." A type without values in the panel answers 404.
- **File names and descriptions.** The images of a tab (the section cover on "Display", the meta image on "SEO") get a description in the language under the same rules as in a [node translation](admin-content-nodes.md#translation-mode): `typeFiles[...].name` and `.description` are prefilled (translated, else base), the "Edit file details" dialog edits both, and `file_meta[{uuid}][name]` / `[description]` travel with `panel` and `values`. `TranslationSaver::saveFileDescriptions()` accepts only files held by the fields of that tab (a file of the other tab or of no value of the type is an error under `file_meta.{uuid}.description`). The base description and the original name stay unchanged.
- **Marker.** A language is marked when the type has any stored translated value in it on either tab (`TranslatedLanguages::forType()`).

The forms (`TypeDisplayForm`, `TypeValuesPanels` of the SEO tab) are one form in both modes: they render `LanguageSwitcher` above it, lock the shared settings in the translation mode and put `ClearTranslationButton` into their own `FormActionBar` (`saveDisabled` until a value changes).

### SEO tab (`content` and `page`)

The "SEO" tab is a separate page with the values of **the type itself** (`meta_title`, `meta_description`, `meta_image`) for the kinds `content` and `page`; for `block` there is none. The settings page (`/edit`) contains only the main type form and does not provide panel props. All values are optional.

- `GET /admin/content-types/{key}/seo` and `GET /admin/page-types/{key}/seo` (`admin.content-types.seo`, `admin.page-types.seo`) — `ContentTypeController::seoTab()`, the page `Pages/Admin/ContentTypes/Seo.tsx`. The route is in the `content-types` and `page-types` sections: for `block-types` and a type of another kind — 404. The fields of the panel are determined by the owner of the type's values (`ValueOwner::forType()`), so for `page` these are the same three `meta_*`. Props: `type`, `section`, `typeFields` (the fields of **the `seo` panel only**), `typeValues`, `typeFiles`.
- `PUT /admin/content-types/{key}/values` and `PUT /admin/page-types/{key}/values` (`admin.content-types.values.update`, `admin.page-types.values.update`, `ContentTypeValuesController`, `UpdateContentTypeValuesRequest`) — the sections `content-types` and `page-types`; for `block-types` and a foreign kind — 404. For `page`, a `section_*` field is rejected as not belonging to the type. `values` — an array of field key → value; it is written by `ContentValueWriter` with the type as the owner in the `default` language. Only the keys from the request are written, so saving the tab does not change the section values. The request may also carry `settings.public.meta` (the "Meta data" block, see below): then both the values and the choice are saved in one transaction, and an error in either part saves nothing. An empty value clears the saved one. A field that does not belong to the type (`title`, a regular field) is rejected; errors come under the keys `values.{key}` and are shown next to the field, with the entered text kept. After success — back with the message "Values saved."
- The form — `Components/Admin/ContentTypes/TypeValuesPanels.tsx` (the `seo` panel) with the same `NodeFieldFrame` and `NodeFieldsPanel` as the node form ([admin-content-nodes.md](admin-content-nodes.md#fields-of-the-node-and-the-seo-panel)), and the sticky `FormActionBar`. This is the **single form of the tab**: it also renders the "Meta data" block under the fields, so there is one "Save" button.

#### Meta data block on the SEO tab

Below the value fields there is a separate section with a border (`fieldset`, `data-testid="public-meta"`) — the component `Components/Admin/ContentTypes/MetaDataSection.tsx`. It has **neither its own button nor its own form**: the tab's form (`TypeValuesPanels`) holds the choice and saves it together with the type's `meta_*` values by the single button of the sticky panel "Cancel / Save". The block is in `content` and `page`; in `block` there is no tab (a block has no address of its own).

- Three optional `Select`s with the item "Not selected": "Title" (the added fields of type `string`), "Description" (`text` and `richtext`), and "Image" (`image` and `youtube`). Each choice is the key of one added field; they are stored in `settings.public.meta` (`title`, `description`, `image`), and the unselected ones are not stored, nor is an empty `meta`. The automatic node `title` field cannot be selected for anything (it is rejected): it is already in the title chain.
- Saving is the same `PUT {basePath}/{key}/values` (`ContentTypeValuesController::update()`; there is no separate route `…/seo/meta`): the request carries `values` and `settings.public.meta`. The action merges only the key `meta` into `settings.public`: the other `public` keys (`page_fields`, `list_fields`, …) and the rest of `settings` (`list`) remain; an empty choice is discarded, and an empty `meta` and an empty `public` are not stored. A request without `settings.public.meta` does not touch the saved choice. The validity of fields is checked by `ContentType::assertValidPublicSettings()`: the error comes under the key `settings`, the block shows it under the choice, and the `meta_*` values are not saved in this case either. After success — `back()` with the message "Values saved." For `block-types` and a foreign kind there is no route (404); access — by the `types` right.
- The `metaOptions` prop of the tab is built by `PublicDisplaySettings::metaOptions()`: `metaFields` (the allowed fields for each choice; the title starts with `title` with the `service` mark) and `current` (the current choice). A field that was later deleted or changed to an invalid type is shown by the block as "Not selected".
- The values of the selected fields are used by the site as the page meta data when the node has no own `meta_*`; then come the type's own `meta_*` from this same tab and the site settings ([public-site.md](public-site.md#page-meta-data)).

### Sitemap tab (`content` and `page`)

The "Sitemap" tab sits right after "SEO" and holds the type's sitemap settings, `settings.sitemap` ([type-sitemap.md](type-sitemap.md) describes the shape, the defaults and what the two sitemaps do with it). It is for the kinds `content` and `page`; for `block` there is no tab and no route.

- `GET /admin/content-types/{key}/sitemap` and `GET /admin/page-types/{key}/sitemap` (`admin.content-types.sitemap`, `admin.page-types.sitemap`) — `ContentTypeSitemapController::edit()`, the page `Pages/Admin/ContentTypes/Sitemap.tsx`. Props: `type`, `section`, `hasSlug`, `sitemap` (`xml`: `type`, `nodes`, `changefreq`, `priority`; `web`: `type`, `nodes`; an unconfigured type has every checkbox off and the defaults `weekly` / `0.5`), `changefreqOptions`, `priorityOptions`.
- `PUT /admin/content-types/{key}/sitemap` and `PUT /admin/page-types/{key}/sitemap` (`admin.content-types.sitemap.update`, `admin.page-types.sitemap.update`) — `ContentTypeSitemapController::update()` with `UpdateContentTypeSitemapRequest`. Only `settings.sitemap` is written; the other keys of `settings` stay. A group stores only the checkboxes that are on, `changefreq` / `priority` are stored only while an XML checkbox is on (defaults `weekly` / `0.5`), and an all-off form removes the key. A `page` type cannot send `type` (validation error). After success — `back()` with "Sitemap saved."
- Access: the `types` right (403 without it); `block-types` and a foreign kind answer 404.
- The form (`SitemapSettingsSection`) has two bordered blocks, "XML sitemap settings" and "Web sitemap settings", and one sticky "Cancel / Save". "Content type" is shown for `content` only; the two selects appear while an XML checkbox is on. A `content` type without a slug shows a hint that it has no public address and so is not in the maps (saving stays possible).
- Cloning copies `settings.sitemap` with the rest of `settings`, so a clone appears in the maps at once.

## Cloning

The "Clone" item of the row menu (all three sections, only for users with the `types` right) opens `CloneTypeDialog` (`Components/Admin/ContentTypes/CloneTypeDialog.tsx`, rendered next to the menu like the delete dialog). It asks for `name`, `key`, a parent type and, for content types only, `slug`. `name`, `key` and `slug` start empty; the parent select starts with the parent of the source and can be changed or cleared (the options are the `parentOptions` prop of the list page, same shape as on the create form).

`POST /admin/{section}/{key}/clone` (`admin.content-types.clone`, `admin.page-types.clone`, `admin.block-types.clone`; behind `can:types`, the kind-bound `{contentType}` gives 404 for another section) is validated by `CloneContentTypeRequest`, which reuses the `name`, `slug`, `parent_type` rules of `StoreContentTypeRequest::sharedRules()` and its `keyRules()`. `description` and `settings` are not accepted.

`Webtack\Ecms\Content\ContentTypeCloner` does the work in one transaction through the models, so their validation still applies: it creates the type of the source kind (the model adds the system fields), copies every user field (key, name, description, value type, multiplicity, `max_items`, requiredness, translatability, label visibility, weight, `settings`), applies the editable attributes of the source system fields (name, description, weight, label visibility, settings) to the new ones and, last, copies the type `settings` (list and public display; the model validates them against the fields, so they cannot be set on create). Last, still inside the transaction, `Webtack\Ecms\Content\ThemeTemplateCopier` copies the [theme templates bound to the source key](site-themes.md#cloning-a-type) to the new key in every theme under `config('theme.path')`: `views/{old}/` becomes `views/{new}/` (without the node-bound files `*--{id}`) and `views/blocks/block-{old}.blade.php` becomes `views/blocks/block-{new}.blade.php` (without `block-{old}--{slug}`). Files are copied byte for byte and nothing is overwritten: if a target exists or a file cannot be written, the files already created are removed, the transaction is rolled back and the controller returns back to the page with the dialog values kept and an `error` message naming the theme and the path (`ThemeTemplateCopyException`). Not copied: nodes, values, the type's own values (SEO), the description, role levels, favorites, page templates `pages/page-{old}` and type keys written inside theme code. On any failure nothing is created. The user is redirected to the fields page of the new type with a `success` message.

## Deletion

`DELETE /admin/content-types/{key}` (`admin.content-types.destroy`) from the "Delete" item of the row menu after confirmation in the dialog (`Components/ui/alert-dialog.tsx`, shadcn on `radix-ui`).

- The dialog names the type and warns that the fields will be deleted together with it. If the row says the type has nodes (`nodes_count`) or child types (`children_count`), the dialog shows the reason ("Delete this type's nodes first." / "Delete or move this type's child types first.") and has no confirm button; only "Cancel" remains.
- **The server checks the prohibition itself**, regardless of the dialog: if there are nodes or child types, the type remains unchanged, and the user is returned back (`back()`) with an `error` message. Otherwise the type is deleted together with its fields (the cascade at the DB level), and the user goes to the list with `success`.
- The prohibition applies at the admin panel level, not at the model level: the model cascade (deleting a type deletes its nodes) is unchanged, because other scenarios may deliberately delete a type together with its data (see [content-model.md](content-model.md#deletion-cascades)).
- The `success`/`error` messages are translated on the server (`__()`) and shown as toasts.

## Type section menu

`Components/Admin/ContentTypes/ContentTypeNav.tsx` builds its tabs from `typeSectionItems(kind)` (`Components/Admin/ContentTypes/typeSectionItems.ts`: ordered `settings`, `display`, `seo`, `sitemap`, `fields`, `nodes`, `children`, without `seo` and `sitemap` for `block`), the list the row menu of [`ContentTypeRowActions`](#row-actions-and-the-create-button) is rendered from too. The permission filter stays in the component: without the `types` permission only "Nodes" is shown. It shows a **breadcrumb trail** (`nav`, `data-testid="type-breadcrumbs"`, only with the `types` right): the link to the list of types, then each ancestor of the type from the root down to its direct parent, each linking to `{basePath}/{key}/edit`; the type itself is not in the trail (its name is the heading), and a root type has only the list link. Below it is the horizontal menu "Settings" (`/admin/content-types/{key}/edit`) / "Display" (`{basePath}/{key}/display`, all kinds) / "SEO" (`{basePath}/{key}/seo`, `content` and `page`) / "Sitemap" (`{basePath}/{key}/sitemap`, `content` and `page`) / "Fields" (`/admin/content-types/{key}/fields`) / "Nodes" (`/admin/content-types/{key}/nodes`; in the page and block sections — `{basePath}/{key}/nodes`) / "Child types (N)" (`{basePath}/{key}/children`, `data-testid="child-types-tab"`, always shown with the `types` right, also for 0 children; `N` is `type.children_count`). Props: `section` ([see below](#generalization-by-kind)), `type` (`NavType`: `{ key, name, slug, children_count, ancestors }`, `ancestors` root first as `{key, name}`), `active` (`'settings' | 'display' | 'seo' | 'sitemap' | 'fields' | 'nodes' | 'children'`), optional `children` (rendered next to the heading, e.g. the favorites star of the node list); the active item has `aria-current="page"` and an underline. Above the tabs the component shows the **name of the type** (`type.name`, not the public `section_title`) as the page `h1`, so the pages that use it (edit, Display, SEO, fields list, node list) have no title of their own. After the last tab it shows a "Preview" tab (`Eye` icon, icon only below `sm`, `target="_blank"`, `rel="noopener noreferrer"`, not a tab, no `aria-current`) to the public list page `/{type.slug}`; it is shown only when `typePublicUrl(section, type.slug)` is not `null` (kind `content` with a non-empty slug) and needs no permission. Every controller action that renders the menu (type edit, Display, SEO; fields index/create/edit; nodes index/create/edit) sends the `type` prop through one helper, `ContentType::navProps()` (`children_count` is one count query, `ancestors` walks `parent_type` with a cycle guard); the TypeScript shape `NavType` is exported from `ContentTypeNav.tsx` and imported by the pages. The component is connected on the type's edit pages (`settings`), the list of fields and the create/edit forms of a field (`fields`, see [admin-content-fields.md](admin-content-fields.md)), the node list and the create/edit forms of a node (`nodes`, see [admin-content-nodes.md](admin-content-nodes.md)). There is no menu on the type creation page — the type does not exist yet.

## Child types tab

`GET {basePath}/{key}/children` (`admin.content-types.children`, `admin.page-types.children`, `admin.block-types.children`; `ContentTypeController::children`) is the "Child types" tab of the [type section menu](#type-section-menu). It is registered in the shared route loop, so it needs the `types` right (403 without it, a guest goes to `/login`) and the kind-bound `{contentType}` gives 404 for a key of another kind.

It renders the same page and table as the list (`Pages/Admin/ContentTypes/Index.tsx`, the same columns, search, sorting, column visibility, row menu, clone dialog and favorites star), restricted to the **direct** children of the type (`children()` with the counts; not the type, not deeper descendants). The action adds the props `parent` (`{key, name, slug}`) and `type` (`ContentType::navProps()`); with `parent` set the page shows `ContentTypeNav` (`active="children"`, which provides the heading) instead of the list title, uses the table id `{kind}-type-children`, and the "Create" button (also in the empty state) links to `{basePath}/create?parent_type={key}` ([preselected parent](#creation)). The list and the tab build their rows with one private builder in the controller. Deleting a row on the tab sends `from_children`, and `destroy` then redirects back to the tab of the parent instead of the list.

## Relation to nodes

The nodes of types live in the section of their kind: `/admin/content-types/{key}/nodes…`, `/admin/page-types/{key}/nodes…`, `/admin/block-types/{key}/nodes…` ([admin-content-nodes.md](admin-content-nodes.md)). The prohibition on deleting a type with nodes ([Deletion](#deletion)) applies until the nodes are deleted on their page.

## Generalization by kind

The same `ContentTypeController`, `ContentFieldController`, form requests, and React pages serve the three sections. One loop in `routes/service.php` registers the routes (`content-types` → `content`, `page-types` → `page`, `block-types` → `block`), and each route has a default `kind` value. The kind and the route name prefix are given by the trait `Controllers\Admin\Concerns\ResolvesTypeSection` (`kind()`, `routeName()`, `section()`), so redirects lead to their own section (`admin.page-types.index` and so on). The controller passes to Inertia the prop `section` = `{ kind, basePath }`; `ContentTypeForm`, `ContentTypeNav`, `ContentTypeRowActions`, `ContentFieldForm`, `ContentFieldRowActions`, and the pages use `section.basePath` instead of a hard-coded `/admin/content-types`. The texts that name the kind ("Create page type", "Delete page type") are given by `sectionLabels(kind)` (`Components/Admin/ContentTypes/section.ts`) — translation keys.

**Slug field of the form (kind `content`).** The field is a plain input; its hint says the slug is lowercase letters, digits and hyphens in each segment with segments separated by `/`. When a parent type is selected, a second hint (`data-testid="slug-parent-hint"`) shows the required prefix (`The slug must start with "common/".`), or says that the parent has no slug and must get one first. Errors of the slug rules appear next to the field and the other values stay in the form.

For `page` and `block` only these differ: there is no slug (a table column, a form field, and the `slug` validation rule — only for `content`), and the parent can be chosen only among types of the same kind.

## Navigation

The item "Content Types" in the sidebar is no longer a layout placeholder: it is active on `/admin/content-types`, and the breadcrumbs show its name (see [admin-shell.md](admin-shell.md)).
