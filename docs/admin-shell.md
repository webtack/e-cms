# Admin shell

The admin part of the CMS is built on Inertia.js (React) + TypeScript on top of Vite and Tailwind 4.

## Stack and build

- Backend: Laravel + `inertiajs/inertia-laravel`.
- Frontend: `react`, `react-dom`, `@inertiajs/react`, `typescript`, `@vitejs/plugin-react`.
- All npm commands run **on the host** (there is no npm in the `app` container). Installation requires `--legacy-peer-deps`:

```bash
npm install --legacy-peer-deps
```

- Build (type check + Vite): `npm run build:package` in the package; the output is the committed `dist/build`, published to hosts as `public/vendor/ecms/build` ([package-frontend.md](package-frontend.md)). The public site theme assets are built by the same tooling (`npm run build:themes`, [site-themes.md](site-themes.md#theme-assets-vite)).
- Dev server with HMR: `ECMS_HOT_FILE=<host>/public/vendor/ecms/hot npm run dev` ([package-frontend.md](package-frontend.md#development-with-hot-reload)).
- Root view: `ecms::app` (`resources/views/app.blade.php`) with its own Vite instance (`AdminAssets`); a host needs no Node.
- Type check only: `npx tsc --noEmit`.

### Structure of `resources/js`

| Path | Purpose |
| --- | --- |
| `app.tsx` | Inertia entry point (`createInertiaApp`); pages are loaded from `Pages/**/*.tsx` |
| `Pages/` | Pages; the component name in `Inertia::render('Admin/Dashboard')` = `Pages/Admin/Dashboard.tsx` |
| `Layouts/AdminLayout.tsx` | Persistent admin shell |
| `Components/ui/` | shadcn/ui primitives (generated by the CLI) |
| `Components/Admin/` | Shell components: sidebar, header, breadcrumbs, user menu, language switcher, theme, toasts |
| `Components/Admin/DataTable/` | Universal data table: `DataTable.tsx`, toolbar, filters, column menu, pagination, state and visibility hooks, `clientEngine.ts`, `params.ts`, `types.ts` (see [admin-data-table.md](admin-data-table.md#structure)) |
| `Components/Admin/FileUpload/` | File upload widget `FileUpload.tsx` (see [file-storage.md](file-storage.md#widget-and-demo-page)) |
| `lib/utils.ts`, `lib/i18n.ts`, `lib/toastDurations.ts`, `hooks/` | `cn()`, the `translate()` function, toast durations, and hooks (`useTranslation`, `use-mobile`) |
| `types/` | Types of shared Inertia props |

The alias `@` points to `resources/js` (configured in `vite.config.js` and `tsconfig.json`), for example `import { cn } from '@/lib/utils'`.

## shadcn/ui

The config is `components.json` (TypeScript, zinc base, CSS variables, Tailwind 4). Aliases: `@/Components`, `@/Components/ui`, `@/lib/utils`, `@/hooks`. **The `Components` directory is written with a capital letter** everywhere (macOS is case-insensitive, the Linux container is case-sensitive). Theme tokens and `@custom-variant dark` are in `resources/css/app.css`; the palette is described in [Admin visual style](admin-visual-style.md).

To add a component (on the host; `npm_config_legacy_peer_deps=true` is needed because of peer dependencies):

```bash
npm_config_legacy_peer_deps=true npx shadcn@latest add <name>
```

After generation, check the imports: `grep -rn "@/components" resources/js` must be empty. The `sonner` component was changed manually: the theme is taken from our `useTheme`, not from `next-themes` (which we do not use). When running `add sonner --overwrite` again, this change must be restored.

## Layout

`Layouts/AdminLayout.tsx` is a persistent layout: a page sets `Page.layout = (page) => <AdminLayout>{page}</AdminLayout>`, so the shell is not remounted between Inertia visits (the sidebar state is kept; also the `sidebar_state` cookie). Inside: `ThemeProvider`, `TooltipProvider`, `SidebarProvider` + `AppSidebar`, `AdminHeader`, `FlashToaster`, `Toaster`.

## Sticky form action bar

`Components/Admin/FormActionBar.tsx` is the bottom action bar of all admin forms (`ContentTypeForm`, `ContentFieldForm`, `ContentNodeForm`): "Cancel" (a link to the list, `cancelHref`) and "Save" (`type="submit"`, disabled while submitting, `processing`). The bar is `sticky bottom-0` with a background, a top border, and a padding `env(safe-area-inset-bottom)`, so it stays in the window when scrolling at all screen sizes; `-mx-4 md:-mx-6` and `-mb-4 md:-mb-6` align it with the edges of `<main>` (whose paddings are `p-4 md:p-6`). The `children` slot on the left is for additional buttons (the node form on `< lg` puts an icon button "Details" there). The bar must be the **last child element of `<form>`** and must not be an element of a `grid`: sticky does not go beyond the limits of its grid row, so the node form keeps the columns in a separate `div`, and the bar is outside it. The type and field forms limit the width (`max-w-xl`) not on the `<form>` itself but on an inner `div`, so that the bar is full width; this `div` has a frame (`rounded-md border p-4`) and a bottom margin `mb-10` to the bar, while the bar itself stays outside the frame. `data-testid="form-action-bar"`.

## Sidebar

`Components/Admin/AppSidebar.tsx` is built on the shadcn `Sidebar` primitive (`collapsible="icon"`): on desktop it is either expanded or collapsed to icons; on mobile it is a Sheet drawer behind a hamburger (`SidebarTrigger` in the header). The active item is determined by `usePage().url` (`isActive`, `activeItem` in `navigation.ts`). Item titles are **translation keys** (English phrases): `AppSidebar` shows `t(item.title)`; the language is chosen by the switcher in the header (see [multilingual admin](admin-i18n.md)).

The **header** shows the logo (`Components/Admin/BrandLogo.tsx`: `resources/images/logo-mini.png`, and `logo-mini-white.png` in the dark theme; the images are imported in the code and bundled by Vite (a host needs no `public/images`); they are not the logos from the site settings) and, under it, the site name from the shared prop `site.name` (`data-testid="sidebar-site-name"`). The whole header block is hidden when the sidebar is collapsed to icons.

**No keyboard shortcut.** The sidebar is toggled only by the `SidebarTrigger` button in the header. The shadcn Ctrl/Cmd+B listener was removed from `Components/ui/sidebar.tsx`, so the combination reaches the page content (for example, bold text in the rich text editor).

**Mobile drawer.** The drawer shows the `Sheet` close button (top right; the header block has right padding on mobile so the button does not cover the site name) and closes after every Inertia navigation: `SidebarProvider` subscribes to `router.on('navigate')` and calls `setOpenMobile(false)`, which also covers the browser back button and programmatic visits.

Order from top to bottom (below the header):

1. **Dashboard**.
2. **Favorites** — the user's types, see [admin-favorites.md](admin-favorites.md); without items the block is not shown.
3. **Navigation** — the admin menu (the block heading with an icon, as in "Favorites"; the Ukrainian translation is in `lang/uk.json`): links to types, links to nodes and collapsible groups configured by the administrator, see [admin-navigation-menu.md](admin-navigation-menu.md). "Favorites" and the menu come from the prop `navigation` (`{ favorites, menu }`, a lazy shared prop of `HandleInertiaRequests`), already filtered on the server by access. The icon of a type link is determined by the kind of type (`content` — `Table2`, `page` — `FileStack`, `block` — `Blocks`); every node link has the same `FileText` icon and leads to the edit form of the node, its label is the node title; groups — `Folder`/`FolderOpen`.
4. **Media Library** — [media library](media-library.md); shown when the media level is not `none`.
5. **Sections at the root** (`sections` in `navigation.ts`, each is a `SidebarGroup` with a heading):
   - "Structure": Content Types ([content types](admin-content-types.md)), Page Types ([pages](admin-page-types.md)), Block Types ([blocks](admin-block-types.md)), Taxonomy ([vocabularies](admin-taxonomy.md)), Menus ([menus](admin-menus.md));
   - "Access": Users ([users](admin-users.md)), Roles ([roles](admin-roles.md)), Site ([site settings](admin-site-settings.md), `/admin/settings`).
6. **Footer** — the icon link "Admin menu" to `/admin/settings/navigation` (`data-testid="sidebar-admin-menu-link"`), only with the `settings` right.

There is no collapsible Settings item and no Pages item. The spacing between blocks is compact (`SidebarContent` without `gap`).

Visibility: each list has its own `visible(can)` field — types by the `types` right or the `own`/`any` level on a type of the kind; Taxonomy, Menus, Users, Roles, Site by system rights. A section without visible items (`visibleSections(can)`) is not shown; Media Library — by the media level; Dashboard always. Hiding is only a convenience: an unavailable address responds with 403.

Expanded groups: the admin menu group expands when it contains the active item (on each visit); manual collapsing is not remembered. The list of nodes of a type that has a link in "Favorites" or in the menu belongs to that link: the section item (for example, Content Types) is not highlighted through it. A node link is active only on the exact path of its edit form; on that page the link to the node's type (in the menu and in "Favorites") and the section item are not active, so exactly one item is highlighted (`linkActive` in `AppSidebar.tsx`). A group that holds the active node link is expanded. Likewise, the `/admin/settings/navigation` page belongs to the footer link, not to the Site item. Without such a link, the item of the types section remains active, as before.

### How to add a menu item

1. Add an entry to the `navigation` array (top level) or to the `items` of a section in `sections` in `Components/Admin/navigation.ts` (`title` is an English key phrase, `href`, `icon` from `lucide-react`, `visible` if needed; without `mock` when the route exists), and add the key to `lang/en.json` and `lang/uk.json`.
2. Create the route and the page with `Page.layout`.
3. Breadcrumbs pick up the title automatically (`getBreadcrumbs` searches all leaves; it returns keys, and the `Breadcrumbs` component performs the translation); for pages outside the menu, add a title key to `extraTitles` and translations to both `lang/*.json` (this is done for `/admin/settings/navigation` → "Admin menu" under Site). The `patternTitles` for type fields and nodes are generalized to `(content|page|block)-types`, so node breadcrumbs lead through the item of their section ("Admin → Page Types → Create node").

## Breadcrumbs and header

`AdminHeader` contains `SidebarTrigger`, `Breadcrumbs` (from the URL and `navigation.ts`, without props from controllers), the icon button "Open site" (`ExternalLink`; a regular `<a href="/" target="_blank" rel="noopener noreferrer">` link to the home page of the public site, opens in a new tab, the admin stays open), `LocaleSwitcher` (a language dropdown, `Components/Admin/LocaleSwitcher.tsx`; the choice goes to `POST /locale` with the sidebar state preserved), `ThemeToggle`, and `UserMenu` (name and the user's avatar, `auth.user.avatar`, through `UserAvatar` with the initials as the fallback, a link to the working [profile page](admin-profile.md) at `/admin/profile`, logout via `router.post('/logout')`).

## Theme

`ThemeProvider` / `useTheme` (`Components/Admin/ThemeProvider.tsx`): the `dark` class on `<html>`, the choice in `localStorage` (key `theme`: `light` / `dark` / `system`); without a choice — the system theme. An inline script in the root view `resources/views/app.blade.php` (`ecms::app`) sets the class before the first render, so there is no flash.

## Toasts

`<Toaster />` (Sonner) is mounted in the layout. `FlashToaster` shows `toast.success` / `toast.error` for `flash.success` / `flash.error`. On the backend, it is enough to `return redirect(...)->with('success', 'Saved')`. A successful **update** in the edit forms (content type, page and block type, field, node, menu, menu item, vocabulary, term, role, user) ends with `return back()->with('success', …)`: the user stays on the same page, Inertia updates the form props with the saved values, and the toast shows success. Creation and deletion, as before, lead to the list (see the admin sections); the type settings tabs and the site settings page also return `back()`. The flash lives for one request, so there are no repeats. A toast is triggered by `flash.id`, not by the text: the server generates a fresh id (a UUID, lazily) for every response that carries a `success` or `error` message, and `FlashToaster` runs one effect keyed on it. Therefore every new flash message produces a toast, even when its text equals the previous one (for example, saving an edit form twice in a row); without a message `flash.id` is `null` and nothing is shown.

Look and behavior are configured in one place, the wrapper `Components/ui/sonner.tsx`:

- **Position**: top-right corner, no offset. A toast may overlap the header, but it never covers the Save button of the bottom action bar.
- **Status colors**: `success`, `error`, `warning` and `info` toasts get a border, a tinted background (mixed into `--popover`, so it stays opaque) and an icon color from the tokens `--success`, `--destructive`, `--warning` and `--info`. Both themes are covered by the tokens; Sonner `richColors` is not used.
- **Size**: width about 440px (`--width`), larger text and padding, `size-5` icons. On narrow screens Sonner stretches the toast to the viewport.
- **Close button**: every toast has one (`closeButton`).
- **Durations**: success 4 s, error 8 s. Sonner has one `duration` per toast and no per-status default, so the constants `TOAST_SUCCESS_DURATION` and `TOAST_ERROR_DURATION` from `lib/toastDurations.ts` are passed where toasts are created: `FlashToaster` and the direct `toast.error` calls in the ContentFields, Terms and Menu Items pages. New `toast.success` / `toast.error` calls must pass them too.

## Routes and shared props

| Method | URL | Name | Page |
| --- | --- | --- | --- |
| GET | `/admin` | — | redirect to `/admin/dashboard` |
| GET | `/admin/dashboard` | `admin.dashboard` | `Admin/Dashboard` (widgets, see [dashboard](admin-dashboard.md)) |
| GET | `/admin/profile` | `admin.profile` | `Admin/Profile` (see [profile](admin-profile.md); also `PUT /admin/profile` and `PUT /admin/profile/password`) |
| GET | `/admin/ui/data-table` | `admin.ui.data-table` | `Admin/Ui/DataTableDemo` (data table demo; 404 in production, not in navigation; see [admin-data-table.md](admin-data-table.md#demo-page)) |

The group has the middleware `auth` + `verified` (see [authentication](admin-auth.md)); individual sections are additionally protected by role rights (`can:types`, `can:taxonomy`, `can:menus`, levels for nodes and the media library; see [access control by roles](access-control.md)). The dashboard (its content is limited by the user's rights, see [dashboard](admin-dashboard.md)), profile, and `lookup/*` are open to every active user; the demo `ui/*` routes require the `types` right. Check: `php artisan route:list --path=admin`.

`HandleInertiaRequests` shares with every page: `auth.user` (only `id`, `name`, `email`, and `can` — the user's rights for showing or hiding elements: `system`, `nodes`, `kinds`, `media`, `edit`; see [access control by roles](access-control.md)), `locale` (`current`, `available`, `messages`; see [multilingual admin](admin-i18n.md)), `site.name` (the site name from `/admin/settings` in the current language, falling back to `config('app.name')`; a lazy prop that does not depend on the user, so the login page gets it too), and `flash.id` / `flash.success` / `flash.error` (`flash.id` is a fresh UUID for each response with a message, `null` otherwise; it makes the toast fire for repeated texts). The types are in `resources/js/types/index.d.ts`.

## Content area width

`AdminLayout` gives `SidebarInset` (the content area next to the sidebar) `min-w-0`. As a flex item it would otherwise grow to its content's minimum width, so a wide [data table](admin-data-table.md) would widen the whole page on desktop instead of scrolling inside its own container.
