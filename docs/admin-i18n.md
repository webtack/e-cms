# Admin interface localization

The language of the admin interface is determined on the server for each request, stored in the user's profile (or in a cookie for a guest), and passed to React together with the translations. Scope: the admin interface and the login page. Translation of CMS content, localized URLs, date/number formats, plurals, RTL, and SSR are not covered here.

## Available languages

The list is the package configuration key `ecms.locales` (`config/ecms.php`; code → the language's own name, shown in the switcher). It does not depend on the host's `config/app.php`, so a stock Laravel application needs no extra key. The default is English and Ukrainian; a host changes it by publishing `config/ecms.php` (`php artisan vendor:publish --tag=ecms-config`). The host's value replaces the whole list, so it must name every language it wants:

```php
'locales' => [
    'en' => 'English',
    'uk' => '<native name>',
    'pl' => 'Polski',
],
```

- `APP_LOCALE` (default `en`) — the language used when nothing else is determined.
- `APP_FALLBACK_LOCALE` (`en`) — the fallback language when a translation is missing.

## How the request language is determined

Priority (the first valid value wins):

1. `users.locale` of the authenticated user;
2. the `locale` cookie (the guest's choice);
3. the best match with the `Accept-Language` header (`uk-UA` matches `uk`);
4. `config('app.locale')` (`APP_LOCALE`).

Values that are not in `ecms.locales` are ignored.

The public site is the exception: on routes named `public.*` the middleware skips this priority and always sets `config('app.locale')`, so the admin's language, the `locale` cookie and the browser language never affect it.

## Where the choice is stored

- `users.locale` — `string(5)`, nullable. `null` means "the user has not chosen"; then the cookie and `Accept-Language` apply. The field is not part of the mass assignment of the `User` model: only `LocaleController` writes it.
- The `locale` cookie — set for everyone (both guests and authenticated users), long-lived, encrypted by the standard cookie middleware. Thanks to this, after logout the login page stays in the same language (the session is destroyed on logout). JavaScript does not read the cookie: the server provides the language in a shared prop.

## Server side

- **Middleware `Webtack\Ecms\Http\Middleware\SetLocale`** — in the `web` group (`bootstrap/app.php`), after the session and cookie encryption and **before** `HandleInertiaRequests`, which reads `app()->getLocale()`. It applies the priority from the section above via `app()->setLocale()`.
- **`POST /locale`** (`locale.update`, `Webtack\Ecms\Http\Controllers\LocaleController@update`) — available to guests too, `throttle:30,1`. The `locale` field is validated by the rule `Rule::in(array_keys(config('ecms.locales')))`; a validation error changes nothing. For an authenticated user it writes `users.locale`, for everyone it sets the long-lived `locale` cookie, and responds with `back()`.
- **Shared prop `locale`** (`HandleInertiaRequests::share`):

  ```ts
  locale: {
      current: string;                              // 'uk'
      available: { code: string; name: string }[];  // [{ code: 'en', name: 'English' }, …]
      messages: Record<string, string>;             // contents of lang/{current}.json
  }
  ```

  The type is described in `resources/js/types/index.d.ts` (`LocaleProps`). The `<html lang>` attribute is taken from `app()->getLocale()` (`resources/views/app.blade.php`) on a full page load; after client-side Inertia visits (for example, after `POST /locale`) it is synchronized by `resources/js/app.tsx` on the `success` and `navigate` events.

Route check: `docker compose exec app php artisan route:list --name=locale`.

## Server translations (`lang/`)

Messages generated by the server (login error, attempt limit, validation) are in the standard Laravel files `lang/{locale}/*.php`:

- `lang/en/auth.php`, `lang/en/validation.php` — the reference, published by `php artisan lang:publish` (other files — `pagination.php`, `passwords.php` — are not needed, so they were removed; they can be published again with the same command).
- `lang/uk/auth.php` — a full translation (`failed`, `password`, `throttle`).
- `lang/uk/validation.php` — only the rules that are actually used, plus `attributes` (`email`, `password`, `locale`) for convenient field names. Missing keys are taken from `en` automatically (fallback).

Rule for developers: when you start using a new validation rule, add its line to `lang/uk/validation.php`, copying it from `lang/en/validation.php`.

### Override rule

The package ships the translations (`lang/{en,uk}.json`, `lang/{en,uk}/auth.php`, `lang/{en,uk}/validation.php`) and the host overrides them:

- **JSON dictionary** (`lang/{code}.json`): the package file is read first and the host's `lang_path("{code}.json")` file on top, so a host key always wins and a host key the package lacks is added. `Webtack\Ecms\Support\InterfaceTranslations` does this merge; `HandleInertiaRequests` sends its result to React, and `SetLocale` asks it whether a language has translations at all (the host's file or the package's), so `/en/...` on the public site takes the locale `en` from the package files when the host has none.
- **PHP groups** (`auth.php`, `validation.php`): the provider registers the package directory without a namespace, so `__('auth.failed')` and the validator keep reading the plain groups. Laravel searches the framework, then the host's `lang/`, then the package, and a later path wins on a key several define: **a key defined in the package's `auth.php`/`validation.php` overrides the same key of the host's file**; keys the package does not define are translated freely by the host. This limit is accepted: on overlapping keys the package text wins, and a host that needs different wording for such a key edits the package texts upstream.

### How to add a language

1. Add an entry to `ecms.locales` (the host's `config/ecms.php`), for example `'pl' => 'Polski'`.
2. Copy the package's `lang/en.json` to the host's `lang/pl.json` and translate the values (do not change the keys). The `TranslationParityTest` requires the same set of keys in all languages.
3. If needed, create `lang/pl/auth.php` and `lang/pl/validation.php` (without them the fallback to `en` works).
4. Check: `docker compose exec app php artisan test --compact tests/Feature/Locale`.

No code change is needed: the language switcher is built from `ecms.locales`.

## Translations in React

The source is `lang/{locale}.json` (a flat dictionary "English phrase → translation"). The key is the English phrase itself, as in Laravel JSON translations; `lang/en.json` contains the same keys with the same values and is the template for a new language. Placeholders are written as `:name`.

```tsx
import { useTranslation } from '@/hooks/useTranslation';

export default function Example() {
    const { t, locale, locales } = useTranslation();

    return (
        <>
            <h1>{t('Dashboard')}</h1>
            <p>{t('Retry in :seconds s', { seconds: 30 })}</p>
        </>
    );
}
```

- `t(key, replace?)` returns the translation or the key itself if there is no entry (the page does not break). Longer placeholder names are substituted first (`:minutes` is not affected by `:min`).
- `locale` — the code of the current language, `locales` — the list of `{ code, name }`.
- The pure function `translate(messages, key, replace?)` is in `resources/js/lib/i18n.ts` and does not depend on React.

**Rule:** every string visible to the user (text, `aria-label`, `<Head title>`, `placeholder`, `sr-only`) goes through `t()`. When adding a string, add the key to **both** files `lang/en.json` and `lang/uk.json` — otherwise `TranslationParityTest` will fail. The brand name `E-CMS` is not translated. Menu item names in `navigation.ts` are stored as keys and translated in the components (see [admin-shell.md](admin-shell.md)).

## Language switcher

`Components/Admin/LocaleSwitcher.tsx` is a dropdown with the `Languages` icon (`aria-label` "Change language"). It shows all languages from `locale.available` by their own names; the current one is marked. The choice is sent via `router.post('/locale', { locale }, { preserveScroll: true, preserveState: true })`: the persistent layout is not remounted, so the sidebar state is preserved. Location: the admin header (`AdminHeader`) and the top right corner of the login page (`Pages/Auth/Login.tsx`).
