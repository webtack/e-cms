# Nodes in the admin panel (content, pages, blocks)

The `/admin/content-types/{key}/nodes`, `/admin/page-types/{key}/nodes`, and `/admin/block-types/{key}/nodes` sections show nodes of types of kinds `content`, `page`, and `block`. The forms write the `default` language; translations are edited one language at a time in the [translation mode](#translation-mode). Nodes live under the type within the section of their kind; the controller, React pages, form, and field widgets are shared by all three, and the route defines the kind. A type of another kind in a section (for example, the key of a type `block` in `/admin/page-types/**/nodes`) gives 404. Access — `auth` + `verified` and the role level per type (`node:{key}`): `none` — 403 for the list, forms, and nodes; `own` — creating, changing, and deleting only own nodes (the author is `content_nodes.user_id`), the list shows all nodes, and a row carries `can_edit` (the decision of `ContentNodePolicy`), without which the client hides the actions; `any` — any nodes. The publication rights (`is_active`, `published_at`, `unpublished_at`) are the same as for the node. A guest is redirected to `/login`. See [access control by roles](access-control.md). The node model is described in [content-model.md](content-model.md), values and writing — in [content-values.md](content-values.md), querying — in [content-querying.md](content-querying.md); the type page from which one gets here is [admin-content-types.md](admin-content-types.md).

## Routes

All routes are nested under the type: `/admin/{section}/{contentType}/nodes…`, where `section` is `content-types`, `page-types`, or `block-types`; names `admin.{section}.nodes.*` (27 routes in total, nine in each section). They are registered by one loop in `routes/service.php`, and the kind (`content`, `page`, `block`) is taken from the route's `defaults('kind', …)` (the same as in the [types section](admin-content-types.md)); redirects after saving, updating, and deleting lead to the list of their own section (`routeName($request, 'nodes.index')`).

| Method and path | Name | Action |
| --- | --- | --- |
| `GET …/nodes` | `index` | list of nodes |
| `GET …/nodes/create` | `create` | create form |
| `POST …/nodes` | `store` | create |
| `GET …/nodes/{node}/edit` | `edit` | edit form |
| `PUT …/nodes/{node}` | `update` | update |
| `DELETE …/nodes/{node}` | `destroy` | delete |
| `PATCH …/nodes/{node}/active` | `active` | set only `is_active` ([see below](#one-click-state-toggle)) |
| `PUT …/nodes/{node}/translations/{lang}` | `translations.save` | save one language ([translation mode](#translation-mode)) |
| `DELETE …/nodes/{node}/translations/{lang}` | `translations.clear` | clear one language |

`{contentType}` is bound by `key` within the kind's section ([admin-content-types.md](admin-content-types.md#editing)): a type key of another kind gives 404. `{node}` is bound by an explicit `Route::bind('node', …)` in `routes/service.php`: it looks up the node by the **pair** (the type key from the already resolved parameter, `uuid`), so an unknown `uuid`, the `uuid` of a node of another type (including another section), and even a `slug` instead of a `uuid` give 404.

**A node is addressed by `uuid`, not by `slug`.** The `uuid` is immutable, while the `slug` is the public identifier for the site frontend, which the owner can change; admin addresses do not depend on it, so a form open in another tab does not break after the slug is changed ([content-model.md](content-model.md)).

The logic is in `Webtack\Ecms\Http\Controllers\Admin\ContentNodeController`.

### Difference from `ContentTypeController`

The list of types is an in-memory collection passed to `TablePage::fromCollection()`. There may be many nodes, and their values lie in EAV tables, so here search, sorting, and pagination are performed by the database through `ContentNodeQuery`; `TableRequest` only parses the address, and `TablePage::make()` wraps the already selected page ([admin-data-table.md](admin-data-table.md)).

## Index response

The Inertia page `Admin/ContentNodes/Index` receives:

- `type` — `{key, name}` of the type, `section` — `{kind, basePath}`;
- `columns` — all columns of the table in display order, including service ones: `{key, name, type, sortable, service?}`. `type` — the column type (`text`, `number`, `boolean`, `date`, and for the `image` and `file` fields — `image` and `file`; the table sees them as `text`, and the page renders them); `sortable` — `false` for file fields (`file`, `image`), `youtube`, `term`, and for the `slug` column; a service column has `service: true`, and its `name` is an English translation key (the client translates the header), while the name of a field is data, shown as is;
- `table` — the result of `TablePage::make()` (`rows`, `meta`, `query`, `ignored`, `operators`).

A table row: `uuid` (the row identifier and the addresses), service values — `slug`, `public_url` (the relative public address of the node or `null`, see [below](#preview-button-and-the-publicurl-prop)), `status` (`published` / `scheduled` / `expired` / `disabled`), `is_active` (boolean), `created_at`, `updated_at`, `published_at`, and `unpublished_at` (dates `Y-m-d H:i`, UTC; an empty `unpublished_at` is `null`), `views` (an integer), and `author` (`{name, avatar}` of the author, `avatar` being the picture URL or `null`, or `null` when the author is unknown; the authors of the page are loaded with one query, only when the column is visible) — and the value of each visible field by its key. Service values are always in the row, and only the keys present in `visible` become columns. The status is derived (`ContentNode::status()`): a disabled node is `disabled` regardless of the dates; an active one with a future `published_at` is `scheduled`; with `unpublished_at` in the past or at the current moment — `expired` ("Expired"); otherwise `published`.

### How columns are built

The columns are `settings.list.visible` of the type, which includes `title` ([content-querying.md](content-querying.md#default-list-settings)) in the order given there. `visible` holds field keys and node service keys: `slug`, `status` (the status), `is_active` ("Active"), `created_at` ("Creation date"), `updated_at` ("Update date"), `published_at` ("Publication date"), `unpublished_at` ("Unpublishing date"), `views` ("Views": an integer without separators, `0` shown as `0`, sortable numerically, column type `number`), and `author` ("Author": the name next to a round `UserAvatar` with the author's picture, or the initials without one; an empty cell when the author is unknown; not sortable). Users can hide it for themselves in the "Columns" menu. A service column exists only when its key is in `visible`, and exactly at the given position; the client adds nothing on its own (the status is shown as a badge, `is_active` as "Yes"/"No", dates as text). The `title` column is always shown and is never hidden: it stands at the position of its key in `visible`, and if the key is not there — first (duplicates are ignored). If `visible` is absent or empty (not counting `title`), `title`, slug, status, publication date, and author are shown. The settings are set in the type form ([admin-content-types.md](admin-content-types.md#node-list-in-the-form)). The settings are cleaned of stale references, because deleting a field does not clean `settings.list`:

- a field key that no longer exists is skipped in `visible`;
- `search` keeps the existing text fields; `sort` keeps the existing field whose column is sortable (not a file field, not `youtube`, not `url`, and not `term`; a multiple field is fine), or the service key `status`, `is_active`, `created_at`, `updated_at`, `published_at`, `unpublished_at`, `views` (not `slug`); if nothing remains after cleaning, the default values apply (all text fields, the creation order);
- a key from the list of [reserved](content-model.md#reserved-field-keys) keys (`uuid`, `slug`, `status`, `is_active`, `created_at`, `updated_at`, `published_at`, `unpublished_at`, `views`, `author`) always means the service column: an existing field with such a key does not duplicate it and is not offered as a separate column. New such fields cannot be created, but previously created ones remain valid.

`ContentNodeQuery` itself reads the type's `settings.list` as a fallback, so the controller passes it a copy of the type with the already cleaned settings (the saved type does not change).

| others | the string as is (`decimal` — the canonical string) |

### Search, sorting, pagination

- **Search** (`q`) is case-insensitive over `settings.list.search`, and without it over all text fields of the type (the decision of `ContentNodeQuery`), and **always also over the node `slug`** (the admin never passes `searchFields`). `%` and `_` are literal in the slug as in values.
- **Sorting** (`sort`, `dir`) is available for the visible field columns, except file fields (`file`, `image`), `youtube`, `url`, and `term`, including multiple ones (the key is the first value, see [content-querying.md](content-querying.md#sorting)); `type_ref` and `node_ref` sort by the target's label ([see above](#type_ref-and-node_ref-fields)), and by the visible service columns `status`, `is_active`, `created_at`, `updated_at`, `published_at`, `unpublished_at` ([content-querying.md](content-querying.md#sorting-by-service-attributes)); slug, file fields, `youtube`, and `term` are not sortable, such a `sort` is ignored and gets into `table.ignored`. For equal keys the order is `title` ascending, then by `id`; the exception is `created_at`, `updated_at`, and `unpublished_at`, where equal values are ordered by `id` in the direction of sorting, without `title`. Without `sort` the order is taken from `settings.list.sort`, and without it — the creation order; nodes without a value go last in both directions.
- **Page** out of range returns the last one: the controller repeats the query for `lastPage()` (one extra query only in this case).
- **Filters** are absent from the table: the `filters[…]` parameters are ignored (the columns are not `filterable`).
- Invalid address parameters are ignored without an error.

## Create and edit form

`create` gives the page `Admin/ContentNodes/Create`: `type`, `section`, and `fields`. `edit` adds `Admin/ContentNodes/Edit` with `values`. Both pages receive `node`: `{slug, is_active, published_at, unpublished_at, updated_at, author}` (`published_at`, `unpublished_at`, and `updated_at` — `Y-m-d\TH:i`; `unpublished_at` may be `null`; `author` — `{name, avatar}` or `null`; in `create` — `slug: ''`, `is_active: true`, `published_at` — now, `unpublished_at: null`, `updated_at: null`, the author — the current user; in `edit` additionally `uuid` and the numeric database `id`, shown read-only in the "Details" block and never sent back; `create` has no `id`). The fields come ordered by weight (`weight`, then `id`, as in `ContentType::fields()`); each has `key`, `name`, `description` (the instruction for the editor, `null` without it), `type`, `is_multiple`, `is_required`, and `settings` — only `min`/`max`, which the client uses for attribute hints. The server remains the arbiter of values.

`values` — a field key → value in the format of the HTML input element: `date` — `Y-m-d`, `datetime` — `Y-m-d\TH:i` (the `datetime-local` format), boolean — a boolean, `decimal` — a string, a multiple field — a list (empty if there are no values), an absent single value — `null`. The values are read by `ContentValueReader` in the `default` language.

### Form contract

The form sends `{ slug, is_active, published_at, unpublished_at, values: { <field key>: <value or list> }, file_meta: { <file uuid>: { name, description } } }`. The values lie under a separate key `values`, because a field key may coincide with `slug`. `file_meta` — the name and description of the files shown in the form (see [Image and file fields](#image-and-file-fields)); the form sends only files that remain in the values.

| Request | `slug` rules | `values` | `is_active` | `published_at` | `unpublished_at` |
| --- | --- | --- | --- | --- | --- |
| `StoreContentNodeRequest` | optional; format `^[a-z0-9]+(-[a-z0-9]+)*$`, up to 190 characters; unique among all nodes; for pages also must not match the slug of a `content` type or a reserved path (`AvailablePublicPath`); for `content` nodes the model rejects a slug that makes the address (`type slug/node slug`) equal to a type slug, with the error "This slug would hide the list of a content type." under `slug` (see [content-model.md](content-model.md#type-slug)) | an array (if needed) | `boolean`, default `true` | `nullable`, `date_format:Y-m-d\TH:i`; empty = now | `nullable`, the same format; later than `published_at` (an empty publication date = the current minute) |
| `UpdateContentNodeRequest` | required; the same format; unique, except the node itself (`ignore($node)`); for pages the first-segment collision check only when the slug is changed | an array (if needed) | `boolean`, without a value it stays as is | `required`, the same format; a cleared date — an error | `nullable`, the same format; later than `published_at`; an empty value clears it, an absent key does not touch it |

`user_id` is not part of the rules, so it does not get into `validated()`: the author is taken from the current user on creation and never changes (a submitted `user_id` is ignored).

The `file_meta` rules are shared (`StoreContentNodeRequest::fileMetaRules()`): an optional array; the key — a uuid of 32 characters `0-9a-f` (otherwise an error `file_meta`); `file_meta.*.name` — required, up to 255 characters; `file_meta.*.description` — optional, up to 2000 characters. The errors have the keys `file_meta.{uuid}.name` / `.description` and are shown next to the file fields.

The order of the dates is checked by `StoreContentNodeRequest::scheduleCheck()` (a comparison to the minute, an error under the key `unpublished_at`); the arbiter is `ContentNode::assertValid()`.

The requests check only `slug`, `is_active`, `published_at`, `unpublished_at`, that `values` is an array, and `file_meta`. The rules for the rest of the values are built by `ContentValueWriter::validate()` from `content_fields` ([content-values.md](content-values.md)) — the single source of rules; among them, for a multiple field with `max_items > 0` — `max:{max_items}` (the number of non-empty items must not exceed the limit; the error has the key `values.{key}`). `formFields()` gives each field `max_items`, so that the form respects the limit. The uniqueness of the slug on update is checked by the request, because the model leaves it to the DB index, and a violation on update would be a 500 rather than a form error.

An empty slug on creation arrives as `null` — then `ContentNodeCreator` generates it from `title` (`SlugGenerator`); for pages, the generated slug does not match the slug of a `content` type or a reserved path (the title "Admin" gives `admin-2`), and an explicit slug is not changed: a match gives an error on `slug`.

### Errors

The errors of `ContentNodeCreator` and `ContentValueWriter` have keys without a prefix (`title`, `scores.1`). The controller re-maps them with the prefix `values.` (`forForm()`), so that the keys match the nesting of `useForm({ slug, values })`: `values.title`, `values.scores.1` — the error of the second element of a multiple field. The errors of service attributes (`slug`, `is_active`, `published_at`) remain as they are. The entered text is kept in the form, because Inertia returns it back.

### Creation

`store` in one `DB::transaction` calls `ContentNodeCreator::create($type, $values, $slug, authorId: …, publishedAt: …, isActive: …)` in the `default` language (the author is `$request->user()`) (the values are validated before saving; the creator's transaction becomes a savepoint) and applies `file_meta` (see [Image and file fields](#image-and-file-fields)). Success — a redirect to the type's list with `success`.

### Updating

`update` in one transaction: `slug`, `is_active`, `published_at`, and `unpublished_at` are written together (`fill()->save()`; unchanged values do not change the row), then `ContentValueWriter::write($node, $values)`, the application of `file_meta`, and `$node->touch()` — so `updated_at` changes even when only field values changed (they lie in other tables). Disabling (`is_active = false`) does not touch `published_at` and `unpublished_at`. Only the keys from `values` are written, but the form sends **all** fields, so a cleared field (`''` or `[]`) loses its value, and the order of a multiple field = the order in the request (`weight` = index). A failure of value validation rolls back the slug change and the file metadata too. `uuid`, the node's type, and the author do not change (the model blocks `uuid` and the type; `user_id` is not accepted from the request); values of other languages are not touched, because `write()` replaces only the `default` language. Success — `back()` with `success`: the user stays on the node's edit form.

### Deletion

`destroy` simply deletes the node (`$node->delete()`), if no `node_ref` values point to it (otherwise — a redirect back with an `error` message and the list of places, [see above](#type_ref-and-node_ref-fields)): the values in all languages are removed by the DB cascade ([content-model.md](content-model.md#deletion-cascades)). There is no separate service. A node of another type gives 404 already at the binding of `{node}`. Success — a redirect to the type's list with `success`. After this, the prohibition on deleting a type with nodes ([admin-content-types.md](admin-content-types.md#deletion)) becomes practicable: the user can first delete the nodes.

When at least one additional language is active ([content-languages.md](content-languages.md)), the response also carries the Translations column and the missing-translation filter:

- `columns` ends with `{key: 'translations', name: 'Translations', type: 'text', sortable: false, service: true}`; every row gets `translations` — the codes of the languages the node is translated into (sorted; empty list for none). One `TranslatedLanguages::forNodes()` query (a `UNION ALL` over the value tables) serves the whole page, so the query count does not depend on the page size.
- The filter is an ordinary table filter on the `translations` column (type `select`, `filterable`, options = the active language codes): `?filters[0][c]=translations&filters[0][o]=eq&filters[0][v]=pl` keeps only nodes that have no stored value in `pl` (`TranslatedLanguages::withoutTranslation()`, a `NOT EXISTS` over the value tables, combined with search, sorting and paging; the total counts the filtered set). Because it is a table filter, it stays in the address and the table state while sorting and paging, and a code that is not an active additional language is ignored like any invalid filter. `translationLanguages` — the active languages `{code, name}` for the options of the quick filter drop-down.
- With multilingual mode off, or no active language, none of these exist (no column, no `translations` in rows, no `translationLanguages`, and a `translations` filter is ignored) and the payload is the same as before.

### One-click state toggle

`setActive` (`PATCH …/nodes/{node}/active`, name `admin.{section}.nodes.active`) sets only `is_active`; the body is a boolean `is_active` (required, otherwise a validation error and no change). It is authorized by `Gate::authorize('update', $node)` like editing (403 for a user who may not edit the node), saves the flag, calls `touch()` so `updated_at` moves, and answers with `back()` and `success` ("Node enabled." / "Node disabled."). `published_at`, `unpublished_at`, `slug`, and values are never touched, so enabling a node shows the state that follows from its dates ("Scheduled" or "Expired" are possible). The client sends the target value (a set, not a toggle), so a double click or a stale list cannot flip the state the wrong way.

## List page

`Pages/Admin/ContentNodes/Index.tsx` shows the [data table](admin-data-table.md) in **server mode** (`tableId="content-nodes-{key}"` — the column visibility is stored separately for each type). The columns are built from the prop `columns` (see [How columns are built](#how-columns-are-built)): the header is the field's name as is (this is data, not a translation key), `title` cannot be hidden, then the service columns: `slug`, the status (a badge), and "Publication date" (sorted by it); the service `slug` column has `width` `16rem`, so a long slug is cut into one line with an ellipsis and the full slug is in `title`. The slug is rendered by [`CopyableText`](#copyabletext) (`Components/Admin/CopyableText.tsx`): a click, or `Enter` / `Space` on the focused slug, copies the full `row.slug` to the clipboard and shows a "Copied to clipboard" toast; the click does not bubble, so it triggers no row action and the list stays open. The `filterable` prop is not passed, so there are **no filters and no filter button**. The page has no title of its own: the heading is the type name (`type.name`) that [`ContentTypeNav`](admin-content-types.md#type-section-menu) shows above the tabs ("Nodes" active), with the favorites star passed to it as `children`. The create and edit forms have no title of their own either, so the type name is their only `h1`. `type` carries `{key, name, slug}`; above the table there is a "Create" button (`{basePath}/{key}/nodes/create`).

The status badge of a row with `can_edit` is a clickable control (`Components/Admin/StatusToggleBadge.tsx`): a click sends `PATCH …/nodes/{uuid}/active` with `is_active = (status === 'disabled')`, without a confirmation. A row the user may not edit keeps the plain badge.

### Row menu

`Components/Admin/ContentNodes/ContentNodeRowActions.tsx` — a button group (`ButtonGroup`): the main button "Edit" (the link `…/nodes/{uuid}/edit`) and the "⋮" button with the items "Edit", "Preview", and "Delete" (destructive, separated by a divider). "Preview" is a regular link `<a target="_blank" rel="noopener noreferrer">` (the icon `Eye`) to `row.publicUrl`, which `Index.tsx` takes from the row's `public_url` field; the item is absent when there is no address (`null`): for a block, and for a node of a `content` type without a public slug. "Delete" opens an `AlertDialog` that names the node by the value of `title` (and without it — by the slug) and has the buttons "Cancel" and "Delete"; the dialog is rendered next to the menu, so that it does not close together with it.

### Link with the type section

Here lead: the item "Nodes" in the type's row menu, the `nodes_count` counter (a link) in the types table, and the item "Nodes" of the section's horizontal menu ([admin-content-types.md](admin-content-types.md)). The items exist for all three kinds. Breadcrumbs (`navigation.ts`, `patternTitles`, the template `(content|page|block)-types`): "Admin → Content Types / Page Types / Block Types → Nodes / Create node / Edit node".

## Translation mode

The edit page follows the [translation mode contract](admin-translation-mode.md): `GET …/nodes/{node}/edit?lang=en` (the code of an active additional language; an unknown or inactive code, or any language while multilingual mode is off, gives 404). It is available for nodes of every kind and needs the same right as the base edit page, including the access level of the type (`Gate::authorize('update', $node)` on the page, the save and the clear; a user who may edit only their own nodes gets 403 for another user's node).

- **Props.** `translation` is `null` when no switcher is shown, otherwise `{lang, baseLang, languages: [{code, name, translated}], values, exists}`. In the translation mode `fields` holds every field of the form, each with `translatable` (`title`, `meta_*` and the fields marked translatable are `true`), `values` the prefilled values of the translatable ones and the base values of the rest, `translation.values` the prefilled values of the translatable fields only — the stored translation of a field, otherwise its base value (a multiple field as a whole list; "stored" means non-blank by `FieldType::isBlank`) — and `files` / `labels` describe those values. `translation.exists` is `true` when at least one translatable field has a stored value in `lang`.
- **Save.** `PUT …/nodes/{node}/translations/{lang}` with `values[...]` (request `SaveNodeTranslationRequest`) calls `TranslationSaver::save()` ([content-values.md](content-values.md#saving-one-language)): non-translatable keys are errors (`values.price`), required is not enforced, values equal to the base are not stored, an emptied field loses its translation. The node is touched, so `updated_at` moves. The answer redirects to `…/edit?lang={lang}` with "Translation saved."
- **File names and descriptions.** Every `image` or `file` field shows, in the translation mode, the display name and the description of each file in its value in the current language, whether or not the field is translatable (the description is the alternative text, so an image has one per language). The server prefills `files[...].name` and `.description` with the translated values, otherwise the base ones (the original name, the base description). For a non-translatable field the file stays in its inert block and a separate group (`data-testid="file-description-{uuid}"`) with a "Name of {name}" input and a "Description of {name}" textarea is editable under it; for a translatable field the file may be replaced as usual and the "Edit file details" dialog edits the name and the description. "Save" sends `file_meta[{uuid}][name]` and `[description]` for the files in the form's values (`translationFileMeta()`). The translated name is for display only: the original name of the file is never changed and is shown wherever no translated name exists. `TranslationSaver::saveFileDescriptions()` accepts only uuids of files held in the node's base values or its values in that language (a foreign uuid is an error under `file_meta.{uuid}.description` and nothing is stored) and stores a value only when it differs from the base one, removing an emptied one ([file-storage.md](file-storage.md#translated-names-and-descriptions-media_translations)). The same file in another node shows the same translated name and description. Clearing a language removes the node's values only; the shared file translations stay. A translatable file field takes new files under the same attachment rule (a foreign file is refused with an error under `values.{key}`).
- **Clear.** `DELETE …/nodes/{node}/translations/{lang}` removes every value of that language from the node, touches it and redirects to the same page with "Translation cleared."
- **Marker.** `translated` of a language is true when the node has at least one stored value in it (`TranslatedLanguages`).

The form is `ContentNodeForm` itself, with the same layout in the translation mode (the language switcher above it, the main column, the side accordion, the sticky bar): the fields with `translatable: false` and the whole "Details" section (slug, status, dates, author) are shown `inert` and dimmed with their base values, nothing is marked required, "Save" stays disabled until a translatable value changes and sends only those values, and "Clear translation" (`ClearTranslationButton`) joins the action bar when a translation exists.

## Layout and service information

The form is a two-column grid on `lg` (from 1024 px): `grid-cols-[minmax(0,7fr)_minmax(0,3fr)]` (a separate `div` inside `<form>`; the grid does not contain the action bar); on the left — the type's fields, on the right — an `aside` with `lg:sticky lg:top-4` — an accordion with the sections "Details" and "SEO" ([below](#fields-of-the-node-and-the-seo-panel)). If both sections are expanded and taller than the window, the `aside` has its own vertical scroll (`lg:max-h-[calc(100vh-10rem)]` + `overflow-y-auto`) and does not overlap the sticky action bar; `overflow` is only on the `aside`, not on the ancestors of the action bar. The service values are not type fields: `useForm` keeps `slug`, `is_active`, and `published_at` next to `values`, so it is one request and one "Save" ([Form contract](#form-contract)).

**Components.**

- `NodeServicePanel` — the content of the block without its own state: rows "label — element" in the order "Show on the site" (`Switch`, `is_active`), "Status" (`NodeStatusBadge`), "Publication date" (`datetime-local`, `published_at`), "Show until" (`datetime-local`, `unpublished_at`, may be empty), "Slug", "ID" (edit only, read-only: the numeric `node.id` in a [`CopyableText`](#copyabletext), so a click or `Enter` / `Space` copies it and shows a toast; `data-testid="node-id"`), "Updated" (edit only, read-only), and "Author" (read-only; a `UserAvatar` with the picture or initials next to the name, `data-testid="node-author"` stays on the name; on creation — the current user). The edit form loads the author (`author:id,name,avatar`) like the list does. There is no creation date. Field errors are shown inside the block. A new service property is added as one more row.
- `status.ts` — `nodeStatus(isActive, publishedAt, unpublishedAt, now)` returns `published` / `scheduled` / `expired` / `disabled` by the state of the form **before saving** (the order: disabled, scheduled, expired, published; `Y-m-d\TH:i` strings are compared lexicographically, UTC) and `formatNow()`; the server-side equivalent is `ContentNode::status()`.
- `hooks/useMediaQuery.ts` — whether a media query matches; before the first computation it returns `undefined`. The `lg` breakpoint (1024 px) does not match `useIsMobile` (768 px), so the hook is generalized separately.

**One render of the panel.** The fields have fixed `id`s (`slug`, `published_at`, `unpublished_at`, `is_active`), so the panel is rendered exactly once: in the `aside` when `useMediaQuery('(min-width: 1024px)') === true`, otherwise — in a `Sheet`. Until the first computation (SSR and the first frame) the mobile variant with a closed panel is shown, so `#slug` is not duplicated. The state lives in `useForm`, so closing the `Sheet` (Radix unmounts the content) does not lose the values, and enlarging the window to `lg` moves the changed values to the right column.

**Action bar.** On all screen sizes at the bottom — the shared sticky [`FormActionBar`](admin-shell.md#sticky-form-action-bar) with "Cancel" and "Save". On narrow screens (< `lg`) its left slot holds the icon button "Details" (without visible text and without a status badge: on small screens the text does not fit; the accessible name is `aria-label` and `title`; a red error dot if there is an error in `slug`, `published_at`, `is_active`, or the "SEO" fields `values.meta_*`); on `lg` there is no button, because the column is visible. The panel is opened by a `Sheet side="bottom"` with a "Done" button; in the sheet there is the same accordion, and its state (the open section) lives in `ContentNodeForm`, so it survives closing the sheet. Between the form content and the action bar there is a margin (`mt-10`), so that the form does not stick to the bar. After a failed save the panel stays closed, the dot is lit, and the messages are visible when it is opened, because errors live in the Inertia state, not in the DOM.

**Table.** After the slug column the client adds the status (a badge, `cell`) and "Publication date" (sortable); see [How columns are built](#how-columns-are-built).

**Rationale.** The service content is separated from the content, and the column is extended by rows. A `Sheet` instead of a second column on narrow screens gives the fields the full width. A single render of the panel excludes duplicate `id`s and state desynchronization.

## Node form

The pages `Pages/Admin/ContentNodes/Create.tsx` and `Edit.tsx` show above the form the [type section menu](admin-content-types.md#type-section-menu) (with "Nodes" active) and the shared form `Components/Admin/ContentNodes/ContentNodeForm.tsx`. It is built from the data (`fields`), not from hard-coded fields: one input element per type field in weight order, with the field's name as the label; required fields have a `*` mark (and a hidden text "(required)" for assistive technologies). There is no language switcher.

### Fields of the node and the "SEO" panel

`ContentNodeController::formFields()` provides in the form only fields whose values belong to **nodes** ([content-model.md](content-model.md#system-fields)): fields that belong to the type itself (`section_*`) do not get into the form and are absent from `fields`, `values`, and the node table columns. The controller adds the mark `panel: 'seo'` to the system metadata fields (`meta_title`, `meta_description`, `meta_image`).

`ContentNodeForm` shows the fields without this mark as the main ones, in weight order, and the fields with `panel: 'seo'` — in the right service column, in the "SEO" section of the accordion (`Components/ui/accordion.tsx` on `radix-ui`) below the "Details" section. The accordion is `type="single" collapsible` with a controlled `string` state (initially `'details'`: "Details" expanded, "SEO" collapsed): at most one section is open at a time, opening one closes the other, and the open one can be closed (then none is open). Each section (`AccordionItem`) has its own frame (`rounded-md border px-3`), with a margin between sections (`space-y-2`); everything together lies in a common frame of the column (`rounded-md border p-3` on `Accordion`). The "SEO" section (`data-testid="seo-panel"`, it exists in the DOM only while it is expanded; the values remain in `useForm`) contains the same field containers (`NodeFieldFrame`) with the same input elements (`NodeFieldInput`/`NodeFieldList`), validation, and errors `values.{key}`; the values are saved together with the node by the same action, and the base language is the single one, as for the rest of the form. A type without such fields (`block`) has no "SEO" section, and the accordion shows only "Details". The "Details" section is `NodeServicePanel` (without its own heading: the heading is the `AccordionTrigger`). The accordion is rendered **once**: in the `aside` on desktop or in the `Sheet` below `lg` (the field ids are fixed). An error in the collapsed "SEO" (`values.meta_*`) opens the section and closes "Details" (a `useEffect` sets the state `'seo'`) and is counted in the red dot on the sheet button. As columns of the node table, `meta_*` are available the same way as any other node field.

An attempt to write the value of a field that does not belong to the node (for example, `values.section_title` in a request) is rejected by `ContentValueWriter`: the error `values.section_title`.

### Field containers

Each field (the component `NodeFieldFrame`, shared by the main fields, the "SEO" section, and the [Display and SEO tabs of the type](admin-content-types.md#display-tab-all-kinds)) lies in its own container with a frame — `<fieldset class="space-y-2 rounded-md border p-4">` with `<legend class="px-1 text-sm font-medium">`, with the same classes as the "File settings" block in the [field form](admin-content-fields.md). The legend is the field's name with the requiredness mark; for a single field the label stays the `<label for>` of the input element, and a multiple field is a named group (`fieldset` with a legend). A boolean field has no legend: the checkbox and its label stand in one row inside the frame.

**Field description.** If the field has a `description` ([the field form](admin-content-fields.md#field-description)), the form shows it right under the legend as `<p class="text-sm text-muted-foreground">` — for single and multiple fields; for a boolean field — under the row with the checkbox and label, inside the frame. Without a description nothing is drawn (there is no empty line). The description is plain text (React escapes HTML). The data comes from `ContentNodeController::formFields()` (`description` in each field). Hints and error messages remain inside the frame of their field. The frame (`FRAME`) has `min-w-0`: a `fieldset` by default has `min-inline-size: min-content`, so unbreakable content (the `truncate` title of a `youtube` card, long URLs) would push the left grid column and go under the service column. The "Save" and "Cancel" buttons are in the sticky bar at the bottom of the window, outside the frames. The order of fields, requiredness marks, and the behavior of multiple fields do not change. The form state is `useForm({ slug, values })`; the "Cancel" button leads to the list of the type's nodes.

The slug is no longer in such a frame: it is in the [service column](#layout-and-service-information). The hint under the slug depends on the mode: on creation — that an empty slug will be generated from the title (for blocks — automatically, with the prefix); on editing — that changing the slug does not change the node's address in the admin panel.

### Slug by kind and the block prefix

The server-side slug rules come from the model ([content-model.md](content-model.md#node-slug)): for page nodes (`page`) an empty slug is taken from the title; for block nodes (`block`) an empty slug is generated with the prefix `block-` (`block-` plus random letters), and an explicit slug without the prefix is rejected with an error on `slug`. A page slug that matches the slug of a `content` type or a reserved path ("This slug is already used by a content type." / "This slug is reserved.") is rejected with an error next to the slug field ([content-model.md](content-model.md#reserved-paths)); `content` and `block` nodes do not have this check.

So that the user does not have to type the prefix, `ContentNodeController` gives the form the prop `slugPrefix` (on `create` and `edit`): `ContentNode::BLOCK_PREFIX` (`block-`) in the blocks section and an empty string in the others. `ContentNodeForm` passes it to `NodeServicePanel`, where the prefix is a separate read-only addon before the slug field (`data-testid="slug-prefix"`). The form state `data.slug` holds only the rest: `onChange` trims a prefix typed or pasted at the start; `transform` before sending adds the prefix to a non-empty rest (an empty one stays empty, so the server generates the slug); in the edit form the prefix is removed from the existing slug. The hint for blocks separately explains the automatic generation and the required prefix.

### Preview button and the `publicUrl` prop

`ContentNodeController::edit` provides the prop `publicUrl` — the relative public address of the **saved** node (by the slug from the DB, not by unsaved form changes; after saving, Inertia updates the prop). The rules match the site routes ([public-site.md](public-site.md)): for a page (`page`) — `/{slug}`, for a `content` node — `/{type slug}/{node slug}` (if the type has no public slug — `null`), for a block — `null`, because it has no own address. The frontend does not duplicate these rules. The table uses the same rules: the private method `ContentNodeController::publicUrl()` takes the kind, the type, and the node, and is called from `edit()` (the prop `publicUrl`) and from `row()` (the row field `public_url`), so the "Preview" item in the row menu needs no additional requests.

`Edit.tsx` passes `publicUrl` to `ContentNodeForm`, which in the left part of `FormActionBar` (next to the "Details" button) shows the "Preview" button — a regular link `<a target="_blank" rel="noopener noreferrer">` (the icon `Eye`; on narrow screens only the icon with an `aria-label` remains). There is no button in the create form and when `publicUrl` is `null`. This is a simple transition to the site: for an invisible node (disabled, scheduled, expired) the site, as before, responds with 404; there is no separate preview of drafts. Coverage: the Feature tests `test_the_edit_form_carries_the_public_url_of_the_node` (`ContentNodeWriteTest`) and `test_each_row_carries_the_public_url_of_the_node` (`ContentNodeIndexTest`).

### Multiple fields

A multiple field is edited by `NodeFieldList.tsx` — a list of widgets of the same type with the buttons "Add item" (except the `image` and `file` fields, see [below](#image-and-file-fields)) and "Delete item", and a handle "Drag to change the order" next to each item. The order is changed with the mouse and from the keyboard (`@dnd-kit/sortable`, as the dragging of table rows: space — lift, arrows — move, space — drop). The order of the list = the order that is stored: the index of an item becomes the `weight` of the value, so the backend does not change, and the form simply sends the list in the new order. Items have client identifiers (values can repeat and are not suitable as keys); they are not sent to the server. Empty items are discarded by the server (`ContentValueWriter` does not store empty rows).

**Item limit.** If the field has `max_items > 0` ([the field settings](admin-content-fields.md#maximum-number-of-items)), in one row with the label inside the frame (the `legend` — `flex items-center gap-2`, the counter does not wrap under the label) the counter "n / max" is shown (`data-testid="field-{key}-counter"`; without a limit there is none), and when there are as many items as allowed (`full`), the "Add item" button is disabled. Deleting an item frees a place. The server checks the limit separately (`max:{max_items}` in `ContentValueWriter`, the error `values.{key}` is shown under the field in the frame); a limit lowered below the existing count does not silently truncate data — the node cannot be saved until the number of items is within the limit. For the `image` and `file` fields see [below](#image-and-file-fields).

### Field errors

Server errors come with the keys `slug`, `values.<key>`, and `values.<key>.<index>`. The error of a field is shown under it, the error of an item of a multiple field — under the corresponding list item; fields with a validation failure have `aria-invalid`. The entered text remains in the form.

### `richtext` field

For `richtext`, `NodeFieldInput` shows `Components/Admin/ContentNodes/RichTextEditor.tsx` — an editor on [Tiptap](https://tiptap.dev) (MIT, `@tiptap/react`, `@tiptap/starter-kit` — which already includes links, underline, and strikethrough — and the extensions `extension-table`, `extension-text-align`, `extension-text-style`, `extension-youtube`). The value type is an HTML string ([content-values.md](content-values.md#rich-text)).

- **Toolbar** (`role="toolbar"`, "Text formatting", `RichTextToolbar.tsx`): block style (one dropdown "Block style", `BlockStyleMenu`, see below), bold, italic, underline, strikethrough, alignment (one button — a dropdown "Text alignment"), text color, background color, bulleted and numbered list, link, image (inserting a file or, when an image is selected, its options), table, YouTube video, frame, emoji, "Clear formatting"; on the left — "Source", on the right — "Full screen". The buttons are `Button`s with `lucide-react` icons and have an `aria-label`; the buttons with a state (formatting, source, full screen) have `aria-pressed`. A mouse click does not take the focus from the editor. There are no actions for inserting other files (documents). In the editor, `code`, `codeBlock`, `horizontalRule`, and the final empty paragraph are disabled, and headings are `h2`–`h4`: this matches the list allowed by the server.
- **Alignment** — `AlignMenu`: the button shows the icon of the current alignment of the block under the cursor (left, if there is none); the menu (`DropdownMenuRadioGroup`) contains "Left", "Center", "Right", "Justify"; the current item is marked (`aria-checked`) and highlighted.
- **Link** — a `Popover` with the field "Link address": "Apply" sets the link on the selection (an empty address removes it), "Remove link" removes an existing one.
- **Text and background color** — a `Popover` with a palette of ready colors, a `#rrggbb` field (`normalizeHexColor`: accepts `#rgb` and `#rrggbb`, stores `#rrggbb`), and a "Reset color" button. The color is written as `<span style="color: …">` / `background-color` (the extensions `TextStyle`, `Color`, `BackgroundColor`); the alignment — `style="text-align: …"` on a paragraph or heading (`TextAlign`).
- **Block style** — `BlockStyleMenu` in `RichTextToolbar.tsx`, a `DropdownMenu` with a `DropdownMenuRadioGroup` built like the alignment menu (`aria-label` "Block style"), inside the same `fieldset disabled`, so the "Source" mode switches it off. The items are "Normal" (a paragraph), "Heading 2", "Heading 3" and "Heading 4" (`h2`–`h4`). The `useEditorState` selector yields `blockStyle` (`'p' | 'h2' | 'h3' | 'h4' | null`): the button shows the icon of the current style and the menu marks it; with a node that is neither a paragraph nor an `h2`–`h4` (an image selected) it is `null`: no item is checked and the button shows the neutral `Type` icon. Choosing an item runs `setParagraph()` or `setHeading({ level })` (not a toggle, so choosing the current level changes nothing) and keeps the focus in the editor.
- **Pasting Word lists** — `RichTextEditor.tsx` passes the clipboard through `convertWordLists` (`richTextUtils.ts`, `transformPastedHTML`) and, for a clipboard with plain text only, through `convertPastedText` (`handlePaste`); both build real `ul` / `ol` lists (each item `li > p`, which the server unwraps on save, see [content-values.md](content-values.md#rich-text)). Recognized on top-level paragraphs: (1) Word's own markup — `mso-list:lN levelM` in `style`, the typed marker in a `mso-list:Ignore` span; the level gives the nesting, a marker such as `1.`, `a)` or `iv.` gives an `ol` (starting at the first number when it is not 1), anything else (`·`, `o`, `§`) a `ul`; (2) a paragraph (or plain-text line) that starts with a bullet glyph `•` `·` `▪` `◦` `●` and whitespace (a Word list that arrived without list markup) — a `ul`; (3) a run of at least two consecutive paragraphs numbered `1.`, `2.`, `3.` (each number one more than the previous; `)` also works) — an `ol` with `start` set to the first number, while a lone `2026. …` or `1.` followed by `5.` stays text. The typed marker and the spaces after it are removed; consecutive items form one list and any other node ends it. Lists that already arrive as `ul` / `ol` (browsers, Google Docs) and any other HTML are pasted by Tiptap as before: when nothing is recognized the function returns its input unchanged. The pure functions run in the browser only (`DOMParser`, never inserting the markup into the page).
- **Clear formatting** keeps bold, italic, underline, links, and headings; it removes strikethrough, color, background, and alignment.
- **YouTube video** — a `Popover` with the address field (`youtu.be/ID`, `watch?v=ID`, `embed/ID`, `shorts/ID`, `parseYoutubeId`); a player on `youtube-nocookie.com` is inserted. An invalid address — a message next to the field, the content does not change. The server keeps only the `iframe` (it removes the `div` wrapper of the extension), so `YoutubeVideo` in `richTextExtensions.ts` also reads a bare `iframe` as a video.
- **Image** — the "Image" button (`ImageButton`) opens a hidden `input[type=file]` (`accept="image/*"`) and immediately uploads the file via `uploadFile()` (`POST /admin/files` with the `content_type` and `field_key` of the field; the same function and CSRF as in `FileUpload`; the rules — the `image` profile, [file-storage.md](file-storage.md)). The editor receives `contentType` and `fieldKey` from `NodeFieldInput` (`typeKey` and `field.key`, including for rows of a multiple field). The node `RichImage` (`richTextExtensions.ts`; a block atom with the attributes `src`, `alt`, `width`, `caption`) is inserted at the cursor position with a **relative** address `/storage/{uuid}.{extension}` (the `pathname` of the response's `url` field is taken, without the protocol and domain) and an `alt` equal to the file name. While uploading, the button is disabled; an error (an unsupported type, an oversized file, a network failure) is shown next to the editor (`role="alert"`), the content does not change. In "Source" mode the button is disabled along with the rest. The file immediately appears in the media library; the relation with the node appears after saving ([media-library.md](media-library.md)); an uploaded but not saved image remains without relations.
- **Image options** — opened by double-clicking the image or by the "Image" button when the image is selected (without a selection the button opens the file choice); there is no separate button in the toolbar. A selected image has a blue outline (`img.ProseMirror-selectednode`, for a caption — `figure.ProseMirror-selectednode img`). It is a modal `Dialog` (`ImageOptionsDialog`, the heading "Image options") with the fields "Width (px)", "Alternative text", "Caption" and the buttons "Done" and "Original size". "Done" applies the three values (`updateAttributes`); the width — an integer from 1 to 4000 (`IMAGE_MAX_WIDTH`), otherwise an error next to the field and nothing is applied; an empty width and "Original size" remove `width` (the natural size, the height is proportional). A non-empty caption is stored as `<figure><img><figcaption>…</figcaption></figure>` (plain text, without formatting); an empty one removes the `figure`. The server checks the same ([content-values.md](content-values.md#rich-text)). **Alignment.** A selected image is aligned by the same "Text alignment" menu: "Left", "Center", "Right" (the "Justify" item is disabled). The choice is written to the node's `align` attribute and is stored in standard HTML: `<figure style="width: 500px; max-width: 100%; margin-left: auto; margin-right: auto; text-align: center"><img width="500">…</figure>`. The `figure` has the width of the image (`width: {width}px; max-width: 100%`, without a set width — `fit-content`) and is shifted by margins (`auto` on both sides — center, only on the left — right, without margins — left), so the image itself is shifted, the caption sits under it centered, and a long caption wraps over lines and neither squeezes nor stretches an image with a set width. "Left" without a caption returns a bare `<img>`. A previously saved `text-align` without margins is read as center/right. **Default width.** An inserted image gets `width="500"` (`IMAGE_DEFAULT_WIDTH`), so large pictures do not stretch the text; the width can be changed in the dialog, and "Original size" removes `width`. **Form width.** The node form has `max-w-5xl` (it was `max-w-2xl`), so that the editor has room for images. **Auto-selection.** An image is selected only by the user (a click, a double click, insertion): text that begins with an image is opened without a selection (`deselectImage` places a `GapCursor` before the image instead of selecting the node). There are no drag handles and no file choice from the media library.
- **Table** — `TableButton` in `RichTextToolbar.tsx`, the button "Table" (`aria-label` "Table"), inside the same `fieldset disabled`, so the mode "Source" switches it off. With the cursor outside a table it inserts a table of 3 rows and 3 columns whose first row is made of header cells (`insertTable({ rows: 3, cols: 3, withHeaderRow: true })`), the cursor in the first cell. With the cursor in a table the button is pressed (`aria-pressed`) and opens a `DropdownMenu` of eight actions on the row and column at the cursor: "Add row above", "Add row below", "Delete row", "Add column before", "Add column after", "Delete column", "Switch header row" and "Delete table"; an action is disabled while its `editor.can()` check fails. The extensions are `Table.configure({ resizable: false })`, `TableRow`, `TableHeader` and `TableCell` of `@tiptap/extension-table` (`richTextExtensions.ts`); without resizing no column width is kept. A cell holds paragraphs, so the inline formatting and the paragraph alignment work inside it. A stored table opens with its rows, header cells and `colspan` / `rowspan` kept (rows of `thead`, `tbody` and `tfoot` are read as the rows of one table, and a legacy `thead` made of `td` cells stays ordinary cells; "Switch header row" fixes one). Limits: there is no merging or splitting of cells and no column width (already stored spans are kept). A table without any text is empty for the server, so a freshly inserted blank table is not saved on its own ([content-values.md](content-values.md#rich-text)). The table scrolls inside the editor: Tiptap wraps it in `.tableWrapper` and gives the table an inline `min-width`, so the wrapper has `overflow-x: auto` (`.rich-text-content`, `resources/css/app.css`).
- **Frame** — a `Popover` with one field that accepts an `https` address or the whole `<iframe>` code (`parseIframeInput` takes `src`, `width`, `height`, `title`, `allowfullscreen`; it drops the rest). The address is checked against the list `richtext.iframeHosts` from the shared Inertia props (it comes from `content.richtext.iframe_hosts`, [content-values.md](content-values.md#rich-text)) by the same rule as on the server; a disallowed one — an error next to the field, the frame is not inserted. In the editor the frame gets `sandbox`; the server forcibly sets it and `loading="lazy"` on saving. Whether a third-party service displays the embed depends on its own headers (`X-Frame-Options`, CSP).
- **Source** — the first button of the toolbar (`aria-pressed`): instead of the formatted text it shows a `textarea` with the raw HTML (each block on a new line, `formatSource`). An edit in the field is applied to the editor at once (`setContent`) and goes to `onChange`; the server cleans the value anyway. While the mode is on, the other buttons are disabled (`fieldset disabled`), except "Full screen". The editor remains mounted, so the content is not lost.
- **Emoji** — `EmojiPicker.tsx`: a `Popover` with a grid of Unicode emoji; choosing one inserts the character at the cursor position, and the focus remains in the editor.
- **Full screen** — the wrapper becomes `fixed inset-0 z-40`, and the editing area takes the free height; `Escape` or pressing the button again returns the normal view, while the mode is on, `body` does not scroll. The editor stays in the same place of the tree, so the content and the cursor are not lost; the `Popover` has a higher `z-index` (`z-50`).
- **Component files** (`Components/Admin/ContentNodes/`): `RichTextEditor.tsx` (the state, full screen, the wrapper), `RichTextToolbar.tsx` (the buttons and dialogs), `EmojiPicker.tsx`, `richTextExtensions.ts` (the composition of extensions, the `Iframe` node), `richTextUtils.ts` (`convertWordLists`, `convertPastedText`, `parseYoutubeId`, `parseIframeInput`, `isAllowedFrameAddress`, `normalizeHexColor`).
- **Value.** `onChange` receives the HTML after each edit, and an empty document — `''` (the server considers `<p></p>` empty in any case). New values from outside (a form reset) are accepted by the editor only while it has no focus: while the user is typing, a late value from the form would reset the text and the cursor.
- **Accessibility and errors.** The editable element (`role="textbox"`) has the field's `id` and name: with `aria-labelledby` pointing to the field's label, and in a row of a multiple field — with `aria-label` of the row. A server error is shown in the frame of the field; the editor and the frame have `aria-invalid`; the entered content remains.
- **Multiple field** — a separate editor in each row (`NodeFieldList`).
- **Styles.** The frame is like `Textarea`; the look of the content — the classes `.rich-text-content` in `resources/css/app.css`.

### `term` field

For `term`, `NodeFieldInput` shows a `Select` of the field's vocabulary terms. The list `settings.terms: {uuid, name, depth}[]` is put into the field description by `PresentsFormFields::formFieldData()` (the method `termOptions()`): all terms of the vocabulary in tree order with the name in the base language, one set of queries per field; `depth` (a root has 1) gives the indentation of the option, so "Jackets" stands below "Clothing" with an indent. The form value is the term's `uuid` (`''` — no value).

- **Single-value field** — a `Select` with the first option "No term": choosing it clears the value (an optional field loses the value on saving). The saved term is marked when the form is reopened.
- **Multiple field** — a list of such `Select`s in `NodeFieldList` by the general rules: "Add item", "Delete item", dragging, the `max_items` limit; the order of the list is the order in which the terms were saved. There is no "No term" option in the rows (an item is removed with its button).
- **Invalid selection.** A term of another vocabulary and a non-existent `uuid` are rejected by the server with the type rule (`TermType`) with the error `values.{key}` (in a list — `values.{key}.{n}`) next to the field; a required field demands a selection.
- **Node list.** The controller collects the term names of the page with one query (`termNames()`, the `default` translation) and the column shows the names separated by commas; sorting by the column is disabled.

**Limitation.** The list of terms is passed in full and without search: for vocabularies with thousands of terms a separate search widget will be needed (autocomplete and creating a term "on the fly" are outside this feature). The form edits only the base language, so the names in the form and the list are in the base language.

### `url` field

For `url`, `NodeFieldInput` shows `Components/Admin/ContentNodes/UrlField.tsx`: two single-line `Input`s in one row (on a narrow screen — in a column): "Link" (the element's `id`) and "Title" (optional, `{id}-title`). Both have an `aria-label` (for an item of a multiple field the name "…, item N" is added to it), and with a server error — `aria-invalid`. There are no modal windows and no requests to external services.

The state of the field is the object `{url, title}` (`UrlValue`, `emptyUrl()` in `types.ts`; `ContentNodeForm.initialValue` brings the saved value to rows). An empty "Link" clears the value, even if "Title" is filled in. A multiple field is a regular `NodeFieldList` with the "Add item" button; each row has its own pair of fields, is deleted and reordered by the general rules.

- **Errors.** An invalid link (`javascript:`, `//host`, spaces, more than 512 characters; a title over 255) is rejected by the server with the type rule with the error `values.{key}` (in a list — `values.{key}.{n}`) next to the field; the entered text is kept in the form. Rules: [content-values.md](content-values.md#links).
- **Node list.** The controller provides `{url, title}`, and `NodeCell` renders an `<a href target="_blank" rel="noopener noreferrer">` with the text `title` or `url`. A relative link in a new tab is resolved relative to the admin panel's host. The column is not sortable, a `sort` by it is ignored, and a sort by a `url` field saved in the list settings is discarded.

### `type_ref` and `node_ref` fields

For `type_ref` and `node_ref`, `NodeFieldInput` shows `Components/Admin/ContentNodes/RefAutocomplete.tsx`: a trigger button (`role="combobox"`, the element's `id`) with the label of the selected target; it opens a `Popover` with a search field and a list (`role="listbox"`). The search goes to the server ([endpoints](#search-for-reference-fields)): on opening — an empty query (the first results), then — after a 250 ms pause from the last character; a response that is no longer needed is cancelled (`AbortController`). The `type_ref` option shows the `name` of the type and a muted `key`; `node_ref` — the `title` of the node. Choosing writes the `key` / `uuid` into the form state (`''` — no value); for a single-value field there is a "Clear selection" button next to it. In a row of a multiple field there is no clear button (there is "Delete item"); the other rules of multiple fields are general (`NodeFieldList`). A server error (`values.{key}`) marks the trigger `aria-invalid` and is shown next to the field; the selection is kept. A search error is shown in the list ("Could not load results").

- **Search targets.** The endpoint and its parameter are taken from `field.settings`: `kind` (`type_ref`) and `content_type` (`node_ref`) are put into the field description by `PresentsFormFields::formFieldData()`.
- **Label on opening.** The edit form provides `labels` (`{value: label}`) for the saved values with one query per reference type (`ReferenceLabels::forValues()`, like `termNames()`); `ContentNodeForm` passes them to `RefLabelsContext`, and the trigger shows the label at once, without typing. The widget remembers the labels from search results and the last selection; a value without a known label (the target no longer exists) is shown as is. The create form does not receive `labels`.
- **Node table.** The cell is `{label, href}` ([value in the row](#value-in-the-row)): `href` is the address of the target's edit page in the section of its kind (`admin.{content-types|page-types|block-types}.edit` for a type, `….nodes.edit` for a node). The page's labels are collected by `ReferenceLabels` with two queries (types, nodes) for the whole page.
- **Sorting.** The column sorts by the target's label, not by `key`/`uuid` (`ContentNodeQuery::applySort`): the `name` of the type or the `title` of the target's `default` language is joined to the first value (`weight = 0`); nodes without a value (and with an unavailable target) go last in both directions, and the secondary order is the same as for other fields. Types are available as a default sort in the list settings.
- **Deleting the target.** A type or a node that the values refer to is not deleted: `ContentNodeController::destroy` and `ContentTypeController::destroy` return back with an `error` message and the list of places (`field (type): count`, `ReferenceUsage`); the model remains the last barrier ([content-values.md](content-values.md#node-reference-node_ref)).

### `youtube` field

For `youtube`, `NodeFieldInput` shows `Components/Admin/ContentNodes/YoutubeField.tsx`: a **video card** — the screenshot (from `files`; without a screenshot a placeholder "No screenshot"), the title-link and the description — with the buttons "Edit" and "Delete". While there is no video, in its place there is an "Add video" button; for a single-value field it disappears as soon as there is a video. The title is a regular `<a href={url} target="_blank" rel="noopener noreferrer">`; without a title the text is the address. The form value is the object `{url, title, description, screen}` (the form does not send `video_id` — the server determines it); an empty object (`url` is empty) clears the value. "Delete" on the card resets the value to empty (saving the node removes the video).

A multiple field is a list of cards in `NodeFieldList`: instead of "Add item" there is the button "Add video" (`youtube-add-{key}`), which opens a window and adds a new card only after "Done". A row's card has "Edit", and the row is deleted by its own "Delete item" button of the list (as is the order — by dragging); the card has no own "Delete" in the list (`removable={false}`).

**Modal window** (`YoutubeFieldDialog.tsx`, `ui/dialog`) is opened by "Add video" and "Edit". It has a local draft `{url, title, description, screen}` and is mounted only while it is open, so each opening starts from the current value. In the window: the field "Link" with the button "Fetch data", "Title", "Description", and a block of the screenshot with `FileUpload` of the field (preview, replacement, removal; `accept` and `maxSize` from `settings` — the `image` profile). The value gets into the form only by "Done" (it is inactive while the link is empty); "Cancel", `Escape`, and a click outside the window discard the draft.

- **The "Fetch data" button** is inactive while the link is empty or a request is in progress. The request is [`POST /admin/youtube/lookup`](#fetching-video-data); success overwrites the link (for Shorts — the regular one), the title, the description, and the screenshot of the draft and shows the preview, but changes neither the form nor the node.
- **An error** of the request (`422`, `503`, network) is shown in the window under the link field (`role="alert"`, `youtube-error-{key}`; the server's text or "Could not get the video data. Try again later."); the draft does not change.
- **Changing the link** without pressing the button does not touch the title, the description, and the screenshot.
- **The screenshot** is replaced by its own image or deleted; the title and the description remain in this case. A screenshot obtained or uploaded in the window and then cancelled remains a free file (it is removed by `files:prune`). The screenshot files do not get into the form's `file_meta` (the file's name and description are edited in the media library).
- **A saving error** (for example, a link to a channel) is shown in the frame of the field; the card and the entered values remain in the form.
- **Editing:** `ContentNodeController::fileInfo()` together with the files of the `image`/`file` fields collects also the screenshots of `youtube` values, so the card has a preview without additional requests; `formFields()` gives the field the `mimes` and `max_size` of the `image` profile (the interface `HasUploadProfile`).

### Image and file fields

For such fields `NodeFieldInput` shows the [`FileUpload`](file-storage.md#widget-and-demo-page) widget in "field" mode: the file is uploaded immediately by a `POST /admin/files` request with `content_type` and `field_key` (the server takes the profile and the narrowing from the type and the field settings), and the form stores only the row `{uuid}.{extension}` (`UploadedFile.value`). A multiple field is a list of widgets (`NodeFieldList`) by the general rules; the order of the list is the order of values.

**Which files a node may take.** The form has no picker of existing library files: new files get in by upload, which records the uploader (`files.user_id`). The server enforces the same on `store`, `update`, and `saveTranslation` (`Webtack\Ecms\Files\AttachedFileGuard`): inside the transaction it compares the files the node references (`media_relations`, every field type that tracks files — `image`/`file` fields, YouTube screenshots, images in rich text — in every language) before and after the write. A file that is new must be uploaded by the user or be changeable by their [media level](access-control.md#media-and-files-in-nodes) (`MediaPolicy::update`: `any`, or `own` for their upload); otherwise the save is refused with an error under `values.{key}` and nothing is stored (no node, no relation, no file change). Files already in the node's saved values stay valid for every user who may edit the node, whoever uploaded them. An administrator is unrestricted.

**Several files at once.** A multiple `image` or `file` field has a zone of [`FileUpload` in `multiple` mode](file-storage.md#multiple-mode): the user selects or drags several files, each is uploaded by a separate `POST /admin/files` request (sequentially), and the uploaded files are added **to the end of the list** as new items with the value `{uuid}.{extension}` (the metadata is remembered by `known`, so the items have a name and a preview at once). The files are checked against the field's settings (the allowed types, the maximum size) the same way as a single one; a rejected file does not become an item, and the reason is shown with its name. Added items are edited by the general rules: deletion, dragging. In a multiple `image` / `file` field there is **no "Add item" button** (an empty widget made no sense): new items appear only by uploading, while other multiple fields (text, number, and so on) keep the button. The file block in a row has **no own "Delete file" button** (`removable={false}`) — the file is removed by the row's "Delete item" button; in a single-value field the block's button remains, because otherwise the field could not be cleared. Single (non-multiple) fields accept one file, as before. **Limit and multiple upload.** When the limit is reached, the `FileUpload` zone is not shown, and instead "Limit reached: N items" is displayed (`field-{key}-limit`); after deleting an item the zone appears again. The list of files that did not fit or were not uploaded (`file-upload-{key}-many-failures`) is displayed by `NodeFieldList` itself (the widget passes it through `onFailures`), so it remains even though the zone is gone; it is cleared on a new batch or on deleting an item. If more files are selected than there are free places, `NodeFieldList` passes to the widget `capacity` (the free places) and `capacityMessage` ("Limit: N"): only the first files in the order of selection within `capacity` are uploaded, and the rest are **not uploaded** (so as not to leave files in the storage without a place in the form) and are named in the list of failures with the limit message. A partial upload is kept as is — the form is not blocked during the queue. The link with the media library arises when the node is saved, as for single files.

- **Rules.** `fields[].settings` for a file field contains the effective `mimes` and `max_size` (the type's profile narrowed by the field settings; `UploadRules::forField`). The widget takes from them `accept` and `maxSize` only for a hint and a quick rejection (a type or size outside the limits is reported before uploading); the server checks authoritatively both during the upload and during the saving of the node (`FileValue`).
- **Saved file.** The `Edit` page receives the prop `files`: a dictionary `{uuid}.{extension}` → `{uuid, name, mime, size, url}`, collected by **one** request `whereIn('uuid', …)` to `media` per page (`ContentNodeController::fileInfo`); `url` is built from the string without requests (`FileStorage::urlForValue`). A file that is not in `media` is shown as the saved string. Files uploaded in the current form are remembered by the form itself (`ContentNodeForm`, the state `known`).
- **File name and description.** The fields "Name" (`media.original_name`, up to 255 characters, not empty) and "Description" (optional, up to 2000 characters) do not take space in the file block: `NodeFieldInput` puts, through the widget's `actions` slot, a pencil button "Edit file data" (`FileMetaDialog`) into the block's button row; a single field and each row of a multiple one, in the create and edit forms. In a row of a multiple field (`removable={false}`) it stands in the place of the former inner cross; in a single field — next to "Delete file". The button opens a modal window (`Components/ui/dialog.tsx`, a shell over the `radix-ui` `Dialog`) with a draft "Name" and "Description", initialized from the form state at each opening: "Done" applies the draft to the form state and closes the window; "Cancel", Escape, and a click outside the window discard it. Nothing is saved until the node's "Save" is pressed. The file block shows the name, the description, and the size **from the form state** (`file_meta`, the fallback — the known file from `files`): the name, under it the description (`line-clamp-2`; an empty description draws nothing, `data-testid="file-upload-{key}-description"`), and the size; after "Done" the block is updated at once, without saving, and "Cancel" does not change it. The errors `file_meta.{uuid}.*` are shown as text (`role="alert"`) under the file block; in the window — next to the corresponding fields, and the button gets `aria-invalid`. The contract of `file_meta` does not change. The state lives in `useForm` as `file_meta` (by the file's uuid): it is initialized from the prop `files` (`name`, `description` — `fileInfo()` provides them), and for a just-uploaded file the entry is added on `rememberFile`; `transform` leaves in the request only the uuids that are still in the values of the `image`/`file` fields (replacing or deleting a file removes its metadata). Whoever may edit a node may change the name and description of the files in that node's values, with no check of the media library access; `file_meta` for a file outside the node's values is ignored without an error. Because of the rule above, those files are the user's own uploads, files their media access allows, or files already in the node. The saved name and description belong to the **file**: after saving they are the same in all nodes where the file is used, and in the [media library](media-library.md) (there — only a view). The extension of the saved file and its path on disk do not change.
- **Saving the file name and description.** `ContentNodeController::applyFileMeta()` (shared by `store` and `update`, in the same transaction as the values) takes the uuids of the files from the **saved values of the node** (`TracksFiles::fileUuids`) and changes only the files of this list: the metadata of a foreign uuid is silently ignored, so an arbitrary file cannot be renamed by a known uuid. The name is cleaned as on upload (`basename`, truncation to 255), and an empty description (spaces) becomes `NULL`. A validation error of the values rolls back the metadata too (and vice versa).
- **Replacing and clearing.** The "Delete file" button (single field) or "Delete item" (a row of a multiple one) only takes the value from the form; after saving, the relation of the file with the node is removed (`FileRelations::sync`), and the file itself remains in the [media library](media-library.md) with the usage count 0. The same happens when the node is deleted.
- **Node table.** The value of a file field is shown by the file name (`original_name`, and without it — the saved string); the names for the page are fetched by one query (`fileNames`), so the number of queries does not depend on the number of nodes. The column of a file field is not sortable (the value is an opaque string).

## Search for reference fields

The autocomplete of [`type_ref` and `node_ref` fields](#type_ref-and-node_ref-fields) calls two JSON endpoints of the admin group (`Webtack\Ecms\Http\Controllers\Admin\ReferenceLookupController`, only `GET`, available to every active user without a level check per type; not tied to a specific field):

| Path | Name | Parameters | Response |
| --- | --- | --- | --- |
| `/admin/lookup/content-types` | `admin.lookup.content-types` | `kind` — required, one of `content`, `page`, `block`; `q` — optional, up to 255 characters | `[{key, name}]` — types of this kind, `name` contains `q` |
| `/admin/lookup/nodes` | `admin.lookup.nodes` | `content_type` — required, the key of an existing type; `q` — optional | `[{uuid, title}]` — nodes of this type, `title` (the `default` language) contains `q` |

The response has at most 20 results (`ReferenceLookupController::LIMIT`) in a stable order (`name`, `key` / `title`, `id`); an empty `q` gives the first 20. The search is case-insensitive, and `%` and `_` in the query are searched literally (`LIKE … ESCAPE`). An unknown or missing `kind` / `content_type` is a validation error (`422` for a request with `Accept: application/json`, which the widget sends); an unauthenticated request is rejected by the `auth` middleware.

Tests: `tests/Feature/Admin/ReferenceLookupTest.php` (results, an empty query, the limit, `422`, a guest) and `ContentNodeReferenceTest.php` (table cells, form `labels`, sorting, the message about the deletion prohibition).

## Fetching video data

The "Fetch data" button of the [`youtube` field](content-values.md#youtube-videos) sends a separate request; it does not change the node, and the node itself does not go to YouTube.

`POST /admin/youtube/lookup` (`admin.youtube.lookup`, `YoutubeLookupController`, the group `auth` + `verified`; available only with the level `own`/`any` on some type or on media, otherwise 403), the body `{ "url": "…" }` (`YoutubeLookupRequest`: a required string). The logic is in `Webtack\Ecms\Youtube\YoutubeLookup`:

1. Parsing of the link (`YoutubeType::parse()`); Shorts becomes a regular `watch?v=`. Not a video → `invalid_url`, YouTube is not contacted.
2. The key is taken from `config('services.youtube.key')` (`YOUTUBE_API_KEY` in `.env`, the example — `.env.example`). Empty → `not_configured`, YouTube is not contacted. The key does not get into the response or into the Inertia props.
3. `GET https://www.googleapis.com/youtube/v3/videos?part=snippet&id=…` (timeout 10 s). A network, quota, access, or server error → `unavailable`; an empty `items` → `not_found`.
4. The largest screenshot (`maxres`, `standard`, `high`, `medium`, `default`; on failure the next smaller one) is downloaded to a temporary file and stored through `FileStorage::store()` in the `image` profile. Only `https` and the hosts `i.ytimg.com`, `img.youtube.com` are allowed; the address is taken only from the API response. If no size succeeded → `unavailable`. The screenshot is stored as the last step, so on any error no files are created.

Responses:

| Status | Body |
| --- | --- |
| `200` | `{ url, title, description, screen: { value, uuid, name, mime, size, url } }`; `url` — the entered link (for Shorts the regular one) |
| `422` | `{ message, reason }`, `reason` = `invalid_url` or `not_found` |
| `503` | `{ message, reason }`, `reason` = `not_configured` or `unavailable` |

The messages are translated through `__()` (keys in `lang/en.json` and `lang/uk.json`). A screenshot file that was obtained but not saved with the node remains a free file in the [media library](media-library.md).

## CopyableText

`Components/Admin/CopyableText.tsx` is a shared piece for values that are copied on click (the slug in the node table, the node `id` in the form). It is a native `button type="button"` (focusable, `Enter` / `Space` work) with props `value` (the copied text), `children` (the displayed content, clipped to one line with an ellipsis), optional `title` (defaults to `value`) and `className`; its `aria-label` is "Copy: :value". The click calls `stopPropagation`, copies through the Clipboard API (`navigator.clipboard.writeText`) and, when it is unavailable or denied (non-secure `http://` hosts other than localhost), through a hidden `textarea` and `document.execCommand('copy')`. The result is shown with a `sonner` toast: "Copied to clipboard" (`TOAST_SUCCESS_DURATION`) or "Could not copy to the clipboard".
